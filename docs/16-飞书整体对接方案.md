## 零、一句话结论

**组织架构同步与审批回流已生产可用，但「免登、机器人会话填表、用户问答」三项核心能力当前为零**——不是「做得少」，而是**底层授权链路一行代码都没有**（`feishu_client.py` 只有 `tenant_access_token`，无 `user_access_token`、无 OAuth、无 `app_ticket`、无长连接）。

因此本方案的核心判断是：

> **所有飞书侧新能力（免登 / 机器人 / 卡片 / 问答）共用同一个前置——飞书「用户态授权 + 机器人凭证」。这个前置没打通，后面全部做不了。所以开发顺序必须从它开始，而不是从用户可见的功能开始。**

### 1.3 两个隐性风险（不显眼但会踩）

**风险 A：`feishu_client.py` 是单 token 缓存架构**

```python
TOKEN_ENDPOINT = "/auth/v3/tenant_access_token/internal"
self._access_token: str | None = None
self._token_expires_at: datetime | None = None
```

`_get_access_token()` 是**单槽位**。若新增 `user_access_token` 而不独立缓存，**用户态 token 会污染租户态 token 的全局缓存** → 所有组织架构同步、审批回流会随机 401。

> **约束**：新增的 user/app token 必须**独立实例或独立槽位**，绝不共用 `_access_token` 字段。

**风险 B：飞书传入的身份是「用户可控输入」**

`docs/02-问答功能设计.md` §四已明确写死红线：

> 🔴 **模型生成的 `query_type` 和 `employee_id` 都不可信，必须由 L2 从 HTTP 身份推导**

**在飞书场景下这条红线更严重**——因为 `open_id` 来自飞书客户端上报的会话，**不能直接当作「当前提问人」的凭据**。必须走完整链路：

```
飞书事件 → 解密验签 → 取 open_id → 查 bot_session 拿已认证员工 → 查 feishu_identity → Employee
                                                    ↓
                                        ❌ 绝不能：直接拿 open_id 去查 Employee 就开始查数据
```

### 2.1 不可破的四条原则（沿用 `01-架构与决策.md`，此处按飞书场景重申）

| # | 原则 | 在飞书场景的具体含义 |
|---|---|---|
| **P1** | **飞书是入口与消息层，不是事实源** | 组织架构事实源 = 飞书通讯录；**绩效数据事实源 = 本系统 L2**。飞书表单/卡片只是采集通道 |
| **P2** | **分数只在 L2 产生** | 机器人、AI、飞书卡片**永远不能产生或修改分数**。机器人填表只写草稿，提交仍走 L2 状态机 |
| **P3** | **权限判定只在 L2** | 飞书传来的任何 ID（`open_id` / `employee_id` / `department_id`）**都不是权限凭据**。L2 必须从「已认证会话 → Employee → access_control」推导 |
| **P4** | **降级必须存在** | 飞书不可用 / AI 不可用 / 卡片发送失败，**主业务必须继续**。通知一律走旁路（现有 `notify_plan_submitted_safe()` 已验证此语义） |

## 三、五项能力详细设计

### 3.1 飞书免登（阶段 1）

#### 3.1.1 链路

```
员工点「飞书登录」
   ↓
GET /v1/feishu/auth/url?redirect_uri=...
   ↓ 后端生成 state（防 CSRF，短时效，存 session/Redis）
飞书 OAuth 授权页 → 用户确认授权
   ↓ 302 回 redirect_uri?code=xxx&state=xxx
POST /v1/feishu/auth/exchange { code, state }
   ↓
① 校验 state（防 CSRF + 防重放）
② app_access_token 换 user_access_token（OAuth code 换）
③ 用 user_access_token 调 /contact/v3/users/{user_id}?user_id_type=user_id
   → 拿 open_id / union_id
   ⚠️ **必须带 user_id_type=user_id** —— 漏了会按 open_id 解析，
   返回 99992351「not a valid {open_id}」，免登**查不到人**
   （2026-11-17 实测发现，见 `17` §0.0.1 F1）
④ FeishuIdentityService.resolve_employee(open_id=...) → Employee
   ├─ 解析不到 → 返回「未绑定」，引导走账号密码绑定流程
   └─ 解析到   ↓
⑤ 复用 routes/auth.py::_generate_token(employee.id, username, token_version)
   ↓
⑥ 返回本系统 token + 用户信息 → 前端写入 authStore，走现有全部路由
```

#### 3.1.2 关键设计点

| 点 | 说明 |
|---|---|
| **飞书 token 绝不落地前端** | `user_access_token` 只在后端内存活，用完即弃；前端只拿**本系统签发的 HMAC token** |
| **复用现有 `_generate_token`** | 已有 `token_version` 失效机制（离职/禁用立即失效）→ 免登**自动继承**这个安全能力 |
| **复用现有 `resolve_employee`** | 其 docstring 明确写「免密登录」是设计调用方；且已有「只认在职且启用账号」防线 |
| **state 防 CSRF** | state 需**一次性**、短时效（≤10 分钟）、绑定 redirect_uri |
| **保留账号密码兜底** | 飞书故障时不至于全员无法登录；前端保留原有登录入口 |
| **`open_id` 是 app 维度** | 同一用户在不同飞书应用下 `open_id` 不同 → 必须用**本应用的** `open_id`；`feishu_identity` 已按 `identity_type` 区分 `user_id`/`open_id`/`union_id`，天然隔离 |

#### 3.1.3 需要新增的文件

| 文件 | 类型 | 说明 |
|---|---|---|
| `backend/app/services/feishu_oauth.py` | 🆕 | 授权 URL 生成、state 签发/校验、code 换 token |
| `backend/app/routes/feishu_auth.py` | 🆕 | 2 个公开端点（url / exchange） |
| `backend/app/services/feishu_client.py` | ✏️ | **独立**加 `get_user_access_token()` / `get_app_access_token()` |
| `backend/app/core/config.py` | ✏️ | `feishu_oauth_redirect_uris`、`feishu_oauth_state_secret` |
| `frontend/src/views/Login.vue` | ✏️ | 「飞书登录」按钮 + 回调处理 |
| `frontend/src/api/auth.ts` | ✏️ | 2 个 API 封装 |

### 3.2 工作台机器人会话填表（阶段 2）

#### 3.2.1 这是差异化价值最高、也最容易被低估的一块

**核心洞察**：飞书机器人**不能**直接「填表单」——飞书侧没有「代填网页表单」的能力。可行路径只有两条：

| 路径 | 说明 | 评价 |
|---|---|---|
| **A. 卡片交互** | 机器人发交互卡片 → 员工在卡片里填 → 卡片回调 → 后端写入 | ✅ **推荐**。飞书原生支持、体验好、无需跳转 |
| **B. 打开本系统页面预填** | 机器人发带 token 的链接 → 员工在 Web 端填 | ⚠️ 可行但退化成「普通网页」；且链接 token 有泄露风险 |

> **决策建议**：以 **A（卡片交互）为主线**，B 作为「复杂表单（周计划多条目、月计划多行）」的补充 —— 卡片适合结构化、少字段的表单；复杂表格用 B 或「卡片 → 跳 Web 预填」混合。

#### 3.2.2 链路

```
员工在飞书工作台点「绩效助手」/ 或 @机器人
   ↓ 飞书推 im.message.receive_v1 事件
POST /v1/feishu/bot/events
   ↓ 复用 services/feishu_event.py：解密 → 验签 → 归一化
   ↓ 取 open_id（消息发送者）
   ↓ FeishuIdentityService.resolve_employee(open_id=...) → Employee
   ├─ 解析不到 → 回「请先绑定员工身份」+ 引导
   └─ 解析到 ↓
   ↓ 查 bot_session（open_id + 业务类型）→ 是否有未完成会话
   ├─ 无 → 按意图路由（见 3.2.3），发对应卡片
   └─ 有 → 按当前卡片状态继续
   ↓
【卡片交互】员工填表 → 点提交
   ↓ 飞书推 card.action.trigger 事件（回调）
POST /v1/feishu/bot/card/callback
   ↓ 校验（解密 + 验签 + session 归属校验）
   ↓ 按 action.value 路由 → 写业务草稿（month_plan / week_plan 草稿）
   ↓ 更新 bot_session 状态
   ↓ 回卡片「已保存草稿，去提交」按钮
```

#### 3.2.3 意图路由（机器人第一版能力）

| 员工说 | 机器人做 |
|---|---|
| 「填月计划」 | 发**月计划卡片**（周期 + 目标 + 权重 + 考核标准）→ 收集 → 写 `month_plan` 草稿 |
| 「填周计划」 | 发**周计划卡片** → 写 `week_plan` 草稿 |
| 「我的绩效」 | → 走 3.4 问答域 |
| 「提交」 | 调 L2 提交端点（**不是直接改状态**，走正常状态机） |
| 「查审批状态」 | 查 `plan_feishu_binding.instance_status` + L2 状态 |

#### 3.2.4 数据模型（新增 `bot_session` 表）

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `open_id` | 飞书用户标识（会话归属校验依据） |
| `employee_id` | 解析出的员工（**冗余存储**，避免每次重解析） |
| `session_type` | `month_plan` / `week_plan` / `qa` / … |
| `business_id` | 关联的业务草稿 ID（`month_plan.id` 等） |
| `card_state` | 卡片当前步骤（JSON 存已收集字段） |
| `status` | `active` / `submitted` / `expired` / `cancelled` |
| `expires_at` | 过期时间（建议 24h） |

| 文件 | 类型 | 说明 |

#### 3.2.6 关键坑位

| 坑 | 说明 | 规避 |
|---|---|---|
| **机器人事件不能用通讯录 webhook 那套 Token 模式** | `feishu_contact.py` 用的是「顶层/header token 比对」；机器人事件若后台启用了加密策略，body 是密文 | **统一走 `services/feishu_event.py`**（已有解密+验签+握手），但**事件类型**过滤分开 |
| **`app_ticket` 与长连接** | 机器人收消息需要 `app_ticket`（每 30 分钟刷新）或 WebSocket 长连接 | 阶段 2 先用**事件订阅回调**（与现有审批 webhook 同构，成本最低），长连接放阶段 6 |
| **卡片回调要校验 session 归属** | 否则 A 员工的卡片回调能被 B 触发 | `open_id` 必须与会话记录的 `open_id` 一致 |
| **卡片 JSON 2.0 结构严格** | 字段层级错一个就渲染空白 | 构造器单测 + 真机截图验证 |

### 3.4 用户问答（阶段 4）

> **严格遵循 `docs/02-问答功能设计.md`**，本节只补「飞书接入的增量设计」，不重复其三层架构。

#### 3.4.1 飞书场景的三层落地

```
飞书消息「@绩效助手 我这月绩效多少」
   ↓  L2 收消息事件 → 解密验签 → open_id → Employee（已认证）
   ↓  ★ 权限推导链在此完成，模型不参与 ★
   ├─ employee_id = 提问者本人（员工问自己）
   ├─ 主管问下属 → 从 access_control 拿直属下属列表（不认模型给的 ID）
   └─ HR 问部门 → 从 access_control 拿可访问部门
   ↓
GET /v1/qa/query（结构化数据，纯 SELECT）
   ↓
POST /v1/agent/qa（agent-service 生成自然语言回答）
   ↓
飞书回复（文本 or 卡片）
```

#### 3.4.2 飞书场景的三个额外约束

| # | 约束 | 说明 |
|---|---|---|
| **Q1** | **数据最小化**：发给模型的只有 `alias`（工号），**不含真名/部门/职位** | 沿用 `02` §五 D4 |
| **Q2** | **小部门 k-匿名**：< 5 人不返回平均分 | 沿用 `02` §九 D1 |
| **Q3** | **飞书回复里不暴露敏感数据** | 主管查下属分数时，回复内容只发给**有权限的人**；飞书消息本身是 IM 记录，需评估留存合规 |

#### 3.4.3 agent-service 需新增 `/v1/agent/qa`

沿用现有契约风格（与 `/v1/agent/draft` 一致：输入结构化数据 + 问题，输出回答 + `data_quality`，**不含任何数字生成**）。

> ⚠️ **质量前置**：`modelEnabled: false` / `EchoModelClient` 状态下，问答只能返回**模板化措辞**（取数正确、文案机械）。**建议先完成 P3-2 真模型接入**，否则阶段 4 的实际体验价值有限。

## 八、第一步可以立刻做的事

> ✅ **已于 2026-11-17 执行完毕**（详见 `17-飞书对接执行流程.md` §0.0）。
> **结论：权限无阻塞、绑定无缺口 → FS-1 可直接开工。**

**在写任何业务代码之前，先做「事实核查」**：

```powershell
# 1. 查飞书应用可见范围与身份绑定覆盖率（决定免登能覆盖多少人）
#    GET /v1/feishu/identities/unbound   → 未绑定的飞书员工
#    GET /v1/feishu/identities/conflicts  → 一人多号 / 一号多人
#
# 2. 扩 backend/scripts/check_feishu_scopes.py，新增探测：
#    - GET  /contact/v3/users/{user_id}          （免登基础）
#    - GET  /authen/v1/index                     （OAuth 授权页）
#    - POST /im/v1/messages                      （卡片/消息发送）
#    - GET  /application/v6/applications/:id    （app_ticket）
#    判读方式沿用 A8 文档 §4 的六类结果法（区分「权限不足」与「参数没传对」）
#
# 3. 结论若「权限不足」→ 立刻提 IT 申请（带具体接口 + 错误码，效率远高于泛泛申请）
#    结论若「权限已开通」→ 直接进阶段 1 编码
```

> 这一步成本极低（改一个脚本 + 跑一次），但能把最大的不确定性（RK1）**从假设变成事实**，避免按错误前提排期。
>
> **实测回报**：除确认「无阻塞」外，还查出了 **`user_id_type=user_id` 漏传会导致免登查不到人**
> 这一关键实现细节（F1）—— 这是纯靠读文档无法发现的。
