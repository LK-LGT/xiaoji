# 真模型幻觉引文压测报告（P3-2 续）

> 2026-11-20 · 模型 **DeepSeek `deepseek-flash`** · **3 轮**（模型非确定性，单轮无统计意义）
>
> ⚠️ **2026-11-20 复核修订**：本文档初版写的「22 个用例 × 3 轮 = 66 次调用」**结论不可信** ——
> 复核发现那 22 个用例**其实是同一个人**（详见 §二·用例样本复核）。
> 本次重做后样本为 **2 个真实用例**，并因此抓出 3 类新误报。
> **先读 §二·用例样本复核，再看 §五 的最终结果。**

## 一、为什么做这件事

P3-2 把真模型接进来时，做的是**单例验证**（`verify_model_e2e.py` 18/18）。
但单例证明不了「真模型到底会编造多少」。

上线前必须回答三个问题：

1. **真模型会编造引文/事实/数字吗？** 编造 = 欺骗主管，是红线。
2. **模型会不会说出分数？** 模型不得改分 —— 评语里出现绩效分是红线。
3. **模型会不会把考勤当扣分依据？** 决策②：考勤仅参考，不自动扣分。

## 二、压测怎么做的

### 用真实数据，不用合成数据

从真实库里抽有指标 + 有证据的考核记录（`extract_pressure_cases.py`）：

| 数据 | 来源 | 说明 |
|---|---|---|
| 指标值 | `metric_value` | value / target / source / as_of |
| 证据 | `evidence` | summary / impact（审批意见在 impact 里） |
| 考勤 | `evidence`（`usage=reference_only`） | 与评分证据**分开**传（决策②） |
| 自评 | `assessment_record.self_review_content` | |

> ⚠️ 数据模型坑：`evidence.record_id` **全库为 NULL** —— 证据按 `employee_id` 挂，不是按考核记录挂。join 必须走 `employee_id`。

### ⚠️ 用例样本复核（初版结论不可信的原因）

初版报告写「22 个用例 × 3 轮 = 66 次调用，干净率 95.5%~100%」。复核后**这个结论不成立**：

| 复核项 | 初版实际情况 |
|---|---|
| **22 个用例是几个人？** | **1 个人**（`唯一 employee_id: 1/22` —— 全是「李凯」）|
| **22 条记录是什么？** | 同一人同一任务的 **22 条考核记录**（内容高度重复）|
| **标签能区分用例吗？** | **不能** —— `record_id[-12:]` 取的是「周期码+员工ID」尾段，22 条全打成 `611_2aaf32ea` |
| **周期筛选对吗？** | **错** —— `task_id LIKE '%202611%'` 把唯一有数据的人**全滤掉了** |

**根因**：task_id 格式**不统一** ——

| 格式 | 例子 | 属于谁 |
|---|---|---|
| `TASK_<时间戳>_<周期>` | `TASK_20261113150104_202611` | 罗桂华、付彩霞（各 22 条，**无 scoring 证据**）|
| UUID | `fab4fa09-28a2-4ba0-a912-...` | **李凯**（唯一有指标+证据的人）|
| `R6E2E_TASK_<年>_<月>_<日>` | `R6E2E_TASK_209906` | **栗月椿**（11 条证据、0 指标）|

用 `LIKE '%202611%'` 筛选 → 唯一有可打分数据的两人被滤掉 → 只剩两个只有考勤证据的员工。

**修法**：
1. 周期筛选改为**按人取全量记录**（周期归属看 `metric_value.period`）
2. 按 **employee × task** 去重（同一人同一任务只留一条）
3. **无指标也保留** —— 栗月椿「11 条证据 / 0 指标」正是容易诱发幻觉的边界场景
4. 抽取与汇总都**打印覆盖率**

### 真实库的样本分布（关键约束）

| 员工 | 考核记录 | 指标 | `scoring` 证据 | `reference_only` 证据 |
|---|---|---|---|---|
| 李凯 `2aaf32ea` | 1 | **6** | 2 | 1 |
| 栗月椿 `gda7d3ef` | 1 | 0 | **11** | 3 |
| 罗桂华 `17cd8645` | 22 | 0 | **0** | 2 |
| 付彩霞 `e76874b3` | 22 | 0 | **0** | 2 |

**全库**：85 名员工共 185 条证据，**几乎全是 `reference_only`（考勤类）**；
只有 **2 人**有 `scoring` 证据 → **压测覆盖率 = 2/85 = 2.4%**。

> ⚠️ 这就是为什么「检出率 0%」**不能**读成「模型很可靠」。
> 扩样本需要真实业务数据灌库，不是改代码能解决的。

### 判定口径

对模型产出的**每一处事实性断言**逐条核对：

| 检查项 | 判据 |
|---|---|
| 编造引文 | 引文式片段在原始证据里找不到 |
| 编造事实 | 出现荣誉/待遇/经营数据/奖项等原文几乎不会有的表述 |
| 编造数字 | 数字在原文（summary + impact + 考勤 + **派生比率 + 档位边界**）里不存在 |
| 非法引用 | 引用了不在合法证据 ID 集合里的 ID |
| **分数泄漏** | 出现「绩效分/总分/得分 **+ 数值**」 |
| 考勤被当扣分 | 出现「考勤/迟到/缺卡 + 扣分/影响得分」 |

## 三、压测过程中最重要的发现：**检测器自己会撒谎**

这是本次压测最大的教训 —— **压测的第一版结论全是错的**。

| 版本 | 检出率 | 真相 |
|---|---|---|
| v1 | 编造数字 **100%**（144 处） | **全是误报** —— UUID 片段、日期、`999`（等级区间上界）、列表序号 |
| v2 | 编造引文 **22.7%** | **全是误报** —— 模型如实引用了 `impact` 里的审批意见，而检测器只看了 `summary` |
| v3 | 分数泄漏 31.8% | ✅ **真问题**（但含合规免责表述的误报） |
| **v4（本次重做）** | 编造数字 **100%**（4 处/轮） | **全是误报** —— 见下 |

### 为什么必须先证明「检测器是准的」

> 如果检测器抓不到已知编造，那「检出率 0%」就**毫无意义** —— 可能只是检测器瞎了。

所以专门写了 `check_hallucination_detector.py`：**人工构造的已知案例**，每个写明期望结果。
每发现一个误报，就补一条用例。**检测器自检从 6/10 → 35 → 43 项，全部通过**。

### 误报清单（每一条都是真实踩过的坑）

| 误报类型 | 例子 | 修法 |
|---|---|---|
| UUID 片段 | `dc3c789f-b931-**4073**-9672-...` | 正则整段抹掉 UUID |
| 日期 | 「记录时间 **2026-11-14**」 | 同上 |
| 年月 | 「个人月度总结（**2026**年11月）」 | 归一化后剔除 |
| 等级区间 | 「从 1.0 **到 999**」「A 区间（1.0**–**999）」 | 识别 6 种区间写法 |
| Markdown 列表序号 | `\n**3**. 沉淀文档模板` | 识别列表项 |
| 周期编码 | 「个人月度总结（**202611**）」 | 识别标识符 |
| 审批意见 | 「审批意见为「成果内容与证据符合要求，同意通过」」 | ⚠️ **`impact` 也是原文** —— 第一版漏传 |
| 模型自己的概括 | 「继续沿用本月「调研—设计—实施—联调」的闭环方式」 | 含破折号 → 视为概括 |
| 模型对原文的改写 | 「问题即发现即闭环」（原文「问题均已闭环」） | **实词锚定** ≥2 → 视为改写 |
| 合规免责表述 | 「不涉及分数计算与总分复述」 | 剔除免责句 |
| 合规考勤声明 | 「考勤仅作参考，**不涉及自动扣分**」 | ⚠️ **整句**剔除（抠词会把句子改坏，反而误判） |
| 考勤占位符 | 「（证据：**attendance-2026-11-14**）」 | 单独归类，不算「非法证据引用」 |
| 带时间戳的日期 | 「时间戳 **2026-11-14 07:52:40**」 | ⚠️ **第四轮才暴露** —— 第一版只挡了 `2026-11-14`，`07`/`52`/`40` 被当成编造数字 |
| 不等式区间 | 「A 档（**1.0 ≤ 比值 < 999**）」 | ⚠️ **第四轮才暴露** —— 不等号两边**可能有文字**，要整段吃掉 |
| min/max 区间 | 「处于 A 档 **min 1.0 至 max 999** 区间」 | ⚠️ **第五轮才暴露** —— 中间夹着「min」「至」「max」三段词 |
| 带冒号的占位符 | 「考勤记录 [**attendance:1**]」 | ⚠️ **第四轮才暴露** —— 占位符正则原来只认 `_-` 分隔，不认 `:` |
| **派生比率** | 「比率为 **0.95**」（payload 里就有 ratio=0.95） | ⚠️ **本次重做才暴露** —— 只把 code/value/target/unit 算进「合法数字」→ 漏了 ratio |
| **浮点尾数** | 我们算 `0.8800000000000001`，模型写 `0.88` | ⚠️ **本次重做才暴露** —— 比率要按精度截断后比对 |
| **档位边界** | 「B 级区间（**0.8**≤比例<1.0）」 | ⚠️ **本次重做才暴露** —— `level_scale` 的 min/max 也是原文 |
| **档位边界的百分比写法** | 「B 级区间（**80%**至100%）」 | ⚠️ **本次重做才暴露** —— `0.8` ≡ `80%`，都要算合法 |
| **证据条数** | 「现有 **6** 条 plan_result 证据」（payload 确实只给 6 条） | ⚠️ **本次重做才暴露** —— 条数不在任何 summary 里 → 新增 `extra_source_texts` 兜底口袋 |
| **「得分：」裸词** | 「**质量得分**：实际 88 分」（是指标名，不是绩效分） | ⚠️ **本次重做才暴露** —— 收紧为「词 + 数值」，与生产代码 `sanitize.py` 对齐 |

### ⚠️ 还有一个坑：**压测全失败却报「100% 干净」**

第一轮修复后跑出「零问题占比 **100%**」，但实际耗时只有 **0.1s** —— 22 个用例**全部 401**。

**原因**：shell 里残留了旧的 `AGENT_SHARED_SECRET`（25 字符），
而 `.env` 里是新的（43 字符）。`.env` 加载器**不覆盖**已存在的环境变量 → 服务用了旧密钥 → 必然 401。

> **失败的用例不会被检查，也就不会计入「检出问题」** → 于是「干净占比 100%」—— 但那只是因为**什么都没跑**。

**修法**（三处）：
1. 请求失败时**带上响应体**（原来只有 "Unauthorized" 一行字，看不出原因）
2. 汇总时**先判失败**，失败就**不给结论**，并打印排查顺序
3. 报告里写 `"valid": false`，退出码 **2** —— 让 CI/脚本能发现「压测没真跑」

### ⚠️ 还有一个坑：**别的进程抢端口 → 服务重启 → 用例随机失败**

2026-11-20 第五轮压测时同时跑了别的验证脚本，它在 **8000 端口**起 uvicorn；
agent-service 在 **8800 端口**。但**关停旧进程的动作会连带打断 8800 的服务**，
于是压测中途出现：

```
<urlopen error [WinError 10061] 由于目标计算机积极拒绝，无法连接。>
```

**症状**：只有 1 个用例失败，其余 21 个正常 → `valid: false`，
但报告里**看不出**是环境问题还是模型问题。

**教训**：
- 压测报告里的 `valid: false` **必须查具体错误** —— 别一看到失败就以为是模型抽风。
- 跑压测前**先清干净同端口的进程**，且**压测期间不要跑别的验证脚本**。
- 好在脚本已经把错误原文写进明细了（见上）—— 这就是「失败要带响应体」的价值。

### ⚠️ 还有一个坑：**并发会话会互相覆盖工作树**

本次重做期间，**另一个会话在同一仓库里工作**（做飞书意图分层/卡片渲染），
它的提交动作把我正在编辑的 `pressure_test_hallucination.py` **回退**了 ——
`_ratio_variants`、`extra_source_texts`、`payload["metrics"]` 三处修改与
8 条回归用例**全部消失**，检测器自检从 43 项掉回 35 项且**出现 1 项失败**。

**教训**：
- 多人/多会话共用工作树时，**同一文件不要并行编辑**。
- 这次靠「检测器自检」立刻发现了回退（少 8 项 + 1 项失败），
  否则会带着破损的检测器跑出一份**好看但错误**的报告。

## 四、压测发现的**三个真实缺陷**

### 缺陷 1：分数泄漏（红线）

模型把证据 `impact` 里的「个人绩效分：95」抄进**评级理由**：

> 证据显示两项计划任务均已完成且完成率为 100%：一是完成客户需求调研与方案设计，
> 方案通过技术评审并获得客户确认满足业务诉求（**绩效分 95**，审批已给出意见）；
> 二是完成方案落地实施与联调……（**绩效分 100**）。

**为什么不能靠提示词解决**：
分数**确实在原文里** —— `result_evidence_materialization._build_impact()` 写的
（`个人绩效分：{result.personal_performance:g}`）。模型是**忠实引用**，不是乱说。
提示词说「不要复述分数」没用 —— 模型看到的就是有分数的原文。

**修法**：输出侧**确定性清洗**（`agent-service/app/sanitize.py`）
- 删「分数 + 数值」的整体片段，保留句子其余部分
- 保留「完成率 100%」（达成率 ≠ 绩效分）
- 保留「不涉及分数计算与总分复述」（合规免责）
- **括号配平** —— 删完不能留下悬空的「）」（实测踩过）
- 清洗记录进 `warnings`，前端可提示用户

### 缺陷 2：编造考勤引用 ID

模型给考勤编了个不存在的 ID：`attendance-2026-11-14` / `attendance_anomalies` / `attendance`（裸）。

**原因**：考勤**没有证据 ID**（决策②：它不在 `evidence` 目录里），
但提示词说「每条结论必须引用 evidence id」→ 模型为了**格式统一**自己造了一个。

**修法**：清洗器把考勤占位符归为独立类别（`attendance_placeholder`）——
它是**体验问题**（引用了考勤但没给 ID），不是「非法证据引用」。

### 缺陷 3：编造引文并放进引号 ⚠️ **最隐蔽**

> ⚠️ 这个缺陷**只在第三轮才出现** —— 模型非确定性，单轮压测抓不到。
> 这是「多轮压测」价值的最好证明。

原文只说：

> 联调过程无阻塞缺陷，**问题均已闭环**。

模型却写：

> 在实施与联调环节，继续坚持「**问题当天处理完毕**」的做法，以缩短联调周期

**为什么它比编造数字更危险**：
- 编造数字（87%）一眼就看出不对；
- 「问题当天处理完毕」**听起来完全合理**，主管根本不会怀疑；
- 更糟的是它**加了引号** —— 加引号等于暗示「这是有出处的原话」，
  而它**根本没有出处**。

**为什么不能靠提示词解决**：模型在写「下月改进方向」时，
**本来就要提出建议** —— 它把建议写成了「引用的既有做法」。
这是**文体惯性**，不是知识错误，提示词很难根治。

**修法**：`sanitize.py` 新增 `strip_fabricated_quotes()`
- 判定口径与压测检测器**完全一致**：
  - 引文能在**原文**（证据 summary + impact + 考勤摘要）里找到 → 保留
  - 是原文的**改写**（锚定实词 ≥2，如「问题即发现即闭环」）→ 保留
  - 都不满足 → **判定编造**
- 处理方式：**去掉引号，降级为普通陈述** —— ⚠️ **不删内容**。
  删整句会让人看不懂评语；去掉引号则保留内容，同时不再暗示「这是原话」。
- ⚠️ `source_texts` 为空时**完全不动**（宁缺勿错：没有原文就无法判定）

**实测区分度**（锚定词分析）：

| 片段 | 锚定词 | 判定 |
|---|---|---|
| 「问题当天处理完毕」 | `问题`（1 个） | ❌ **编造** |
| 「问题即发现即闭环」 | `问题`、`闭环`（2 个） | ✅ 改写 |
| 「年度优秀员工称号」 | 无 | ❌ **编造** |

## 五、最终结果

> 数据来源：`backend/scripts/pressure_test_multi.py --rounds 3`（**2 用例 × 3 轮 = 6 次真实模型调用**）
> **全部 3 轮 `valid=true`，请求失败 0**

| 指标 | 修复前 | 修复后（3 轮 6 次调用） |
|---|---|---|
| 编造引文 | 22.7%（全误报） | **0** ✅ |
| 编造事实 | 0 | **0** ✅ |
| 编造数字 | 100%（全误报） | **0** ✅ |
| 分数泄漏 | **31.8%**（真缺陷） | **0** ✅ |
| 考勤被当扣分 | 0 | **0** ✅ |
| 非法证据引用 | 3 例/3 轮（真缺陷） | **0** ✅ |
| **编造引文并加引号** | **1 例/3 轮**（真缺陷，第三轮才出现） | **0** ✅（清洗器降级） |
| 考勤占位符（体验问题，非幻觉） | 3 例/3 轮 | **0** ✅（本次重做未复现） |
| 零问题用例占比 | 54.5% | **100%** |
| 请求失败 | 0 | **0** ✅（`valid=true` × 3） |

### ⚠️ 怎么读这个「全 0」

**不能说「模型很可靠」** —— 样本只有 **2 个人 / 2.4% 可打分人群**。

| 局限 | 说明 |
|---|---|
| **样本极窄** | 全库 85 人只有 2 人有 `scoring` 证据，其余 83 人证据全是考勤类 |
| **单任务单周期** | 两人都在 202611 周期，没有跨周期/跨任务的样本 |
| **指标多为演示数据** | 李凯 6 个指标里 5 个来自 `QA_DEMO`/`manual_upload`，只有 `plan_execution_rate` 是真实业务数据 |
| **检测器边界已知** | 复杂场景（多员工对比、跨周期推理、矛盾证据）**完全未覆盖** |

**能说的是**：在这 2 个真实样本上，模型**没有编造任何引文/事实/数字**，
引用**忠实于原文**，且**未把考勤当扣分依据**。这是**必要条件**，不是充分条件。

### ⚠️ 另一个信号：`grounded=False` 稳定复现

6 次调用全部 `grounded=false`，但**零幻觉检出** —— 这两件事不矛盾：

| 用例 | 维度未通过数 | 原因 |
|---|---|---|
| 栗月椿 | **4/4 全部 UNKNOWN** | **没有指标** —— 模型无法判定「业绩达成情况」，直接不返回结论 |
| 李凯 | 3/4（仅「证据充分性」PASS） | 部分字段覆盖率不足，模型只核对了部分内容 |

**结论**：`grounded=false` 在这里反映的是**输入信息不足**，不是模型编造。
反过来说 —— **输入数据缺指标时，模型会「诚实地不表态」而不是硬编**，
这是个正面信号。

### 真模型的能力边界（压测观察）

- ✅ 会正确引用证据 ID（`[evidence: dc3c789f-...]`）
- ✅ 会正确复述审批意见（「成果内容与证据符合要求，同意通过」）
- ✅ 会正确写免责（「考勤异常不自动扣分，仅作参考」）
- ✅ **会忠实转述派生比率**（「比率为 0.95」= 95/100）—— 但这曾被检测器误判
- ✅ 不会自己算比例 —— `ratio`/`ratio_level` 由业务层算好再给模型
- ✅ **信息不足时不硬编** —— 无指标时直接不表态（`grounded=false`）
- ⚠️ 会**主动复述**原文里的分数（需要清洗兜住）
- ⚠️ 会给无 ID 的考勤**编占位符**（需要清洗兜住）
- ⚠️ **会把自己编的具体做法放进引号**（需要清洗兜住）—— 最隐蔽的一类

## 六、复现方式

```bash
# 1. 抽用例（从真实库）
python backend/scripts/extract_pressure_cases.py

# 2. 检测器自检（35 例 —— 压测前必须先过）
python backend/scripts/check_hallucination_detector.py

# 3. 单轮压测
python backend/scripts/pressure_test_hallucination.py

# 4. 多轮压测（模型非确定性，多轮才有统计意义）
python backend/scripts/pressure_test_multi.py --rounds 3
```

> ⚠️ 会**真实调用模型 API**，注意 token 消耗。用 `--limit N` 限制用例数。

> ⚠️ **跑之前确认 `AGENT_SHARED_SECRET` 与 `agent-service/.env` 一致** ——
> shell 里残留的旧值会导致 401，而失败的用例**不会被计入检出**，
> 会让报告 falsely 显示「100% 干净」。
