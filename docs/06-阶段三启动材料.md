# 方案 B：考勤 → 主管评分页展示链路

## B.1 现状盘点（已勘察）

**后端已具备主要能力**，但有 **2 个真实缺口**（下方已列实测证据）：

```
backend/app/main.py:360-401
  GET /api/records/{record_id}          ← 注意是 /api/ 不是 /v1/
    → evidence.reference_only = evidence_service.build_attendance_view(reference_ev)
    → 已包含：type / count / summary / approved / as_of / disclaimer
```

新增的 5 个考勤端点也已可用（`/v1/attendance/*`）。

### 缺口 1：考核记录详情没有「待评记录列表」接口

实测 `GET /v1/assessment/records` → **404**。现在只有单条详情
`GET /api/records/{record_id}`。而 `ManagerReview.vue` 需要的恰恰是
「待评下属列表」。后端没有这个列表接口，前端无法对接。

### 缺口 2：考勤证据没有按考核周期过滤（**必须修**）

实测证据：

```
AssessmentRecord  →  没有 period 字段
AssessmentTask    →  有 period 字段，值形如 "202611"（紧凑 YYYYMM）
考勤 Evidence     →  source_ref 周期段形如 "2026-11"（带横杠 YYYY-MM）
```

`get_record()` 调 `list_scoring_evidence(db, rec.employee_id)`，
**只按员工过滤，不按周期过滤**。实测结果：

```
员工 2aaf32ea 的考核记录（202611 周期）
  → reference_only evidence = 1 条：2aaf32ea|2026-11|attendance|missing_punch
```

如果该员工还有 2026-10 的考勤证据，**会一起被返回**。
后果：主管评 10 月的绩效，页面上会显示 11 月的考勤异常 —— 这是口径错误，
比缺功能更严重。

**修复方向**（低成本）：
1. `get_record()` 改为经 `AssessmentRecord.task_id` → `AssessmentTask.period`，
   把 `202611` 转成 `2026-11` 后过滤 `source_ref`；
2. 或给 `AssessmentRecord` 补 `period` 列（更干净，但要走迁移）。

**唯一缺口在前端**：

```
frontend/src/views/performance/ManagerReview.vue
  → allRecords = ref<any[]>([...])   ← 硬编码 Mock 数据
  → 没有调用任何后端接口
```

| B-5 | 接入主管评分页 | 替换 Mock，接真实 record 详情 + 考勤面板 | 1 天 |
| B-6 | 员工自查页 | 同样的组件，个人视角（复用同一组件） | 0.5 天 |

## B.3 验收标准

| # | 标准 | 验证方式 |
|---|---|---|
| B-S1 | **考勤证据按考核周期过滤** | 评 202611 周期时，不返回 2026-10 的考勤证据 |
| B-S2 | 主管评分页展示真实考勤数据，六类异常齐全 | 用真实员工联调 |
| B-S3 | 每条考勤异常都带**免责标注**「不自动扣分，仅作参考」 | 目视 + 断言 |
| B-S4 | 展示**数据截至时间**（as_of） | 目视 + 断言 |
| B-S5 | **前端不产生任何算分行为** | 代码走查：前端无 attendance → score 路径 |
| B-S6 | 主管只能看下属考勤，员工只能看自己 | 越权请求返回 403 |
| B-S7 | 打卡明细可下钻查看 | 可展开看日期级记录 |
| B-S8 | 待评列表来自真实接口，不再是 Mock | 搜索确认 |
| B-S9 | 全量测试不回归 | pytest 全绿 |

## B.4 风险与注意点

1. **免责标注必须显眼**：决策②明确「六类全部展示、均不自动扣分」。
   建议用 `el-alert` 或灰色标签，**不能**用红色警告色暗示扣分。
2. **周期口径必须先修（缺口 2）**：不修就会出现「评 10 月看到 11 月考勤」。
   这是 B-1 的核心，优先级高于任何前端工作。
3. **请假要区分已审批/待确认**：当前 `leave` 一律 `approved=true`（飞书排班免除）。
   若后续接入审批数据，这个语义要改。
4. **overtime / outside 无真实数据**：面板上这两类会是空的，
   需要决定是隐藏还是显示 0，避免看起来像功能坏了。
5. **口径与证据表可能不一致**：`attendance_record` 是逐条，
   `Evidence` 是按「员工×周期×类型」聚合。展示层要用哪个要明确。
6. **主管评分页当前全是 Mock**：接真实数据会暴露一批原本被 Mock 掩盖的问题
   （空状态、字段缺失、异常分支），工时可能上浮。
7. **待评列表接口要按阶段一权限模型设计**：
   主管看直属下属、部门负责人看管理范围、HR 看全部 —— 不要用简单的
   `manager_id == user_id` 硬编码，否则和阶段一的权限体系打架。

# 建议

**建议先做方案 B**，理由：

1. 后端主要能力已就绪，B 的工作量集中在前端 + 2 个已定位的后端前置，风险可控；
2. 考勤数据已真实入库，B 可以立刻在真实环境联调，闭环快；
3. B 做完后再做 A 时，成果计划产生的证据**已经有地方展示**（主管评分页），
   两个阶段的成果能串成一条链路，而不是各自孤立；
4. A 的最大不确定性（飞书成果计划数据源）需要你去确认，
   在你确认前，A 的 A-1 探测随时可以插入。

**B 有一个必须先做的正确性修复**（缺口 2）：
考勤证据按周期过滤。不修的话，主管评 10 月绩效会看到 11 月的考勤异常。
这属于「宁可少做也不能做错」，所以我把它排在 B-1，优先于所有前端工作。
