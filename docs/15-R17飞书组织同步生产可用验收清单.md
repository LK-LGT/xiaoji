## 2. 关键设计决策：飞书游标的真实能力边界

### 2.1 飞书通讯录 API **没有**「按更新时间拉取变更」的端点

这一点经飞书开放平台文档核实：

- `GET /contact/v3/departments/0/children` —— 仅支持 `page_token` / `page_size` 分页
- `GET /contact/v3/users` —— 仅支持 `page_token` / `page_size` / `department_id`

真正的「按变更增量」只有一条路：**订阅事件**
（`contact.user.updated_v3`、`contact.department.deleted_v3` 等），
需要应用订阅 + 开放平台配置，且事件推送可能丢失。

> **因此**：本实现采用「**分页游标续传 + 按飞书稳定 ID 幂等 upsert**」，
> 而不是伪装成「只拉变更」。这是当前接口能力下**能达到的最优解**，
> 也与原代码文档中的判断一致。

### 2.2 本轮实现的「增量」到底省掉了什么

| 能力 | 效果 |
|------|------|
| **分页续传** | 批次中断后从断点继续，最多重拉 1 页，而非重拉全部 |
| **按部门切分** | 增量模式下跳过游标之前已处理的部门（`departments_to_process`） |
| **幂等 upsert** | 拉到的实体按 `user_id` / `department_id` upsert，没变的不动 |
| **失败不推进** | 批次有失败时游标**不推进**，下次从断点重来，绝不跳过失败数据 |

### 2.3 ⚠️ 安全兜底：游标失效时退化为全量

飞书部门树返回顺序**不保证稳定**，且部门可能被删除。
因此不能简单地「跳过前 N 个」，必须：

- 用 `checkpoint` **之后的部门 ID 集合**判断，而非位置；
- 若 `checkpoint` 指向的部门**已不在远端** → 位置失效 → **退化为全量处理**。

> 宁可多同步，也**不能漏同步**。这一条有专门的回归测试
> `test_incremental_degrades_to_full_when_checkpoint_vanished`。

### 2.4 ⚠️ 安全约束：离职判定的前提

「远端没拉到这个人」有两种截然不同的含义：
1. 这个人真的离职/被删除了；
2. 这次**没拉到**（接口抖动、权限变化、拉取失败）。

把 2 误判成 1 = 整部门员工被停用。因此：

- 任一部门拉取失败 → 快照标记为**不完整**；
- 只有 **全量模式 + 快照完整** 才允许把「远端缺失」解释为离职；
- 增量模式**一律不做**离职判定。

## 3. 本轮修复的实际缺陷

开发过程中通过真实库验证与测试发现并修复了 3 个**真实缺陷**（非需求字面要求，但属生产可用性必要项）：

### 3.1 Token 本地有效期计算错误（`feishu_client.py`）

**原代码**：
```python
self._token_expires_at = datetime.now(timezone.utc) + timedelta(
    seconds=max(30, expires_in - 300)
)
```

**问题**：当 `expires_in <= 330` 时，`expires_in - 300` 为负数，被 `max(30, ...)`
兜成 30 秒 —— 也就是**声称**这个 token 还有 30 秒有效期，哪怕它 5 秒后就过期。
客户端据此继续使用过期 token → 撞上 401 → 整条链路多一次往返。

**修复**：
```python
if expires_in <= 30:
    effective_ttl = 0.0
else:
    effective_ttl = float(min(expires_in, max(30, expires_in - 300)))
```

**语义**：本地 TTL **永不超过** token 的真实寿命；正常 token 提前 300s 过期；
极短命 token 不会被「延长」。

### 3.2 主动离职 / 冻结状态漏判（`organization_sync.py`）

**原代码**只看 `is_exited` 和 `is_activated`：
```python
employment_status = "exited" if status.get("is_exited") else (
    "inactive" if not status.get("is_activated", True) else "active"
)
```

**漏掉的两个飞书状态位**：

| 字段 | 含义 | 原行为 | 风险 |
|------|------|--------|------|
| `is_resigned` | 主动离职 | 当成 active | **离职员工仍可登录**（安全漏洞） |
| `is_frozen` | 冻结停用 | 当成 active | **冻结员工照样能登录**（安全漏洞） |

**修复**：新增 `_resolve_employment_status()`，按
`is_exited`/`is_resigned` → `exited`，
`is_frozen`/`is_activated=False`/`is_unjoin` → `inactive`，
否则 `active`。

**同时修正了账号恢复语义**（原先用赋值后的新状态判断，是个隐蔽 bug）：

| 场景 | 旧状态 → 新状态 | 账号处理 |
|------|-----------------|----------|
| 离职 | active → exited | 禁用，`token_version` 递增（**不自动恢复**，需人工复职） |
| 冻结 | active → inactive | 禁用，`token_version` 递增 |
| 解冻 | inactive → active | **自动恢复** `enabled` |
| 离职后复职 | exited → active | **不自动恢复**，需人工确认绑定 |

### 3.3 部门员工拉取失败未计入统计（`organization_sync.py`）

**原代码**：部门**写入**阶段失败会计入 `departments_failed`，
但部门**拉取**阶段失败（`fetch_employees_in_department` 抛错）只记进 `_failed_departments`，
**没有**计入统计、**没有**落错误记录。

**后果**：批次状态显示 `ok`、对账看起来干净，
但这个部门的员工其实**一个都没同步** —— 运维完全看不出「少了半个部门」。

**修复**：新增 `_failed_fetch_departments`，拉取阶段失败同样
计入 `departments_failed` + 写 `OrganizationSyncItemError`。

## 4. 数据库迁移

新增迁移 `0018_widen_sync_cursor_resource_type`：

```
organization_sync_cursor.resource_type : VARCHAR(32) → VARCHAR(128)
```

**为什么**：增量同步按部门粒度记录分页续传位置，游标键为
`员工:<64位部门ID>`（飞书部门 ID 是 64 位十六进制串），总长约 67 字符，
`VARCHAR(32)` 装不下。SQLite 不强制长度但 **PostgreSQL 会直接报错**。

- ✅ 幂等：已检查列长度，可重复执行
- ✅ 已在真实库 `backend/data/perf.db` 应用并验证
- ✅ CI 迁移往返测试（升级 → 降级 → 升级）通过

### 8.1 真正的事件驱动增量尚未接入（建议 R18）

当前增量依赖**轮询 + 分页游标**。若要达到「变更秒级可见」，

> ⚠️ 事件订阅需要：开放平台应用配置 + 事件回调地址 + 签名校验。
> 这不是代码问题，是**飞书侧配置**，建议单独排期。

### 8.2 对账显示 `conflict_count=279`（真实库遗留数据）

真实库副本上发现 **279 条身份映射冲突**。这与本次同步改造无关，
是历史数据遗留。含义：多个 `FeishuIdentity` 指向同一飞书用户，或同一员工有多个身份记录。

**建议**：上线前跑一次身份冲突清理，否则会影响员工身份绑定与登录。
当前 `GET /sync-organization/errors` 与 `/reconciliation/latest` 已能定位这些记录。

### 8.3 PostgreSQL 真机验证未做

本次在 SQLite 上验证。`resource_type` 扩容正是为 PostgreSQL 准备的
（SQLite 不强制 VARCHAR 长度，PostgreSQL 会直接报错）。
**建议部署到 PostgreSQL 后重跑一次迁移与同步**，确认无长度/约束问题。
