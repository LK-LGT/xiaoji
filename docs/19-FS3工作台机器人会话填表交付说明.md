## 一、功能是什么

员工在飞书里跟机器人说一句话，机器人回一张**填表卡片**，
员工在卡片里填完点「保存草稿」，草稿落到本系统 `month_plan` 表。

```
员工：填 2026-11 的月计划
  ↓
机器人：回「填 2026-11 月计划」表单卡片
  ↓
员工：填内容 → 点「保存草稿」
  ↓
机器人：写 month_plan 草稿 → 回「草稿已保存」卡片（带「去提交」链接）
  ↓
员工：点「去提交」→ 跳到系统 → 走**正常**提交审批流程
```

---

## 二、⚠️ 一条最重要的边界：机器人只写草稿

**机器人不提交、不审批、不改任何业务状态。**

| 动作 | 谁来做 |
|---|---|
| 填表内容写进 `month_plan` | 机器人（状态 = `draft`） |
| 提交月计划 | 员工在系统里点「提交」（L2 状态机） |
| 审批 | 主管 / HR（正常审批链路） |

这是 Runbook §4.2 约束 **C4**。落地方式：
- 机器人只调 `planning.upsert_month_plan_draft()`，**不调** `submit_month_plan()`；
- 回执卡片措辞是「**草稿已保存**」，**不是**「已提交」——
  说「已提交」会让员工以为审批已经走完。

## 四、🔧 飞书后台配置（需要 IT / 管理员操作）

### 4.1 开启机器人能力

1. 开发者后台 → 你的应用 → **应用能力** → 添加「**机器人**」
2. 机器人能力页里能看到 App ID / App Secret（与 `.env` 里的 `FEISHU_APP_ID` 一致）

### 4.2 订阅事件

**事件与回调 → 事件配置 → 订阅方式：长连接 or Webhook**

> ⚠️ 本系统走 **Webhook**（HTTP 回调），不是长连接。
> 长连接需要常驻进程，与本项目的部署形态不匹配。

添加这两个事件：

| 事件类型 | 用途 |
|---|---|
| `im.message.receive_v1` | 接收员工消息（识别「填月计划」） |
| `card.action.trigger` | 卡片交互（保存草稿） |

### 4.3 配置回调地址

**事件与回调 → 事件配置 → 请求地址**

```
生产：https://<你的域名>/v1/feishu/bot/events
本地：http://localhost:8000/v1/feishu/bot/events
```

保存时飞书会 POST 一个 `challenge` 做校验，**必须在 1 秒内**返回：

```json
{"challenge": "<飞书给的值>"}
```

本系统已实现（`feishu_bot.py` 的 `_read_verified_body` + 端点里的握手分支）。

### 4.4 配置卡片回调地址（可选）

**事件与回调 → 卡片回调地址**

```
https://<你的域名>/v1/feishu/bot/card/actions
```

> 可以**不配**——`card.action.trigger` 也会推到事件订阅地址。
> 配成独立地址的好处是排查时能分开看「消息事件」和「卡片回调」两条链路。

### 4.5 申请权限

| 权限 | 用途 |
|---|---|
| `im:message:send_as_bot` | 机器人发消息 / 发卡片 |
| `im:message.p2p_msg:readonly` | 接收单聊消息（员工私聊机器人） |
| `im:message.group_at_msg:readonly` | 接收群聊 @ 机器人（可选） |
| `contact:user.employee_id:readonly` | 拿到 `user_id`（用于匹配本系统员工） |

### 4.6 Encryption Key / Verification Token

**事件与回调 → 加密策略**

| 项 | 本系统的用法 |
|---|---|
| Encrypt Key | 配了 → 走「验签 + 解密」；不配 → 明文模式。**两种都支持**。 |
| Verification Token | ⚠️ **必须填 `FEISHU_BOT_EVENT_TOKEN` 的值**（机器人专属） |

**关于 Verification Token（重要）**

飞书开发者后台里，每个应用订阅事件时会生成一个 Verification Token。
本系统要求机器人用**独立**的 Token（约束 C2）：

```
FEISHU_BOT_EVENT_TOKEN=<你在后台看到的 Token>
```

⚠️ **不要**把它填成 `FEISHU_APPROVAL_WEBHOOK_TOKEN` 的值。
审批 / 通讯录 / 机器人是**三条独立的事件源**，共用一个 Token 的代价：
排障时分不清是哪条链路被调；一次泄露全线失守。

> 如果应用已经为审批事件订阅生成了 Token，机器人的订阅会生成**另一个** Token。
> 找不到的话，在「事件与回调 → 事件配置 → 订阅方式」里重新保存订阅，
> 后台会显示该订阅对应的 Verification Token。

### 4.7 环境变量

```bash
# backend/.env
FEISHU_BOT_EVENT_TOKEN=<后台的机器人 Verification Token>
FEISHU_BOT_SESSION_TTL_MINUTES=120
FEISHU_BOT_ENABLED=true
```

## 五、🔒 安全边界（这几条不能改）

| # | 约束 | 实现 |
|---|---|---|
| **C1** | 机器人事件走 `services/feishu_event.py` | 复用解密 + 验签 + 握手，**不**用 `feishu_contact.py` 那套顶层 token 比对 |
| **C2** | 独立 Verification Token | 新增 `FEISHU_BOT_EVENT_TOKEN`，**不复用**审批的 |
| **C3** | 卡片回调校验 session 归属 | `open_id` 必须与会话记录一致，否则**拒绝** |
| **C4** | 只写草稿，不改状态 | 只调 `upsert_month_plan_draft()`；回执说「已保存」不说「已提交」 |
| **C5** | 测试 fixture 用官方原始报文 | 见下节 |
| **C6** | 卡片 JSON 2.0 结构严格 | 卡片结构由 `feishu_card.py` **唯一**出口产出，有护栏禁止绕过 |

### 5.1 为什么 C3 最重要

**卡片是可以转发的。**

不校验 `open_id` 的话：A 把卡片转发给 B，B 点「保存草稿」，
草稿就写进了 **A 的名下**。本系统已实现校验并有测试：

```
test_card_action_rejects_other_users_open_id   → 越权回调被拒，且不写任何数据
```

### 5.2 为什么 C5 最重要（A8 的血泪）

A8 的 35 个测试全绿，是因为「测试 payload 是照着实现自己构造的」——
自证自洽，测不出「实现和真实协议不符」。

本项目的 fixture **逐字段照抄飞书开放平台官方文档**：

| fixture | 官方来源 |
|---|---|
| `OFFICIAL_MESSAGE_EVENT` | [接收消息事件](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/events/receive) |
| `OFFICIAL_CARD_ACTION_EVENT` | [卡片回传交互回调](https://open.feishu.cn/document/feishu-cards/card-callback-communication) |

**这个做法当场抓到了三个真 bug**（都是「照着自己构造 payload」发现不了的）：

| # | 官方文档里的细节 | 如果没照抄会怎样 |
|---|---|---|
| 1 | 群聊文本带 `@_user_1` 占位符 | 意图识别匹配不到关键词 |
| 2 | `action.value` 类型是 **string 或 object** | 只按 dict 解析 → **所有按钮都不生效** |
| 3 | `form_value` 多选组件回传**数组** | 写成 `"['a', 'b']"` 脏数据 |
| 4 | 官方明确：**用 `message_id` 去重，别用 `event_id`** | 飞书重推 → 同一条消息处理两次 → 两条草稿 |

## 六、验收清单（真机走查）

⚠️ **代码层面的测试覆盖了逻辑，但覆盖不到「飞书真实报文 + 真实卡片渲染」。**
下面每一条都必须用**真飞书账号**走一遍。

### 6.1 功能验收（对应 Runbook §4.4）

- [ ] 飞书里发「填月计划」→ 收到卡片
- [ ] 卡片填完提交 → **后端 `month_plan` 草稿落库**（查库确认，不是只看界面）
- [ ] 卡片回执正确显示「已保存」
- [ ] 点「去提交」→ 走正常提交流程 → 状态正确流转
- [ ] 重复点击提交 → 幂等（不产生两条草稿）

### 6.2 卡片渲染验收（C6）

- [ ] 卡片**不空白**（JSON 2.0 层级写错就是空白，飞书不报错）
- [ ] 表单输入框能正常输入
- [ ] 数字字段能填数字
- [ ] 「保存草稿」/「取消」按钮可点

### 6.3 安全验收

- [ ] 未配 `FEISHU_BOT_EVENT_TOKEN` 时端点返回 503
- [ ] 用**审批的** Token 打机器人端点 → 401
- [ ] 用 B 的 open_id 点 A 的卡片 → 拒绝且不写数据

### 6.4 配置验收

- [ ] 飞书后台保存回调地址时握手成功（challenge 回显）
- [ ] 加密模式下（配了 Encrypt Key）事件能正常处理

## 七、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | **只支持月计划** | 意图识别目前只认「月计划」相关关键词。周/日计划未接。 |
| 2 | **卡片一次一条** | 一次提交写**一条**条目。多次填表会**累加**（每次 upsert 一条）。 |
| 3 | **多选组件被拍平** | 表单多选值转成逗号分隔字符串存进 `quality` 等文本字段。 |
| 4 | **不识别富文本** | 员工发图片/文件/富文本 → 走「听不懂」提示。 |
| 5 | **没有会话过期清理任务** | `expires_at` 已落库，但**没有**后台任务删过期会话（会话行会累积）。 |
| 6 | **「去提交」链接是相对路径** | 回执卡片里的链接是 `/planning/month/<plan_id>`，**依赖**员工是在系统域名下的会话里点。若卡片在飞书 App 内打开，需改成绝对 URL。 |

> ⚠️ **限制 6 是上线前要确认的**：飞书 App 内点击相对路径链接的跳转行为，
> 建议在真机走查时确认；若不通，改为配置绝对 URL 前缀。
