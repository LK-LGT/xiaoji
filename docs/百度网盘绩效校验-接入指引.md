## 二、⚠️ 实测发现的三个关键事实（与官方文档不符）

| 官方文档说 | 实测结果 |
|---|---|
| 应用只能访问 `/apps/{appname}` | ❌ **不成立** —— `file?method=list` 能读**任意授权目录**（如 `/成品-小瑶`） |
| 递归用 `multimedia?method=listall` | ❌ **读不了业务目录** —— 报 `20020 该路径不在允许的访问范围内` |
| —— | ⇒ **递归必须自己用 `file?method=list` 逐层下钻** |

**代码已按实测改**：`list_files_recursive` 改成自建递归（`file?method=list` 下钻），
带最大深度限制（4 层）+ 单目录失败不中断整轮 + 根目录失败必须冒泡。

### ⚠️ 第二个关键事实：上传时间 ≠ 制作日期

用户网盘结构：`/成品-小瑶/11月/11.19/xxx.mp4`

```
11.19 目录里的文件，上传时间是 2026-11-20；
11.5  目录里的文件，上传时间是 2026-11-06。
```

⇒ **按 `server_ctime` 归日会整体错位**（11.19 做的片子算到 11.20 头上）。

⇒ **业务日期必须从目录名解析**（`11月` / `11.19`）。
`parse_period_from_path` 负责这件事，
`business_day` 优先用目录名、解析不出才降级用上传时间。

⚠️ `11.19` 的语义是 **11 月 19 日**（中文习惯月在前）——
写反会读成 11 月 11 日，有测试守着。

### 前端设计约束（均有测试守着）

⚠️ **核对面板只在主管评价时显示** —— 员工填报（`is_own`）时不显示。
网盘计数是**部门级**总量，在填报阶段给员工看会造成「这是我的产出」的误解。

⚠️ **前端自己写死「不产生任何分数影响」** —— 不依赖后端传文案。
（原本只渲染后端的 `notice`，后端文案一变前端就静默失去这道提示。）

⚠️ **权限位 `system:pan-verification:manage` 三处贯通** ——
后端 `ROLE_UI_PERMISSIONS` → 路由 → 侧边栏必须同一个值，
否则会出现「侧边栏藏了但能敲 URL 进来」的漏洞。

## 五、三个百度特有的坑（已在代码里处理）

### 坑 1：`refresh_token` 只能用一次

官方原文：*"refresh_token 只支持使用一次，refresh_token 使用后失效，
下次刷新 Access Token 时需要使用上一次刷新请求响应中的 refresh_token"*

⇒ 刷新后**必须**把响应里的新 refresh_token 存回数据库。
不存 ⇒ 30 天后整条链路断掉。

**已处理**：`baidu_pan_service._save_tokens` 里
```python
if tokens.refresh_token:
    row.refresh_token = tokens.refresh_token
```
⚠️ 注意 `if` —— 刷新响应**可能不含**新 token，那种情况要沿用旧的。

**测试覆盖**：`test_ensure_access_token_refreshes_and_saves_new_refresh_token`、
`test_ensure_access_token_keeps_old_refresh_token_when_not_returned`。

### 坑 2：错误码不在 HTTP 状态码里

百度**一律返回 HTTP 200**，错误藏在响应体的 `errno` 字段。

只看 HTTP 状态码 ⇒ 把失败当成功 ⇒ 数据静默为空。

**已处理**：`_xpan_request` 强制检查 `errno`，非 0 抛
`BaiduPanError` 并翻译成人话。

### 坑 3：`/apps` 限制的实际范围（实测推翻文档）

见上文「实测发现的三个关键事实」。

## 九、设计原则：不自动改分

```
网盘文件 ──> baidu_pan_count ──> 主管核对视图
                                     ↓
                        申报 6 条 / 实测 5 条
                                     ↓
                     "相差 1 条 —— 请核实后人工评定"
```

⚠️ **比对结果里没有任何分数字段** —— 由 `compare_with_report` 保证，
有测试 `test_compare_result_has_no_score_field` 守着。

⚠️ **网盘计数是部门级总量，没按人拆** —— 网盘文件不带"谁剪的"信息
（得靠文件名猜）。核对视图里 `actual` 保守留空，
由主管自己判断归属。等飞书多维表格接入（它有提交人字段）才能按人核对。

理由与 `semantic_qc` / `distribution_qc` 一致：
**数据源只提供依据，判定权在人**。
