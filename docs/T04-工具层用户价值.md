> 文档版本：v1.0

> 配套：`docs/T03-工具层落地执行方案.md`（怎么做）、`docs/T02-工具层实施方案-v2.md`（为什么这么做）

## 一、先说结论：工具层把「AI 助手」从摆设变成能干活的

现在的项目里，AI 助手长这样：

| 用户看到的 | 后端实际返回 |
|---|---|
| 点「AI 助手」→ 生成月计划 | `_empty_generate_response()` —— `items: []` |
| 点「AI 检查」→ 检查月计划 | `issues: []`、`notice: ""` |
| 点「优化单条任务」 | `_empty_plan_item()` —— 全是空字符串 |

`backend/app/routes/employee_ai.py:444` 的 `_empty_generate_response()` 是**字面意义的空壳**。前端 `PlanAiAssistant.vue` 渲染得再漂亮，后端返回的也是空数组。

**工具层做的事，一句话讲清**：

> 让 AI 从「只会写文字」变成「会自己查数据、查完再写」。

现在的 AI 只能基于**请求体里已经塞好的**东西作答。塞了什么它就只能说什么。
工具层给了它三个能力：
1. **自己取数** —— 说「查一下我这个月哪些指标没达标」，它自己去调工具拿真实数据
2. **自己组合** —— 需要几个数据源就调几次工具，自己判断顺序
3. **自己判断够不够** —— 数据不全时它会说「查不到」，而不是编一个

## 二、具体到每个角色，能多做什么

### 2.1 员工 —— 从「填表机器」到「有人帮我看数据」

**现在的痛点**：想知道「我这个月做得怎么样」，只能自己打开报表、逐个指标看、自己心算达成率。

**有工具层之后**：

```
员工问：「我这个月哪些指标没达标？为什么？」

AI 行为：
  1. 调 get_metric_values(period="202611")
     → 拿到 5 个指标：GMV 达成率 92%、客户数 78%、回款 105%...
  2. 调 get_evidence(period="202611")
     → 拿到这个月关联的证据卡片
  3. 组织语言回答：哪些没达标、缺口在哪、证据支持到哪一步
```

**关键点**：达成率 92% 这个数**不是 AI 算的**，是 `scoring.score_record()` 算完它复述的。

这条对应 `docs/01-架构与决策.md` 的原则①：模型永不产生分数。所以员工问「为什么是 78 分」，AI 只能解释「因为达成率 92% 落在 B 区间」，**不能**说「我觉得你努力了应该给 85」。

**多出来的具体收益**：
- 不用来回切页面 —— 一个问题问完所有维度
- 追问可以继续 —— 「那客户数差在哪？」→ AI 带着上一轮的工具结果继续调
- 每个结论都带引用（`citations`）—— 员工能点回去看原始数据，不用信 AI 的话

### 2.2 主管 —— 从「看汇总表」到「直接问对比」

**现在的痛点**：想知道「我团队里谁这月掉得最厉害」，要打开筛选、导出、再自己排序。而且**现在连"查下属"这个操作都是坏的**（见下文 §四）。

**有工具层之后**：

```
主管问：「张伟这月比王芳差在哪？」

AI 行为：
  1. 调 get_metric_values —— 分别取两人的指标
  2. 对比后组织语言：差在回款率（78% vs 95%）和客户数（85% vs 102%）
```

主管拿到的是**差异分析**，不是两张表让他自己比。

**多出来的具体收益**：
- 省掉「导出 Excel 自己透视」这一步
- 差异是 AI 按指标逐个对齐后说的，不会张冠李戴
- 主管看到的仍然是聚合口径，不会暴露员工隐私（部门 < 5 人时 AI 拿不到平均分，工具层直接返回 `null`）

### 2.3 HR —— 从「跑报表」到「随时追问」

**现在的痛点**：想验证「这次评级有没有松紧不均」，得自己拉数据、算分布、看异常。

**有工具层之后**：

```
HR 问：「销售部这个月 A 档给了几个？比上个季度紧还是松？」

AI 行为：
  1. 调 get_department_stats(period="202611")
     → 部门总人数、已评人数、等级分布（聚合，无个人）
  2. 调 get_metric_values —— 需要时取本期指标口径
  3. 组织语言回答 + 标注 k-匿名状态
```

**多出来的具体收益**：
- 异常分布能被 AI 主动标出来（结合 `CalibrationAgent` 的松紧检测）
- **不用担心 AI 泄密** —— 工具层返回的是聚合数，人数不足 5 时连平均分都没有
- 每次问答都留痕（`ai_tool_call` 表）—— 出问题能查「当时 AI 看了什么数据」

### 2.4 员工（计划助手）—— 从「AI 写空表」到「AI 读懂你的历史」

这是**提升最明显**的一块，因为现在 `employee_ai.py` 全是 `_empty_*` 空壳。

**Step 6 之后**：

```
员工点「AI 助手」→ 说「我想做客户回款优化」

AI 行为：
  1. 调 get_plan_history(months=6)
     → 拿到过去 6 个月他实际做过的计划条目
  2. 调 get_acceptance_standards()
     → 拿到这个岗位/部门的验收标准（任务要写到什么颗粒度才算合格）
  3. 生成建议：结合他历史计划的写法 + 部门验收标准，
     给出「任务名 / 任务内容 / 交付物 / 质量标准 / 起止 / 权重」
```

**多出来的具体收益**：
- 建议**贴着这个人的历史习惯**，不是通用模板
- 交付物和权重**对得上部门的验收标准**，交上去不被打回
- 历史计划里有「重复在做低价值的事」这类信号，AI 能指出来

## 三、对比表：工具层前 vs 后

| 场景 | 现在 | 有工具层 |
|---|---|---|
| 员工查自己指标 | 打开报表页 → 逐个看 | 直接问，AI 调工具取数后答 |
| 主管对比两人 | 导出 → Excel 透视 → 手工找差异 | 直接问，AI 逐指标对齐后说差异 |
| HR 看部门分布 | 跑报表 → 看数字 | 直接问，AI 调聚合工具 + 标注 k-匿名 |
| 员工写月计划 | `items: []` 空壳 | 读历史计划 + 部门验收标准后给建议 |
| AI 数字准不准 | 只能复述请求体里给的 | 工具返回 L2 规则引擎算的值，AI 无法编 |
| AI 查不到数据时 | 不知道，会编一个 | 工具报错 → 明确说「查不到」 |
| 数据被脱敏 | 无（证据正文里的手机号不管） | L2 返回前就掩码 |
| 问答留痕 | 无 | 每次工具调用写 `ai_tool_call` |

## 四、顺带修掉的两个现存问题（这是额外收益）

工具层要走的路上，有两个**现在就在的洞**。做工具层必须修，否则新的 AI 能力会建立在越权之上。

### Bug 1：主管查下属的分数是坏的

`backend/app/main.py:1251`：

```python
dependencies.check_can_view_score(
    current_user,          # ← 传的是 Employee 对象
    request.target_employee_id,
    db
)
```

但 `backend/app/dependencies.py:316` 的签名是 `check_can_view_score(user_id: str, ...)` —— **要的是字符串**。

这意味着 `colleague_result`（主管查下属）这条路径要么报错、要么在别处被 try/except 吞掉。主管想用 AI 查下属，**前提是这条路径先能用**。

### Bug 2：任何人都能查任意部门的聚合数据

`backend/app/main.py:1263` 的 `peer_performance_distribution` 分支：

```python
target_emp = db.get(Employee, request.target_employee_id)
if not target_emp:
    raise exceptions.RecordNotFound(...)
# ← 没有任何权限校验！
summary_data = qa_service.query_department_summary(
    target_emp.department_id, request.task_id, db
)
```

只要知道一个员工 ID，**任何登录用户**都能拿到他所在部门的完整绩效分布（平均分、各等级人数）。

工具层必须修这个 —— 因为 `get_department_stats` 工具就是干这个的。如果网关不拦，等于**给这个洞加了个更好用的入口**。

## 五、为什么必须有工具层，不能靠「把数据都塞进 prompt」

这是最容易被质疑的一点，所以单独说。

### 5.1 塞 prompt 塞不下

一个部门 30 人 × 5 个指标 × 6 个月，光指标数据就是几千行。塞进 prompt：
- 贵 —— 每次提问都付全额 token
- 慢 —— 输入越长推理越慢
- **且没意义** —— 员工问「我自己的」，塞了整个部门的给他

### 5.2 塞 prompt 做不到「多轮追问」

工具层的循环结构是这样的：

```
用户问 → AI 调工具 → 拿到结果 → AI 判断够不够
                              ├─ 不够 → 再调一个工具 → 回到上一步
                              └─ 够了 → 组织答案
```

塞 prompt 是「一次性把所有可能的输入准备好」。而真实场景里，用户问什么、需不需要追问第 3 个数据源，**事先不知道**。

「查一下我这个月哪些指标没达标」—— 需要 `get_metric_values`。
「那客户数具体差在哪？」—— 需要 `get_evidence`。
「部门里其他人也这样吗？」—— 需要 `get_department_stats`。

**用户自己也不知道要问什么的时候，工具层才能跟上。**

### 5.3 塞 prompt 会破坏「模型不可信」这条防线

这是最本质的一点。

如果数据由调用方（前端或后端编排层）预先塞进 prompt，那**模型就有能力在没有数据支撑的情况下编数字** —— 因为它「看到」了字段名和格式，就会顺着编。你只能靠 prompt 说「别编」，但这是**软约束**。

工具层不一样：

- 工具返回的数据是**结构化的、来自 L2 规则引擎的**
- 工具失败时返回的是**明确的错误**，模型没法从错误里编数据
- 最关键：**模型的输出可以被校验** —— `citations` 里列的每个 id，都必须能在工具返回结果里找到

`agent-service/app/grounding.py` 那套「来源锚定」机制（把结论逐条对照封闭来源目录做原文校验）之所以能成立，前提就是**来源是封闭的**。工具层提供的正是这个封闭性 —— 模型能引用的东西，就是工具返回的那些。

## 六、效果的天花板在哪（诚实的边界）

工具层不是万能的，有些事它**做不到**：

| 做不到 | 为什么 |
|---|---|
| 模型不能改分 | 原则①，`scoring.py` 是唯一写入 `Score` 的地方 |
| 模型不能排名 | 工具只返回聚合数，k-匿名保护 |
| 模型不能算分 | 达成率/等级都来自 `score_record()` |
| 模型不能审批 | 没有任何写工具，`ToolRegistry.register()` 拒绝 `read_only=False` |
| 模型不能自己决定查谁 | 身份只从令牌取，工具参数不接受 `employee_id` |
| 小部门看不到平均分 | L2 侧 k-匿名，工具返回 `null` |

**这是设计如此，不是缺陷。** 工具层扩大的���**是「能查什么、能说什么」，不是「能决定什么」。**

---

## 七、一句话总结

> 工具层给 AI 装上了「自己查数据」的能力：
> 员工从「自己翻报表」变成「一句话问出来」，
> 主管从「导出 Excel 自己比对」变成「直接问差在哪」，
> HR 从「跑报表看数字」变成「随时追问还能看留痕」，
> 计划助手从「返回空数组的空壳」变成「读懂你的历史和部门标准再给建议」。
>
> 同时因为所有数据必须经过受控的只读工具，
> AI 只能在**允许的范围内**说话 —— 不会编数、不会越权、不会改分。
