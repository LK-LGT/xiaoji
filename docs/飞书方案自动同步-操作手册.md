# 飞书绩效方案自动同步 —— 操作手册

> 面向 HR 与运维。目标：飞书上的部门绩效方案文档**全自动**进系统，
> 改了就自动生效，不用人再录一遍。

---

## 一、这条链路现在能跑到哪一步

**全自动闭环**（你选的方案）：

```
飞书文档被修改
      ↓  自动发现 / 人工绑定   （来源绑定）
变更检测（obj_edit_time 比对）
      ↓
抓取正文 → 解析成方案 payload
      ↓
新建方案版本 → 自动发布生效
      ↓
到周期 → 自动发起考核任务 → 通知员工
```

**实测结论（2026-11-20，探针脚本 `backend/scripts/probe_feishu_docs.py`）**：

| 环节 | 状态 | 说明 |
|---|---|---|
| 变更检测 | ✅ **可用** | `wiki get_node` 能拿到 `obj_edit_time`，能回答「文档变了没」 |
| 人工绑定 | ✅ **可用** | HR 填「部门 + 飞书链接」即可建立绑定 |
| 自动发现（扫知识空间） | ❌ 缺权限 | 需 `wiki:wiki:readonly` |
| 抓取正文 | ❌ 缺权限 | 需 `docx:document:readonly` 等 |
| 自动建版本 / 发布 | ✅ 代码就绪 | 等正文权限到位即生效 |
| 自动发起考核 | ✅ 代码就绪 | 默认关闭，需显式开配置 |

⇒ **现在就能做**：人工绑定 + 变更检测（知道「该同步了」）。
⇒ **IT 补权限后自动打通**：正文抓取 → 建版本 → 发布 → 发起考核，**无需改代码**。

## 二、要向 IT 申请哪些权限

去 **飞书开放平台 → 开发者后台 → 你的应用 → 权限管理** 申请这 5 个
**只读**权限，然后**发布应用新版本**（⚠️ 不发布不生效 —— 这是最常见的坑）：

| 权限标识 | 用途 | 不申请的后果 |
|---|---|---|
| `docx:document:readonly` | 读云文档正文（docx） | 抓不到正文，只能检测到「变了」 |
| `wiki:wiki:readonly` | 扫描知识空间节点 | 自动发现不可用，只能人工绑定 |
| `drive:drive:readonly` | 读云空间文件 | 拿不到 docx 附件 |
| `drive:export:readonly` | 导出云文档为标准 docx/xlsx | 只能走 blocks 兜底，表格保真度下降 |
| `sheets:spreadsheet:readonly` | 读电子表格 | 表格型方案读不了 |

> 申请话术：
> 「绩效方案需从飞书云文档自动同步到绩效考核系统，应用为自建应用，
> 需只读访问知识库与云文档（docx / wiki / drive / sheets），不涉及写权限与用户个人信息。」

**验证权限是否到位**（不要靠猜）：

```powershell
python backend/scripts/probe_feishu_docs.py M41sw6DwOipVJukEYGIcQlianXb
```

看到 `[2] 正文抓取 → OK` 就是通了。

## 三、配置项

在 `backend/.env` 加这几行（**注意：默认值全部是关闭的**）：

```env
# ── 总开关 ──
FEISHU_SCHEME_SYNC_ENABLED=true

# 同步间隔（秒）。不得小于 60。建议 1800（半小时）。
FEISHU_SCHEME_SYNC_INTERVAL_SECONDS=1800

# ── 自动发现（需要 wiki:wiki:readonly，没权限可先留空）──
FEISHU_SCHEME_SYNC_SPACE_ID=7702734617867635710
FEISHU_SCHEME_SYNC_PERIOD_TYPE=monthly

# ── 自动发布 ──
#   true  = 建版本后立即发布生效（全自动，你要的）
#   false = 只建草稿，等人工在网页端点发布（保守）
FEISHU_SCHEME_SYNC_AUTO_PUBLISH=true

# ── 自动发起考核 ──
#   ⚠️ 默认 false。改 true = 方案一发布，到周期就给全员开考核。
FEISHU_SCHEME_SYNC_AUTO_START_TASK=false

# 自评 / 主管评分截止天数（相对周期结束日）
FEISHU_SCHEME_SYNC_SELF_REVIEW_DAYS=3
FEISHU_SCHEME_SYNC_MANAGER_REVIEW_DAYS=7

# ── 告警接收人 ──
# 留空 = 只入库不外发。同步失败可在接口查到。
FEISHU_SCHEME_SYNC_ALERT_RECEIVER_ID=oc_xxxxxxxxxxxx
FEISHU_SCHEME_SYNC_ALERT_RECEIVER_TYPE=chat_id
```

## 四、绑定方案来源

### 方式 A：人工绑定（**现在就能用**，推荐先跑通）

HR 在系统里填「部门 + 飞书文档链接」：

```
POST /v1/feishu/scheme/sources
{
  "departmentId": "D001",
  "sourceUrl": "https://xxx.feishu.cn/wiki/M41sw6DwOipVJukEYGIcQlianXb",
  "periodType": "monthly"
}
```

- 只支持 **HR / 系统管理员**。
- **人工绑定优先级最高** —— 自动发现永远不会覆盖它。
- 支持 `wiki` / `docx` / `sheets` 三种链接，也能直接给 token。

### 方式 B：自动发现（需要 `wiki:wiki:readonly`）

```
POST /v1/feishu/scheme/sources/discover
{ "spaceId": "7702734617867635710", "dryRun": true }
```

- 先 `dryRun=true` **看看匹配结果**，确认无误再落库。
- 匹配规则：标题里**唯一命中**某个部门名（如《短视频部门绩效方案》）。
  命中多个 ⇒ **拒绝匹配**（不猜 —— 把 A 部门方案套到 B 部门，比匹配不上严重得多）。
- 标题需含关键词之一：`绩效` / `考核` / `方案` / `考评`。

### 方式 C：机器人收文件（不需要任何云文档权限）

HR 在飞书里把方案文件**直接发给机器人**，系统据此落库解析。
适合权限一时批不下来的场景。

## 五、改了方案怎么更新

**不用做任何操作。**

1. HR 在飞书上改文档
2. 下一次同步（默认 30 分钟内）检测到 `obj_edit_time` 变了
3. 自动抓正文 → 解析 → 建新版本 → 发布生效

### 版本策略：「保留旧版本，旧版本不动」

你选的策略。实现在 `next_effective_window()`：

- 新版本从**旧版本结束日的次日**开始
- **旧版本的生效期一个字节都不改** —— 历史考核不受影响
- 已发起的考核用 `ConfigSnapshot` 里的旧快照，评分不受影响

例：旧版本 `2026-11-21 ~ 2026-11-30`，文档改了 ⇒
新版本 `2026-12-01 ~ 2026-12-31`。

### 内容没变就不建版本

用 sha256 指纹比对。只改了标题/格式、实质没变 ⇒ 跳过，不产生版本垃圾。

## 六、⚠️ 两个必须知道的边界

### 1. 「自动发布」意味着没有人真的核对过

系统对 `direct_points`（直接分值）方案有个人工核对闸门
（`document.review_confirmed`）。全自动模式下系统**自动填入**核对说明
（记录来源文档、编辑时间、内容指纹），让校验通过。

⇒ 事后可追溯，但**确实没人逐项看过**。想保留人工闸门：

```env
FEISHU_SCHEME_SYNC_AUTO_PUBLISH=false
```

同步会停在「已建草稿」，等人在网页端确认发布。

### 2. 文档里没有等级规则 ⇒ 只建草稿，不自动发布

如果飞书文档只有「指标 / 分值 / 评分标准」而**没有「等级 / 总分区间」**，
系统**不会自动发布** —— 因为主管填完分数后**无法判定等级**，
这是业务闭环的断点。

系统**不会凭空造等级**（等级区间是绩效标准，猜一个等于凭空造标准）。
它会生成草稿并写明原因，等人工补齐。

⇒ **请确保飞书文档里有等级表**，例如：

| 等级 | 总分区间 | 说明 |
|---|---|---|
| A | 90-100 | 优秀 |
| B | 80-89 | 良好 |
| C | 60-79 | 合格 |
| D | 0-59 | 不合格 |

## 七、运维接口

| 接口 | 用途 |
|---|---|
| `GET /v1/feishu/scheme/sources` | 列出来源绑定 |
| `POST /v1/feishu/scheme/sources` | 人工绑定 |
| `PATCH /v1/feishu/scheme/sources/{id}` | 启用 / 停用 |
| `DELETE /v1/feishu/scheme/sources/{id}` | 解除绑定 |
| `POST /v1/feishu/scheme/sources/discover` | 自动发现 |
| `POST /v1/feishu/scheme/sync` | 立即同步一轮 |
| `GET /v1/feishu/scheme/sync/batches` | 同步历史（排查「为什么没同步」） |
| `GET /v1/feishu/scheme/sync/status` | 调度器运行态 |

**排查「为什么没同步」**的顺序：

1. `GET /sync/status` —— 看 `scheduler.lastResult` / `lastError`
2. `GET /sync/batches` —— 看批次里每个来源的 `result` 与 `error`
3. 看 `feishu_scheme_source.last_error` —— 单个来源的失败原因

---

## 八、多实例部署

调度器用分布式锁（`job_lock_service`，锁名 `feishu_scheme_sync`），
保证同一时刻只有一个实例执行。人工触发的 `POST /sync` **也会拿同一把锁** ——
所以手动和定时不会重复跑。
