# 短视频剪辑工作量统计 —— 实现方案（BP-2）

> 目标：把「剪辑师上传到百度网盘的成片」自动折算成**工作量条数**，
> 与「运营人工填报的完播率/留存率」合并进同一个绩效面板，
> 并提供**异议复核工单**闭环，全程留痕可审计。
>
> **第一性原则（继承框架既有约束）**
> 1. 网盘计数只作**客观证据**，不自动改分、不自动算主观分。
> 2. **判定权在人**：数据源只提供依据，最终评定由主管/HR 人工完成。
> 3. 原始记录**永久留存**，任何更正以**追加**方式留痕，禁止覆盖删除。

## 〇、**实测探针结论（2026-11-21 真实网盘跑通）** ★ 优先级最高

> 探针脚本：`backend/scripts/probe_pan_ownership.py`、`backend/scripts/probe_pan_dirs.py`
> （只读，不改数据；用 BP-1 已有 token 直连真实网盘）

### 探针实测结果

```
① uinfo（当前授权账号）
   uk = 1102224043442        ← 这是「公司共享账号」，不是剪辑师个人账号

② 目录结构（网盘根目录）
   DIR  oper_id=1102224043442 | /成品-小瑶      ← 小瑶
   DIR  oper_id=1102224043442 | /成品-小雨      ← 小雨
   DIR  oper_id=0             | /口播成品
   DIR  oper_id=0             | /鹿13

③ 递归到底层文件（233 个条目）
   oper_id=1102224043442  出现 232 次   ← ★ 全部相同！
   oper_id=0              出现   1 次

④ 目录层级（实测）
   /成品-小瑶/11月/11.19/慵懒毛衣两件套-2.mp4
   /成品-小瑶/10月/10.31/低腰牛仔裤.mp4
   /口播成品/5.28/白衬衫.mp4
```

### 由此得出的**四条硬结论**

| # | 结论 | 依据 | 影响 |
|---|---|---|---|
| **C1** | **`oper_id` 在共享目录下没有区分度** —— 全部返回**公司共享账号**的 uk | ③ 中 232/232 条 `oper_id` 相同，且等于 `uinfo` 的 uk | ⚠️ **不能靠 `oper_id` 拆人**。必须靠**目录路径** |
| **C2** | **但「按人区分」的需求本身已经满足了** —— 只是靠**顶层目录名** | ② `/成品-小瑶` 与 `/成品-小雨` 是**两个独立顶层目录** | ✅ **归属可全自动**：路径前缀 → 人。只需一次性配好映射表 |
| **C3** | **目录层级完全符合 BP-1 已实现的解析逻辑** | ④ `/成品-{人}/{月}月/{日}.{日}/文件名` | ✅ `parse_period_from_path` 直接可用，**业务日期能从目录名准确解析** |
| **C4** | **同一目录下文件混放，文件名里带标记** | ④ `/11.19/` 下有 `11.19 低腰牛仔裤.mp4` 与 `慵懒毛衣两件套-2.mp4` 两种命名风格 | ⚠️ **文件名是唯一载体** —— 标记（`智能体`/`OOTD`/`-2`）只能从文件名认 |

### ⇒ 对方案的最终定论

```
归属：/成品-{人}/...  →  路径前缀匹配映射表  →  employee_id     ✅ 全自动
归日：/11月/11.19/... →  parse_period_from_path  →  business_date  ✅ 全自动
加权：文件名含【智能体】/OOTD/-2 → match_markers → count_weight    ✅ 全自动
过滤：ext 白名单 + 关键词 + 目录段                                ✅ 全自动
```

⚠️ **不再需要**「每人各自 OAuth 授权学 uk」这条路径（`pan_account_identity` 表降级为可选）——
实测证明共享目录下 `oper_id` 拿不到上传者，授权再多也学不到。**顺带消掉了 R18 的 10 人授权上限问题。**

⚠️ **但要提醒**：C1 同时意味着 —— **公司账号能看到所有人的文件，剪辑师之间也能看到对方的**。
⇒ 权限上「剪辑师只能看自己的统计」是我们**系统层面**的约束（按 `employee_id` 过滤），
**不是网盘层面的**。面板上不要直接暴露网盘原始链接给不该看的人。

## 〇·一·二、**数据质量实测（526 个真实文件）** ★ 决定标记与过滤规则

> 脚本：`backend/scripts/probe_pan_data_quality.py`、`probe_pan_markers.py`、`probe_pan_name_collision.py`
> 样本：`/成品-小瑶` + `/成品-小雨` 全量 **526 个文件**

### Q1：靠「文件名」能不能区分剪辑师？

| 指标 | 实测值 | 结论 |
|---|---|---|
| 不同文件名数 | 510 | — |
| **跨人撞车的文件名** | **0 个** | ✅ **文件名不跨人** |
| 去掉日期/序号后的基础名跨人撞车 | **1 个**（`智能体`） | ⚠️ 仅此一个 |
| 同名文件（同一目录内） | 13 个名字共 29 个文件（5.5%） | ⚠️ 同名但 md5/大小**各不相同** ⇒ 是**不同内容**，不是重复上传 |

⇒ **你的判断是对的**：两个人的文件名基本不撞，**文件名确实带各自的信息**。

⚠️ **但它不能替代「谁」这个信息**：文件名叫 `智能体.mp4`，**光看名字不知道是小瑶的还是小雨的**
（实测 `智能体` 是唯一跨人撞车的基础名）。
⇒ **归属仍然靠目录**（`/成品-小瑶/` vs `/成品-小雨/`）。文件名负责「**是什么**」，目录负责「**是谁**」。

### Q2：两个人的命名风格**完全不同** ⇒ 标记规则必须分人

```
小瑶（斜杠分隔 / 名称在前）：
   11.13 智能体.mp4        11.13 智能体-2.mp4      11.16 智能体.mp4
   11.17 OOTD.mp4          10.29 OOTD.mp4          11.2 OOTD.mp4
   低腰牛仔裤 10.22.mp4    卡其牛仔裤 10.23.mp4      紫色撞色假两件 2.0.mp4

小雨（横杠分隔 / 纯日期型）：
   11.14-智能体.mp4        11.14-智能体2.mp4        11.6--智能体.mp4
   10.26-1.mp4   10.26-3.mp4   10.29-1.mp4   10.29-4.mp4
   10月17日 (1).mp4   10月17日 (2).mp4   10月17日 (3).mp4
   白色斜肩9.16(10.19).mp4
```

⚠️ **关键差异**：
- 小瑶用 `-`+空格（`11.13 智能体`），小雨用 `-`+无空格（`11.14-智能体`）
- 小雨用**全角括号** `（1）` `（6）`，小瑶用**半角** `(1)`
- 小雨有 `10月17日` 这种**中文日期**格式
- 小雨的 `-1` `-3` `-4` `-6` **序号跨度很大**（同一天 7 个版本）

⇒ **一条全局正则匹配两个人的标记会出错**。标记规则必须**按目录（按人）可配**。

### Q3：三个必须处理的实测问题

| # | 问题 | 实测证据 | 处理方案 |
|---|---|---|---|
| **D-1** | **mp4 与 png 是同一条内容的两种格式**（封面图） | `/成品-小雨/10月/10.19/`：`卡其色裤子10.4(10.19).mp4` + `卡其色裤子10.4(10.19).png`（md5 不同但同名） | ⚠️ **只数 mp4**，png/jpg 全部排除 —— 否则**工作量翻倍** |
| **D-2** | **文件名前缀日期与目录日期不一致** | 190 个带日期前缀的文件里 **6 个冲突**：<br>`/10月/10.30/10.28 V领假两件.mp4`<br>`/11月/11.14/11.17-智能体.mp4`<br>`/11月/11.16/11.6--智能体.mp4` | ⚠️ **以目录日期为准**（目录是归档行为，文件名是随手写）。冲突记 `anomaly_flags=["name_date_conflict"]` |
| **D-3** | **`-N` 后缀不是「双条」标记** | 27 组「`X-N` 与 `X`」配对，**md5 全部不同**（大小也差 20~90MB）⇒ 是**不同版本/不同内容**，不是同一文件重复上传 | ⚠️ **不把 `-2` 当双条标记**。`-N` 只是「当天第 N 版」，各算 1 条 |

⚠️ **D-3 直接推翻了「`-2` = 2 条」的假设** —— 这正是必须实测的原因。
`11.13 智能体.mp4`(239MB) 与 `11.13 智能体-2.mp4`(123MB) 是**两个不同的视频**，
各算 1 条，不是「1 条 + 双条」。

### ⇒ 最终计数口径（实测支撑）

```
计入：仅 .mp4（排除 .png/.jpg 封面）
归属：目录路径前缀（/成品-小瑶/ → 小瑶）
归日：目录日期（11月/11.19/），文件名日期冲突时以目录为准
标记：按人可配的规则（小瑶『11.13 智能体』/ 小雨『11.14-智能体』/ OOTD）
去重：md5 相同 = 同一文件（实测无跨目录重复，但仍保留该保险）
排除：草稿/工程目录、扩展名白名单外
```

## 二、百度网盘开放 API 能力边界（**先看这个，它决定方案形状**）

### 2.1 能做到的 ✅

| 需求 | 用哪个接口 | 说明 |
|---|---|---|
| 列目录 / 递归取文件 | `GET /rest/2.0/xpan/file?method=list` | 实测（2026-11-20）**可读任意授权目录**，非递归 → 需自建下钻（BP-1 已实现） |
| 文件名 / 路径 | `list[].server_filename` / `list[].path` | ✅ |
| 上传时间 / 修改时间 | `list[].server_ctime` / `server_mtime` / `local_ctime` | ✅（但 ≠ 制作日期，见 R2） |
| 文件大小 / 类型 | `list[].size` / `list[].category`（1=视频） | ✅ |
| 内容哈希（去重用） | `list[].md5` / `filemetas[].md5` | ✅ 云端哈希，非真实 MD5，用于**同内容重复**识别足够 |
| 唯一文件 ID | `list[].fs_id` | ✅ 永不变化 → 主键幂等锚点 |
| **上传者 ID** | `list[].oper_id`（操作者）/ `owner_id`（所有者）/ `user_id`（所属用户） | ⚠️ **字段存在，但共享目录下无区分度** —— 实测 232/232 条都是公司账号 uk（见 §〇 C1）。**不可用于拆人** |
| **共享目录上传者信息** | `filemetas` 顶层 `names` 字段 | ⚠️ 查询共享目录时返回「共享目录文件上传者信息」；失败码 `42212`/`42213`。⚠️ 需实测确认其值是否等于上传者本人（**不作为主路径依赖**） |
| **当前授权账号信息** | `GET /rest/2.0/xpan/nas?method=uinfo` → `uk` / `netdisk_name` | ✅ 用于识别「这个 token 是谁的账号」，是排查归属问题的第一手依据 |
| 视频时长 / 媒体信息 | `filemetas` 的 `needmedia=1` → `duration` | ✅（`meta` 受 `/apps` 限制，`multimedia?method=filemetas` 不受） |
| 批量元信息（≤100 个 fs_id） | `GET /multimedia?method=filemetas&fsids=[...]` | ✅ 一次 100 个，用于补 md5/duration |
| 单文件元信息 | `POST /file?method=filemetas&target=[路径数组]` | ✅ 路径批量，同样不限于 `/apps` |
| 下载直链 | `filemetas` 的 `dlink=1` | ⚠️ **仅 8 小时有效**，不适合长期审计证据 |
| 创建分享链接 | `POST /apaas/1.0/share/set` | ⚠️ **付费接口**，需单独开通；`period` 单位为天 |

### 2.2 做不到的 ❌（**必须绕开，需求要改口径**）

| 需求原文 | 结论 | 原因 | 替代方案 |
|---|---|---|---|
| **「文件备注里带指定标记」** | ❌ **个人网盘 API 拿不到** | `file?method=list` 与 `filemetas` 的响应字段里**都没有「文件备注/描述」**；`filemanager` 只支持复制/移动/重命名/删除，**无设置备注的参数**。百度「备注」只存在于**分享链接**（`share/set` 的 `remark`），不是文件属性 | 标记**从文件名 + 目录名**识别。⚠️ **注意**：**百度企业版网盘**（与个人网盘是不同产品）的 API 文档提到支持「文件描述/自定义属性」—— 若公司用的是企业版，「备注」**可能可读**，需向百度企业版销售/客服确认。**未确认前按文件名方案实现**，不阻塞 |
| **「谁上传的」按上传者拆人** | ⚠️ **实测：共享目录下不可行** | `oper_id` **确实返回**，但实测 232/232 条**全部等于公司共享账号的 uk**（见 §〇 C1）—— 共享目录不暴露真实上传者 | **靠顶层目录路径**（实测已有 `/成品-小瑶`、`/成品-小雨` 等按人隔离目录）→ 路径前缀映射表 → **全自动**（见 §2.3） |
| **完播率 / 留存率** | ❌ 网盘里没有 | 网盘无任何播放数据 | 运营人工填报（需求已如此设计） |
| **「原始文件数」含草稿/工程文件** | ❌ 网盘不区分「成片/草稿」 | 网盘只知扩展名与路径，无业务语义 | 用**后缀白名单 + 排除关键词 + 目录约定**三重过滤（需求已如此设计） |
| **按上传时间精确归日** | ⚠️ **不准** | 实测：`/成品-小瑶/11月/11.19/` 里的文件 `server_ctime` 是 **2026-11-20** | 业务日期**从目录名解析**（BP-1 `parse_period_from_path` 已实现） |
| **长期有效的文件证据链接** | ⚠️ **受限** | `dlink` 8 小时过期；`share/set` 是付费接口且 `period` 按天计 | 存**自有证据链接**（`/v1/baidu/workload/files/{fs_id}/link` 代理跳转）+ fs_id + path + md5 三元组；付费分享服务开通后再补 `share_url` |

### 2.3 关键结论

> **百度网盘在本方案里扮演的纯粹角色是「一个带路径层级的文件仓库 + 元数据来源」。**
> **文件清单、文件名、路径、上传时间、md5 —— 全部可以自动拉取**（BP-1 已跑通真实数据）。
> 所有业务语义（哪个是成片、标记是什么、一条算几条）**由「目录结构 + 文件名约定」承载**，由我们的系统解释。
> ⇒ **运营侧必须配合定目录规范与命名规范**，否则标记识别与归日会失准（风险 R3）。

⚠️ **「按上传者拆人」的最终结论（2026-11-21 实测，见 §〇）**

> **实测：共享目录下 `oper_id` 全部返回公司共享账号的 uk（232/232 条相同）**
> ⇒ **靠 `oper_id` 拆人不可行**，必须靠**目录路径**。
>
> **但这不影响可行性** —— 实测网盘根下已有**按人隔离的独立顶层目录**：
> ```
> /成品-小瑶/11月/11.19/xxx.mp4     ← 小瑶
> /成品-小雨/11月/11.19/xxx.mp4     ← 小雨
> ```
> ⇒ **归属 = 路径前缀匹配映射表 → employee_id**，**全自动**，映射表一次性配置即可。
> ⇒ 需求第 1 条「公司网盘上传目录按人隔离」—— **该设计天然适配，无需改动网盘用法**。

## 三、数据结构

### 3.1 实体关系

```
Employee（飞书组织架构）
   │ 1:N
   ├─► PanAccountIdentity   员工 ↔ 百度网盘 uk（★ 可自动学习）
   │
   ├─► PanAccountBinding   员工 ↔ 网盘目录 / oper_id（交叉校验 + 兜底）
   │
   ├─► PanWorkloadFile     单文件证据（★ 永久留存，审计根）
   │      │ 1:N（按 biz_date 归集）
   │      ▼
   ├─► PanWorkloadDaily    按人按日汇总（物化聚合）
   │      │ 1:N
   │      ▼
   │   PanWorkloadReview   复核工单
   │      │ 1:N
   │      ▼
   │   PanWorkloadReviewEvent  留痕事件流（hash 链）
   │
   └─► PanManualMetric     运营人工填报（完播/留存）
           │
           └─► PanImportBatch   人工填报导入批次

#### 归属判定算法（**路径归属为主 —— 实测结论**）

```python
def resolve_owner(
    file_path: str,
    bindings: list[PanAccountBinding],
) -> tuple[str | None, str, str | None]:
    """判定文件归属 → (employee_id, bind_type, conflict_note)。

    ⚠️ **只用路径**（2026-11-21 实测结论）
    实测：公司共享网盘下 ``oper_id`` **232/232 条全部等于公司账号 uk**，
    共享目录**不暴露真实上传者** ⇒ ``oper_id`` 无区分度，不能用于拆人。

    ⇒ 归属 = **顶层目录路径前缀**匹配：
        /成品-小瑶/...  →  小瑶
        /成品-小雨/...  →  小雨

    ``bind_type`` 取值：
        - ``path``      路径命中（**主路径**）
        - ``unbound``  未命中任何绑定 → **不丢弃**，标待人工确认（R3）
        - ``ambiguous`` 命中多条绑定 → 配置有歧义，需 HR 修正（R20）

    ⚠️ **命中多条时不自动取第一条** —— 那会造成「同一文件算给两个人」。
    宁可标 ambiguous 让 HR 修，也不要静默算错。
    """
    hits = [
        b for b in bindings
        if b.active and file_path.startswith(b.folder_path)
    ]
    if len(hits) == 1:
        return hits[0].employee_id, "path", None
    if len(hits) > 1:
        # ⚠️ 绑定表配置有歧义（如 /成品 与 /成品-小瑶 同时存在）
        return None, "ambiguous", f"命中 {len(hits)} 条绑定"
    return None, "unbound", None
```

⚠️ **前缀匹配的边界坑**：`/成品-小瑶` 与 `/成品-小雨` 是**兄弟目录**，
但若有人配了 `/成品` 这条绑定，它会**同时命中两者** ⇒ 触发 `ambiguous`。
⇒ 绑定表入库时**必须校验「同一前缀下互不为前缀」**（加一条校验规则）。

    #: 不排除会导致工作量翻倍，见 §〇·一·二 D-1）
    allowed_extensions: Mapped[str] = mapped_column(
        String(255), default="mp4,mov,m4v,avi,mkv,flv,wmv", nullable=False)
    #: 排除关键词（草稿/工程/返工/截图）
    exclude_keywords: Mapped[str] = mapped_column(
        String(512), default="草稿,工程,返工,废片,废弃,作废,rework,_v2,_v3,副本,prj,aep", nullable=False)
    #: 标记字典（JSON）—— ⚠️ **按人可配**（实测两人命名风格完全不同，见 §〇·一·二 Q2）
    marker_rules: Mapped[dict] = mapped_column(JSON, default=dict, nullable=False)
    #: 突增阈值（相对近 N 日均值的倍数）
    surge_multiplier: Mapped[float] = mapped_column(Float, default=2.0, nullable=False)
    #: 突减阈值（相对近 N 日均值的倍数）
    drop_multiplier: Mapped[float] = mapped_column(Float, default=0.4, nullable=False)
    #: 基线窗口天数
    baseline_days: Mapped[int] = mapped_column(Integer, default=20, nullable=False)
    updated_by: Mapped[str | None] = mapped_column(String(64))
    updated_at: Mapped[datetime] = mapped_column(DateTime, default=_now, nullable=False)
```

### 4.2 标记识别规则（**核心口径**）

```python
def match_markers(file_name: str, rules: dict) -> tuple[int, list[str]]:
    """识别文件标记 → (折算条数, 命中规则名列表)。

    ⚠️ 命中多条时的口径：**取最高权重，不叠加**
    例：文件名同时含【智能体】和【双条】 → 2 条，不是 3 条。
    ⇒ 避免一个文件被多个标记重复加权。

    ⚠️ **匹配用「原文包含」，不做去括号/去空格**
    因为剪辑师命名不规范是常态，宽松匹配收益远大于误伤。

    ⚠️ **不做大小写归一化到 patterns 上**，而是匹配时统一 lower() 两边
    ⇒ ``OOTD`` / ``ootd`` / ``Ootd`` 都算命中。

    ⚠️⚠️ **绝不能把 ``-2`` / ``-1`` / ``(1)`` 当作「双条」标记**（实测结论，见 §〇·一·二 D-3）
    27 组「``X-N`` 与 ``X``」配对的 md5 **全部不同**、大小差 20~90MB
    ⇒ ``-N`` 是「当天第 N 版」，是**不同内容**，各算 1 条。
    ⇒ 把它当双条会**直接导致工作量翻倍**，且错得离谱。
    """
    weight, hits = 1, []
    haystack = file_name.lower()
    for name, rule in rules.items():
        if not rule.get("enabled", True):
            continue
        patterns = rule.get("patterns") or []
        if any(p and p.lower() in haystack for p in patterns):
            hits.append(name)
            weight = max(weight, int(rule.get("weight", 1)))
    return weight, hits
```

### 4.2·一、**业务口径已确认（2026-11-21）**

> ✅ **「智能体」和「OOTD」各算 2 条。**
> ⇒ 普通成片 1 条，含「智能体」或「OOTD」的文件 2 条。
>
> ⚠️ **配套口径（由实测推导，与上面一致）**：
> - 一个文件最多算 **2 条**（多标记取最高，不叠加）
> - `智能体-2.mp4` = **2 条**（不是 4 条）—— `-2` 是版本号不是数量
> - `智能体2.mp4` = **2 条**（同上）
> - mp4 + png 封面 = **1 条**（png 排除）

默认标记字典（`marker_rules`）：

```json
{
  "智能体": {"weight": 2, "patterns": ["智能体"], "enabled": true},
  "OOTD":   {"weight": 2, "patterns": ["ootd"],   "enabled": true}
}
```

⚠️ **匹配大小写不敏感**（`OOTD` / `ootd` / `Ootd` 都算 —— 实测小雨全部用小写 `ootd`）。

⚠️ **「智能体」与「智能体2」不区分** —— 实测两种写法都存在，
且 `智能体2` 的 md5 与 `智能体` 不同（是不同版本），
但**按业务口径都算 2 条**（「智能体2」= 智能体的第 2 版，不是「2 条智能体」）。

### 4.2·二、**按人可配的标记规则**（实测必须，见 §〇·一·二 Q2）

⚠️ **实测发现两个人的命名风格完全不同**，一条全局规则会漏配或误配：

| 剪辑师 | 实际文件名 | 匹配情况 |
|---|---|---|
| 小瑶 | `11.13 智能体.mp4` / `11.17 OOTD.mp4` | ✅ 上述默认规则命中 |

| 小雨 | `10月17日 (1).mp4` / `10月22日（6）.mp4` / `10.26-3.mp4` | ⚠️ **不含标记** ⇒ 权重 1 |

⇒ **`marker_rules` 改为「全局默认 + 按人覆盖」两级**：

```json

    "智能体": {"weight": 2, "patterns": ["智能体"], "enabled": true},
    "OOTD":   {"weight": 2, "patterns": ["ootd"],   "enabled": true}

⚠️ **「智能体」到底算几条（2 条还是 1 条）？—— 业务待确认**

## 五、状态流转

### 5.1 复核工单状态机

```
        剪辑师发起                     主管审核
  (无异议/复核驳回后再次发起)          ┌──────────────┐
                │                     │              │
                ▼                     ▼              ▼
   ┌──────────────────┐        ┌──────────┐   ┌──────────────┐
   │ pending（待复核） │───────►│ approved │   │ rejected     │
   └──────────────────┘  通过   └──────────┘   └──────────────┘
          │                                        （驳回）        │
          │ 撤回（剪辑师）                    │                    │
          ▼                                  ▼                    ▼
   ┌──────────────┐                  ┌─────────────────────────────────────┐
   │ withdrawn    │                  │ PanWorkloadDaily.status             │
   │ （已撤回）   │                  │  pending → review_approved          │
   └──────────────┘                  │  pending → review_rejected          │
                                     └─────────────────────────────────────┘
```

**规则**

| 当前状态 | 动作 | 目标状态 | 谁能做 |
|---|---|---|---|
| `no_objection` / `review_rejected` | 发起复核 | `pending` | **仅该员工本人** |
| `pending` | 审核通过 | `approved` | 直属主管 / 部门负责人 / HR |
| `pending` | 审核驳回（须填备注） | `rejected` | 同上 |
| `pending` | 撤回 | `withdrawn` | 仅申请人本人 |
| `approved` / `rejected` | — | **终态，不可再改** | — |

⚠️ **一单一锁**：`uq_pan_review_daily_emp` 保证同一 (人, 日) 只有一个工单。
发起新工单前，旧工单必须是终态。

⚠️ **审核不自动改分**：
- 审核通过 → `PanWorkloadDaily.status = review_approved`；
  主管**可选**在 `adjusted_weight` 填人工调整值（调整必须写备注，进留痕）。
- 审核驳回 → `status = review_rejected`，**条数维持自动值**，
  但保留「已提出异议」的事实标记，主管在评分时能看到。

⚠️ **谁能看到待复核工单**：直属主管、部门负责人、HR。
普通员工**只能看自己的工单**，且**看不到别人的**。

### 5.2 日汇总状态映射

| `PanWorkloadDaily.status` | 含义 | 触发 |
|---|---|---|
| `no_objection` | 无异议 | 自动采集后默认 |
| `pending_review` | 待复核 | 工单创建 |
| `review_approved` | 复核通过 | 主管审核通过 |
| `review_rejected` | 复核驳回 | 主管驳回 |

工单撤回 → 日汇总回到 `no_objection`（但留痕里保留「曾发起过」）。

### 逐文件裁定的增量算法

```
final = system_count + Σ(每个成立项的增量)

  missing（系统漏了）    → += 该文件应算的条数
  overcounted（多算了）  → -= (原值 - 应算值)
  weight（权重不对）     → += (正确值 - 原值)
  rejected / need_more   → 不动
```

### 飞书端的两条通路

```
通路 A：发消息触发（员工主动）
──────────────────────────────────────────────────────────
  员工发「完播率 35%」或「填报表数据」
      ↓ 意图识别 INTENT_MANUAL_METRIC

──────────────────────────────────────────────────────────
  员工把数据截图发进聊天

### 关键设计取舍

| 取舍 | 决定 | 理由 |
|---|---|---|
| **截图要不要自动识别数值** | ❌ **不识别** | OCR 认错数字 = **错误绩效数据**。截图只作**证据**，数值必须员工自己填 |
| **指标和数值认不出怎么办** | ❌ **不猜，回错误卡** | 与框架「AI 只提供建议、判定权在人」口径一致 |
| **月度高亮怎么写** | ✅ **两条独立 MetricValue** | 量纲不同（条 vs 比率）合成综合分就**没法分别设目标**、**没法拆开看贡献** |
| **网盘条数取哪个值** | ✅ **优先 ``adjusted_count``** | 有人工裁定时以裁定为准；但 ``total_count`` **永远保留** ⇒ 可对照、可审计 |
| **没指标时截图怎么办** | ✅ **存为待关联** | 员工自然顺序是「先截图再补数值」⇒ 截图**不能被丢弃** |

### ⚠️⚠️ 顺带抓出的**静默少计**缺陷

绑定后跑真实采集，发现**面板条数与机器判定条数对不上**：

```
机器判定 1347 条  vs  日汇总 1345 条   ← 差 2
```

**根因**：`/口播成品/灯笼裤.mp4`、`/口播成品/6月18日.mp4` 直接挂在**根目录**，
**目录名里没有日期** ⇒ `business_date` 为空
⇒ `aggregate_daily` 里 `if not r.business_date: continue` ⇒ **整行被跳过**
⇒ 文件**计入判定成立**却**永远进不了日汇总** ⇒ **无声少计**。

⚠️ **为什么难发现**：机器判定值与聚合值**对不上却查不出原因**，
面板上只显示聚合值 ⇒ 差额「看起来像是重复采集导致的」⇒ 会被误判成别的问题。

**修法**（`resolve_file_business_date`，降级链**逐级留痕**）：

| 级别 | 来源 | 异常标记 |
|---|---|---|
| 1 | **目录日期**（`/10.24/xxx.mp4`） | —— |
| 2 | **文件名日期**（`6月18日.mp4`） | `date_from_name` |
| 3 | **上传时间** ``ctime`` | `date_from_ctime` |
| 4 | **显式占位** `0001-01-01` | `date_unknown` |

⇒ **契约**：**机器判定条数 == 日汇总条数**，永远相等。
⇒ 第 4 级用「不存在的日期」占位 ⇒ 既不与真实日期混淆，
又**在日汇总里占一行** ⇒ 主管看得见「这天日期定不出来」，能人工复核。

**实测结果（修后）**：

```
佟瑶(小瑶):   机器 207 / 汇总 207 / 差 0 ✅
李婵雨(小雨): 机器 196 / 汇总 196 / 差 0 ✅
巫宜珊(口播): 机器 1347 / 汇总 1347 / 差 0 ✅

## 九·十二、**各部门功能板块隔离（2026-11-21 已完成）** ★ 用户投诉项

### ⚠️ 用户原话

> 「还有为什么别的部门为什么会有剪辑板块？
> 这个没有做各部门功能板块隔离，我要的是对应的部门有对应的功能，不是这样的」

（配图：仓储部 / 客服部 / 财务部的侧边栏里都出现了「剪辑工作量」）

### 根因：把「权限」误当成了「板块」

| 维度 | 回答的问题 | 载体 |
|---|---|---|
| **权限**（角色维度） | 「这个人**能不能干**这件事」 | `RolePermission` / 权限串 `pan:workload:view` |
| **板块**（组织维度） | 「这个**部门有没有**这个业务」 | ★ 新增 `department_module` 表 |

之前 `pan:workload:view` 授予了基础 `employee` 角色，而前端菜单过滤**只有权限串**这一个维度
⇒ **全公司每个部门**的侧边栏都出现「剪辑工作量」。

⇒ **两个维度必须同时成立**，否则必然出现「别的部门看到不属于自己的板块」。

### 设计原则

1. **默认关闭（Fail-Closed / 白名单）**
   `department_module` 里**没有 active 行 = 板块不开通**。
   与框架 `DataSourcePolicy`「默认不信任」同一套哲学 ——
   漏配导致「功能没出现」（**可见、可修**），而不是「功能到处乱出现」（**不可见、不可修**）。

2. **向上继承，不向下**
   「运营中心」开通 ⇒ 其子部门「短视频」自动获得；
   「短视频」开通 ⇒ **不会**让父部门「运营中心」的老总看到剪辑面板。
   ⇒ 与 `access_control._department_descendants`（**权限范围**，向下）方向**故意相反**。

3. **主管不自动继承下属的板块**
   主管能否用板块，看**他自己所在部门**是否开通。
   （下属数据可见性是 `pan_workload` 自己的范围问题，与板块归属是两件事。）

4. **HR / 系统管理员豁免**
   他们要配置板块、维护绑定、核对全局数据 ⇒ 不受隔离约束。
   ⚠️ 否则管理员被挡住 ⇒ 而管理员正是唯一能开通板块的人 ⇒ **死锁**。

### 落地实现

| 层 | 文件 | 做法 |
|---|---|---|
| 数据 | `backend/app/domain/pan_workload_models.py` | 新增 `DepartmentModule` 表（`uq_department_module_dept_code` 唯一约束） |
| 数据 | `backend/migrations/versions/0040_department_module_isolation.py` | 建表 + 种子（`短视频` × `pan_workload`） |
| 判定 | `backend/app/services/department_modules.py` | `enabled_modules_for_employee()` —— 唯一的判定口径 |
| 后端 | `backend/app/routes/pan_workload.py` | 路由级依赖 `_require_pan_module` ⇒ 未开通部门 **403** |
| 后端 | `backend/app/routes/auth.py` / `feishu_auth.py` | 登录 / `/me` / 飞书换票 响应里注入 `modules` 数组 |
| 后端 | `backend/app/routes/department_modules.py` | ★ HR 维护入口（`GET/POST /v1/department-modules`） |

### ⚠️ 权限位：**独立于 `system:org:view`**

板块配置页用的是**专属权限串** `system:department-module:manage`：

| 角色 | 有此权限位 |
|---|---|
| `hr` | ✅ |
| `admin` | ✅ |
| `manager` / `department_leader` / `employee` | ❌ |

**为什么不用 `system:org:view`** —— 「能看部门树」≠「能改板块开通范围」。
板块开关**直接决定**谁能访问剪辑工作量这类业务接口 ⇒ 必须是 HR 专属动作，
不能跟一个「只读」权限位混在一起。

**前后端必须同一口径** —— 前端菜单用这个串过滤，后端守卫也用**同一个串**判定，
否则会出现「菜单看不见但接口能调」或「菜单能看见但接口 403」。
⇒ 后端判定：`has_department_module_manage()`（按角色解析）**或** `is_admin_or_hr()`（兜底，防死锁）。
⇒ 契约由测试 `test_前端菜单项权限串与后端一致` 固化（直接读前端源文件断言）。

**实测**：全库只有 3 人拥有该权限位 —— 李夏冉 / 桂依蕊 / 林雅静（HR + 管理员）。

### 防御纵深：三层都拦

```
① 后端路由守卫  → HTTP 403「当前部门未开通「剪辑工作量」模块」
② 前端路由守卫  → 跳回工作台 + 提示「当前部门未开通该功能板块」
③ 前端菜单过滤  → 侧边栏根本不出现入口
```

⚠️ **只做 ③ 是不够的** —— 用户仍可直接敲 URL 访问
⇒ **必须同时有 ①**。

### ⚠️ 三个容易踩的坑

1. **管理员判定不能按主键查**
   `SystemAdmin` 的主键是 `id`，管理员身份挂在 `employee_id` 字段上
   ⇒ 用 `db.get(SystemAdmin, employee.id)` **永远查不到**
   ⇒ 管理员被当成普通员工 ⇒ 管理员也被隔离挡住 ⇒ 死锁。

2. **管理端点不能在板块守卫之下**
   否则「开通板块」的入口自己被挡住 ⇒ 没人能开通 ⇒ 死锁。
   ⇒ `department_modules` 路由**自己**校验「必须是 HR / 管理员」。

3. **向上 / 向下继承方向不能搞反**
   用「后代」的话 ⇒ 运营中心的老总也会看到剪辑面板
   ⇒ 变成「上面的部门莫名看到下面子部门的业务」⇒ 同样不对。

## 九·十三、**飞书端「表格填报」（2026-11-21 已完成）** ★ 用户明确要求

### ⚠️ 用户原话

> 那剪辑人员如何在飞书端填表呢，我想要的就是该部门是以表格的形式填写

⇒ 需求澄清：**不是**卡片里画个表格，**而是**该部门成员在飞书里**以表格形式**填报。

### 关键结论：飞书卡片做不到表格内输入（实测确认）

| 方案 | 可行性 | 结论 |
|---|---|---|
| 卡片 JSON 2.0 的 `table` 元素内放 `input` | ❌ | `table` 元素**纯展示**，不支持 form 组件 |
| 卡片 `form` 容器里放 `table` | ❌ | `form` 内不能嵌套 `table` 组件 |
| **飞书电子表格（Spreadsheets）** | ✅ | 原生表格 UI，员工直接填写 |
| **飞书多维表格（Bitable）** | ✅ | 原生表格 UI + 字段类型约束 |

⇒ **最终定论**：剪辑人员在**飞书原生表格**里填 → 后端**只读**拉取 → 解析 → 落库。

### 架构

```
剪辑人员（飞书）
   │  在「飞书电子表格 / 多维表格」原生 UI 里逐行填写
   │  日期 | 成片数 | 完播率 | 留存率 | 备注
   ▼
飞书开放平台（应用只读授权）
   │  sheets:spreadsheet:readonly（✅ 已开通）
   │  bitable:app:readonly（❌ 待 IT 开通）
   ▼
后端定时 / 手动同步（feishu_metric_sync.sync_one）
   │  列名别名归一化 → 解析 → 内容哈希幂等
   ▼
PanManualMetric（source='feishu_table'）
```

### 数据结构

`PanFeishuMetricSource`（`backend/app/domain/pan_workload_models.py`）：

| 字段 | 说明 |
|---|---|
| `employee_id` | **唯一约束**（`uq_pan_feishu_metric_source_employee`）—— 一人一张表 |
| `table_kind` | `sheet`（电子表格） / `bitable`（多维表格） |
| `obj_token` | 表格 token（`shtcnXXX` / `bascnXXX`） |
| `table_id` / `sheet_id` | Bitable 数据表 ID / Spreadsheet 工作表 ID |
| `last_content_hash` | 内容哈希 —— **幂等键**，内容没变不重复落库 |
| `last_error` | 上次同步失败原因（权限缺失 / 文件未共享等） |

### REST API（`backend/app/routes/pan_workload_feishu_table.py`）

挂载点：`/v1/baidu/workload/feishu-tables`，**全部在 `require_module(PAN_WORKLOAD_MODULE)` 守卫之下**。

| 方法 | 路径 | 说明 | 谁能调 |
|---|---|---|---|
| GET | `/sources` | 查绑定列表 + 上次同步状态 | 员工**只看自己的** / HR 看全部 |
| POST | `/sources` | 绑定表格（**绑定即验证表头**） | 员工**只能绑自己** / HR 可代绑任何人 |
| DELETE | `/sources/{id}` | 解绑（停用，保留痕迹） | 员工**只能解绑自己的** / HR 可解绑任何 |
| POST | `/sources/{id}/sync` | 同步**指定**绑定 | 员工可同步**自己的** |
| POST | `/sync` | 批量同步 | 仅 HR / 管理员 |
| GET | `/template` | 填报模板说明（表头 + 别名 + 示例） | 板块内员工 |

> ⚠️ **员工自助绑定**是这条链路能跑通的关键 ——
> 否则「剪辑在飞书填表」还得先找 HR 代操作，不成立。
> ⇒ 员工绑自己的表时，请求体里的 `employee_id` **被强制改写为本人**。

### 定时自动同步（`backend/app/services/feishu_metric_scheduler.py`）

| 项 | 值 |
|---|---|
| 间隔 | 默认 **1 小时**（`feishu_metric_sync_interval_seconds`），**下限 10 分钟**（飞书开放平台频控） |
| 启动 | 服务启动即执行一次（避免空窗） |
| 分布式锁 | `feishu_metric_table_sync`（与网盘采集 `pan_workload_sync` **互不阻塞**） |
| 没绑定任何表 | **静默跳过**（`skipped_no_bindings`）—— 预期状态，不刷告警 |
| 失败 | 写进绑定行的 `last_error` + 调度器状态 `lastError` —— **绝不静默失败** |

⇒ **员工填完表不用做任何操作**，数据自动进系统；也可以在页面上点「立即同步」马上看结果。

### 列名别名（后端自动归一化，员工的表头可以自己写）

| 字段 | 接受的别名 |
|---|---|
| 日期 | 日期 / 制作日期 / 发布日期 / 成片日期 / date |

| 留存率 | 留存率 / 留存 / 保留率 / retention |

**数值解析**：
- 完播/留存率支持 `35%` / `0.35` / 裸整数 `35` → 统一归一化到 `0~1`。
- 日期支持 `2026-11-01` / `2026/11/1` / `11月1日` / Excel 序列号。

### 幂等设计

同步时算整表**内容哈希**（列名+行内容归一化后 SHA-256）→ 与 `last_content_hash` 相同则**跳过**，不重复落库。
即使哈希变化，也按 `(employee_id, work_date, metric_type)` 维度 upsert —— **重复同步不会产生重复数据**。

### ★ 九·十五、**部门 × 岗位 考核口径**（2026-11-23）

#### ⚠️ 用户原话（第二次投诉）

> 「**为什么你每次实现代码的时候都这样，不看清楚哪个部门有哪个对应的员工就乱实现呢，

#### ⚠️ **根因**

之前只做了一半的隔离：

| 层级 | 回答的问题 | 表 | 状态 |
|---|---|---|---|
| 权限 | 「**这个人**能不能干这件事」 | `role_permission` | ✅ 已有 |
| 部门板块 | 「**这个部门**有没有这个业务」 | `department_module` | ✅ 0040 |
| ★ **岗位口径** | 「**这个部门里这个岗位**怎么考核」 | ★ `pan_workload_policy` | ★ **本次新增** |

⚠️ **板块开通 ≠ 全部门都要收推送** —— 短视频部 5 个人 3 种角色，
主播（口播成品不用管）/ 运营 / 编导 跟剪辑的考核方式**完全不同**。

## 九·十五、**★ 角色倒转：剪辑填数量、主管填比率（2026-11-23 已完成）**

### ⚠️ 业务原话

> 「剪辑先不填完播率，视频留存率这些，现在只要普通视频、xx条，ootd、xx条，
> 智能体，xx条，然后在下方给加一个备注框和上传截图/图片的框。
> 剪辑人员主要填这几项，然后完播率/视频留存率……这些数值给到主管填的」

### 倒转后的分工

| 角色 | 岗位口径 | 填什么 | 解析口径 |
|---|---|---|---|
| **剪辑** | `reporter` | 普通视频 xx 条 / OOTD xx 条 / 智能体 xx 条 / **备注（选填）** | `parse_count` —— **整数**，0~10000 |
| **主管**（编导/运营） | `reviewer` | 完播率 / 视频留存率 | `parse_rate` —— **0~1** |
| **主播** | `none` | — | 不收任何推送 |

⚠️ **「谁来填什么」由「部门 × 岗位」口径表决定**（`pan_workload_policy`），
不是代码写死的 —— 这正是 §九·十三 的核心。

### 🔴⚠️ 最危险的坑：**条数不能走比率解析**

```python
parse_rate("8")   # → 0.08   ❌ 「我剪了 8 条」变成「0.08 条」
parse_count("8")  # → 8.0    ✅
```

⇒ **静默错掉 100 倍**，不报错、不告警 ⇒ 必须两套解析器。

### 主管提交效果指标的安全边界

| # | 边界 | 落地 |
|---|---|---|
| **1** | 主管**只能**填**管理范围内**的剪辑 | `_leader_scope_employee_ids` —— 直属下属 + 汇报线全链 + 代理授权 + 所管部门；HR/管理员不限 |

| **3** | **认不出目标人就不填** | `_find_employee_by_name_or_id` —— 按姓名/工号精确匹配；**0 个或重名都返回 `None`** ⇒ 绝不瞎猜 |

### ⚠️⚠️ 「表格即表单」走不通（2026-11-23 真机实测）

用户提问：「能不能用户直接在框中填？」⇒ 试了把输入框放进表格单元格里：

| 变体 | 结构 | 结果 |
|---|---|---|
| **A** | 表格单元格里放 `input` | ⚠️ 接口接受，但**渲染成** `map[element_id:in_a1 input_type:text…]` —— Go 模板把字典当字符串打印了 |
| **A2** | `form` 里放 `table` | ❌ `type of element is not supported tag: table` |
| **B** | 表格列 `data_type: "input"` | ❌ `column idx:2` |
| **C** | `form` 里嵌套 `table` | ❌ 同 A2 |

⇒ **表格单元格只支持纯文本/数字/Markdown**；
⇒ 输入框**只能**在 `form` 里，而 `form` **装不下** `table`
⇒ 「表格即表单」在飞书卡片上**做不到**。

⚠️ **教训**：「接口返回 200」**≠**「渲染正确」——
飞书卡片结构错了不报错，只显示成乱码 ⇒ 必须**真机发一张 + 肉眼确认**。

### ⚠️⚠️⚠️ `plain_text` 不能当 body 元素（2026-11-23 真机实测，踩了）

⚠️ **症状** —— 用户点「提交」后飞书显示 **「显示出错了重试 code200671」**，
而**数据其实已经存进库了**（提交逻辑跑完了）—— 失败的只是**回执卡发不出去**。

⚠️ **根因** —— 回执卡把 ``_text(...)`` 直接当 body 元素：

```python
elements=[_text(f"{day_text}\n{lines}...")]   # ❌ 错
```

⚠️ **飞书报错**（WS 接收器日志里）：

```
type of element is not supported tag: plain_text,
path: ROOT -> body -> elements -> [0]
```

⇒ JSON 2.0 的 ``body.elements`` **不接受** ``plain_text``。

⇒ ``plain_text`` **只能**出现在**字段值**里：
``label`` / ``placeholder`` / ``button.text`` / ``header.title`` / ``div.text``。
⇒ 当正文元素必须包一层 ``div``：``{"tag": "div", "text": {"tag":"plain_text",...}}``
⇒ 已在 ``feishu_card.py`` 加 ``_div()`` 助手 + **全量守卫测试**
（把所有卡片构造器都跑一遍 ⇒ 不会再出现「某张卡发不出去」）。

### ⚠️⚠️⚠️ 飞书后台配的是 **WebSocket** 模式（2026-11-23 真机实测）

⚠️ **症状** —— 用户点按钮 ⇒ 飞书提示 **「目标回调服务当前未在线」**。

⚠️ **根因** —— 飞书后台「事件与回调」配的是**长连接**：

```json
{ "callback_type": "websocket", "subscribed_callbacks": ["card.action.trigger"] }
```

⇒ **WebSocket 模式下飞书不往任何 URL 发 HTTP 请求** ——
它等你的服务**主动连上去** ⇒ 只起 uvicorn（提供 HTTP 端点）**完全没用**。

⇒ 必须另起常驻进程：

```bash
python backend/scripts/run_feishu_ws.py
```

⚠️ **它注册了 ``card_action.trigger``** ⇒ 卡片回调能收到。

⚠️ **验证是否真连上**（不能只看进程在不在）：

```powershell
Get-NetTCPConnection -State Established |
  Where-Object { $_.OwningProcess -eq <WS进程PID> }
# 看到 RemotePort=443 Established ⇒ 连上了
```

⚠️ **读后台配置的官方 API**（不用猜）：

```python
GET https://open.feishu.cn/open-apis/application/v6/applications/{app_id}
# → data.app.callback_info.callback_type
#   = "websocket" | "webhook"
```

⇒ **正式部署建议切 Webhook**（配公网 HTTPS 地址）⇒ 单进程搞定，
不用维护「uvicorn + WS 接收器」两个进程。
