# CI 流水线说明

> 建立日期：2026-11-14
> 定义文件：`.github/workflows/ci.yml`
> 本地复现脚本：`backend/scripts/run_ci_locally.py`

---

## 一、为什么建这条流水线

在本流水线建立之前，项目的质量保障**完全依赖开发者本地的手工执行**。
这带来三个具体风险：

1. **本地绿灯 ≠ 线上绿灯**。本地环境有 `.env`、有历史数据库、有本地配置，
   CI 环境一切从零，二者行为可能不同。
2. **契约脱节静默积累**。前后端接口靠人工对齐，
   一旦有人改了后端路由而忘了改前端，没有任何东西会报警。
3. **「基线失败」吞掉真问题**。前端曾存在 10 个历史遗留失败测试，
   如果 CI 直接按退出码判定，它会永远红灯；
   如果直接忽略，又会让技术债悄悄扩大。

这条流水线的目标就是**用机制锁死前两类风险，同时正确处理第三类**。

> **2026-11-16 更新**：第三类风险已彻底解决 —— 10 个失败全部修完，
> 基线机制退役，前端测试改为**零失败硬门槛**（详见 §四）。

## 二、流水线结构

```
push / pull_request / workflow_dispatch
        │
        ├── job: backend ────────────┐  契约 + 测试 + 迁移 + 静态检查
        │                             │
        ├── job: agent-service ──────┤  智能体服务独立测试
        │                             │
        └── job: frontend ───────────┘  类型检查 + 零失败测试 + 构建
```

三个 job **并行**执行，互不阻塞；任一 job 失败则整体红灯。

### 触发条件

| 事件 | 分支 |
|---|---|
| `push` | `main` / `master` / `develop` |
| `pull_request` | `main` / `master` / `develop` |
| `workflow_dispatch` | 手动触发（排查用） |

同分支的后续 push 会**自动取消**上一个未完成的运行（`concurrency`），
避免 PR 上堆一串重复的检查记录。

## 三、各项检查详解

### 3.1 后端 job（12 步）

| 步骤 | 命令 | 拦截什么 |
|---|---|---|
| 安装依赖 | `pip install -r backend/requirements.txt` | — |
| **API 契约校验** | `python backend/scripts/check_api_contract.py --strict` | 前后端端点对不上（缺失 > 0 即失败） |
| **后端测试** | `pytest backend/app/tests -q` | 功能回归 |
| Alembic 升级 | `alembic upgrade head` | 迁移脚本不可执行 |
| Alembic 版本校验 | `alembic current` / `alembic heads` | 分支不一致 / 多头 |
| **迁移往返** | `downgrade -1` → `upgrade head` | 迁移不可回退 |
| **Schema 校验** | `verify_phase3_schema.py` | 9 张新表 / 20 个索引缺失，外键违规 |
| 静态检查 | `ruff check backend/app backend/scripts` | 未定义名、语法错误、未用导入、import 顺序、pyupgrade、bugbear |

> **契约校验是这条流水线最有价值的一步。**
> 它比对前端 `frontend/src/api/*.ts` 里所有 `http.get/post/put/delete('...')` 调用
> 与后端 FastAPI 实际注册的路由，任一侧单独改动都会被立即发现。

> **迁移往返检查的价值**：只测 `upgrade` 是不够的——
> 一个能升不能降的迁移，在生产环境回滚时会直接卡死。

### 3.2 智能体服务 job（4 步）

`agent-service/` 是独立的 FastAPI 服务，有自己的依赖与测试，
单独成 job，避免与主后端互相污染依赖。

### 3.3 前端 job（7 步）

| 步骤 | 命令 | 拦截什么 |
|---|---|---|
| 安装依赖 | `npm ci` | — |
| **类型检查** | `npx vue-tsc --noEmit` | TypeScript / Vue 模板类型错误 |
| **单元测试（零失败）** | `node --experimental-strip-types --test tests/*.test.ts` | **任何**测试失败 |
| 构建 | `npm run build` | 打包失败 |

## 四、前端测试：零失败硬门槛（2026-11-16 起）

### 4.1 演进

早期前端有 **10 个历史遗留失败**（断言与实现已不同步）。当时引入了
「基线锁定」机制 —— 用 `frontend/tests-baseline.json` 记录已知失败集合，
CI 判定「失败集合 ⊆ 基线集合 → 绿」。

这套机制**已于 2026-11-16 全部退役**：

- 10 个失败已逐条判定并修复（断言过时 → 改断言；实现退化 → 修实现）；
- `frontend/tests-baseline.json` 与 `frontend/scripts/run-tests-with-baseline.mjs` **已删除**；
- `npm run test:ci` 直接跑 `node --experimental-strip-types --test tests/*.test.ts`；
- CI 的前端测试步骤同步改为零失败硬门槛。

### 4.2 现在的规则

```
任一测试失败  →  红（立即阻断）
全部通过      →  绿
```

不再有任何「已知失败」豁免。

### 4.3 常用命令

```bash
cd frontend

# 本地跑（与 CI 完全一致）
npm run test:ci

# 只跑单个文件
node --experimental-strip-types --test tests/workspaces.test.ts
```

## 六、踩坑记录

### 坑 1：SQLite 相对路径在不同 CWD 下指向不同文件

`sqlite:///./data/x.db` 是**相对于进程工作目录**解析的：

| 运行者 | CWD | 实际落点 |
|---|---|---|
| 应用（pytest / 脚本） | 仓库根 | `<root>/data/x.db` |
| Alembic（CI 里 `working-directory: backend`） | `backend/` | `<root>/backend/data/x.db` |

两者指向**不同的文件**，导致 schema 校验查了一个空库，报「9 张表全部缺失」。

**解决**：CI 与本地脚本一律使用**绝对路径**：

```yaml
echo "DATABASE_URL=sqlite:///${{ github.workspace }}/data/_ci_backend.db" >> "$GITHUB_ENV"
```

> ⚠️ **2026-11-14 实战踩坑**：在 PowerShell 里临时设了
> `$env:DATABASE_URL` 指向临时库跑迁移，日志显示 `Running upgrade ... 0005`
> 一切正常，但**真实库 `backend/data/perf.db` 根本没变**——迁移写进了另一个文件。
> 教训有两条：
> 1. 跑迁移前先 `Remove-Item Env:\DATABASE_URL`，确认
>    `settings.database_url` 指向你以为的那个库；
> 2. 迁移后**必须回查** `alembic_version` 和目标表是否存在，不能只看日志。

### 坑 2：Windows 下 shell 不展开 glob

`spawn(..., { shell: true })` 配合 `tests/*.test.ts` 在 Windows 上不会展开通配符，
node 会把字面量 `tests/*.test.ts` 当文件名，导致一个测试都跑不到。

**解决**：运行器改为用 `readdir` 显式列出测试文件，`shell: false` 启动。

### 坑 3：`logging` 未导入的潜伏 bug

`ruff` 检查（`F821 Undefined name`）在 `backend/app/main.py` 中发现：

```python
@app.on_event("startup")
def _startup() -> None:
    ...
    except Exception:
        logging.getLogger(__name__).exception("启动飞书定时同步失败")
```

`logging` 没有在模块顶层导入。**只有当飞书定时同步启动失败时才会触发**，
平时测试覆盖不到——这是一颗定时炸弹。已在 CI 中加入 ruff 检查防止复发。

### 坑 4：`backend/tests/` 是历史遗留目录

该目录来自初始化提交，其中的测试引用了**早已被移除**的
`assessment_record.manager_comment` 列，因此 21 failed + 20 errors。
它**不属于**当前活跃测试套件（活跃套件是 `backend/app/tests/`）。

**处理**：CI 只跑 `backend/app/tests/`。
`backend/tests/` 的去留作为独立技术债项处理，不在本次范围内。

### 坑 5：本地 `.env` 泄漏进测试进程 —— 全量慢 16 倍（2026-11-21）

**现象**：本地跑全量后端测试要 **36 分 35 秒**；
把两个开关关掉后只要 **2 分 14 秒**（2477 passed / 0 failed）。
**同一个代码库、同一份测试，差 16 倍** —— 而且**测试全绿**，看不出任何异常。

**根因链条**：

| # | 环节 | 说明 |
|---|---|---|
| 1 | `config.py` 读本地 `.env` | `env_file=(BACKEND_ROOT / ".env", ".env")` —— **测试进程会读开发者本地的 `backend/.env`** |
| 2 | 本地 `.env` 开着调度开关 | 为真机联调，`BAIDU_PAN_ENABLED=true` / `FEISHU_SCHEME_SYNC_ENABLED=true` |
| 3 | startup 真起后台线程 | `app` 的 startup 钩子启动这两个调度器 |
| 4 | shutdown 要 join 线程 | 每个线程 `join(timeout=5.0)`（`_STOP_JOIN_TIMEOUT_SECONDS`） |
| 5 | 线程卡在真实取数 | 百度 OAuth / 飞书 API 未响应停止事件 → **不会立刻退出** |
| 6 | 每个 TestClient 白等 10 秒 | 全量有 31 个文件用 `TestClient`，反复建 app → 10 秒 × 数十次 |

**关键认知**：⚠️ **「本地慢、CI 快」的真相** ——
CI 上没有 `backend/.env`（被 `.gitignore` 排除），走代码默认值
（两个开关默认 `False`），所以 **CI 一直是快的**。
⇒ 本地那 36 分钟**不是「代码慢」，是「本地配置泄漏进了测试」**。

**解决**：在**仓库根 `conftest.py`**（导入期生效，早于任何 fixture）里
强制关闭所有后台调度器开关：

```python
_TEST_SCHEDULER_OFF = {
    "FEISHU_SYNC_ENABLED": "false",
    "FEISHU_SCHEME_SYNC_ENABLED": "false",
    "BAIDU_PAN_ENABLED": "false",
    "FEISHU_EVENT_CONSUME_ENABLED": "false",
    "PERIOD_SCHEDULER_ENABLED": "false",
    "NOTIFICATION_ENABLED": "false",
}
for _key, _value in _TEST_SCHEDULER_OFF.items():
    # ⚠️ 直接赋值，不用 setdefault —— setdefault 不覆盖已存在的值
    os.environ[_key] = _value
```

**为什么不在 `config.py` 里改默认值**：
这些开关的**代码默认值本来就该是 `False`**（防没配凭证时裸跑），
改默认值等于放松生产安全边界；而真机联调需要的恰恰是「本地 `.env` 开着」——
所以要关的是**测试进程**，不是配置本身。

**护栏**：新增 `backend/app/tests/test_test_scheduler_isolation.py`（11 例）——
① 每个开关都必须在根 conftest 里被关闭；② 不得用 `setdefault`；
③ **扫描 `config.py` 自动发现新增的 `*_enabled` 开关**，
漏关就失败（防止下次新增调度器又踩同一个坑）；
④ 用 **AST** 判定赋值必须在模块顶层（放 fixture 里会太晚 ——
`settings` 是模块级单例，首次 import 时就已读入 `.env`）。

**效果**：全量后端测试 **36 分 35 秒 → 2 分 13 秒**；
本地 CI 脚本 **10/10 全绿，总耗时 3 分 36 秒**。

> ⚠️ **这类失败的迷惑性**：测试**全绿**，只是慢得离谱。
> 如果只看「红绿」，永远不会发现它。
