### 🔴 BUG-R6-42 详述（本轮最有价值的发现）

**现象**
真实库 30 个部门，`organization_sync_cursor.checkpoint_value = 'e27127g2abc13e82'`
—— 正是部门列表里的**最后一个**（索引 29 / 30）。

此后每轮增量同步：

```
departmentsSynced  = 0
departmentsSkipped = 30
status             = ok        ← 表面完全正常
```

**根因**
游标被 `CursorManager.departments_to_process()` 当作**切分点**消费
（「checkpoint 之前的算已处理，之后的算待处理」），
但旧的 `_advance_cursors()` 记录的是 **全量部门列表的最后一个 ID**，
而不是**本轮真正处理过的最后一个部门**。

两者只在「全量列表最后一个 == 本轮处理最后一个」时相等 ——
而 `to_process` 恰好是 `departments` 的**后缀切片**，所以长期被掩盖。
一旦 `to_process` 为空（增量已到树末尾），checkpoint 就会被改写到
一个**本轮根本没处理过**的位置。

**为什么这个 bug 特别危险**
1. 批次状态永远是 `ok`，运维从监控上完全看不出问题；
2. 「新增部门同步不进来」会被误判成「飞书那边本来就没有」；
3. 飞书部门树顺序**不保证稳定**，顺序一变，切分点就漂移到无关部门。

**修复**
`_advance_cursors()` 增加 `processed_department_ids` 参数，
checkpoint 改取「本轮**实际处理过**的最后一个部门」；
本轮一个部门都没处理时**不推进**游标。

**验证**
- 新增 `backend/app/tests/test_sync_cursor_semantics.py`（8 个用例）；
- 真实飞书 API 链路连续三轮增量同步全部 `status=ok`，
  且 checkpoint 在「无增量可处理」时**保持不变**；
- 已重置真实库中被卡死的游标。

> 再取一次 `.data` 会得到 `undefined` → 页面显示「未找到自评内容」。

## 🔴 BUG-R6-06：审批详情把十六进制主键 ID 强转 int，全部塌成 0

**现象**
`GET /v1/leader/month-plan-approvals/{planId}` 返回：

```json
{ "plan": { "ownerId": 0, "orgId": 0,
            "items": [ { "id": 0, ... }, { "id": 0, ... } ] } }
```

实际主键是 `2aaf32ea`、`486d98d57d1c6b14`、`7db40cf4-0fe5-...` 这类**十六进制字符串**。

**根因**
`backend/app/services/plan_approval.py` 的 `_as_int()`：
```python
def _as_int(value: Any) -> int:
    """把字符串主键转成 int（前端 TS 类型是 number）。失败回退 0。"""
    try:
        return int(str(value))
    except (TypeError, ValueError):
        return 0
```
十六进制串 `int()` 必抛 ValueError → 一律回退 **0**。
`serialize_month_plan_approval_item()` 里 `ownerId` / `orgId` / `items[].id` 全走它。

**影响**
- 所有审批项的 `ownerId` / `orgId` / 条目 `id` 都是 0，**互相无法区分**；
- 前端 `el-table` 的 `row-key` 若用条目 id → 主键冲突；
- 任何依赖 `ownerId` / `orgId` 的前端逻辑（按人筛选、按组织筛选）都会失效。

**前端类型其实是对的**（`frontend/src/api/department.ts`）：
```ts
export interface MonthPlanApprovalItem {
  id: string
  /** 归属人 ID（飞书 user_id，string）。 */
  ownerId: string
  /** 组织 ID（飞书 department_id，string）。 */
  orgId: string
  ...
}
```
→ 是后端 `_as_int` 与前端类型**长期不一致**，注释里的「前端 TS 类型是 number」已过时。

**待修**
`plan_approval.py`：`_as_int` 改为原样返回字符串（并同步 `MonthPlanApprovalItem.items[].id`
的前端类型 `number` → `string`）。同类 `_as_int` 调用点一并排查。

## 🔴 BUG-R6-08：审批状态枚举前后端不一致 → 中文标签全部失效

**现象**
审批列表 / 详情里状态栏直接显示英文 `submitted`（应为「待审批」）、
审批意见区显示「待审批」但状态列是 `submitted`。

**根因**
- 后端 `backend/app/domain/enums.py` `PlanStatus`（`StrEnum`）用的是**小写**：
  `draft` / `submitted` / `approved` / `rejected`
- 前端 `frontend/src/views/performanceAdapters.ts` 的标签表用的是**大写**：
  ```ts
  const approvalStatusLabels: Record<string, string> = {
    PENDING_APPROVAL: '待审批',
    RETURNED: '待补正',
    APPROVED: '已通过',
    REJECTED: '已驳回',
  }
  ```

**连带影响（关键）**

**待修**
统一枚举口径：后端序列化时输出前端认识的值（或前端标签表补小写别名）。

## 🟡 观察项 R17：92 条同步错误 = 部门外键被 rollback 连带撤销

**根因（已用最小复现脚本验证）**
`organization_sync.py` 的 `_upsert_department()` 只调 `self.db.flush()`
（发 SQL 但**不 commit**）；随后 `_sync_employees()` 里某条员工插入异常时
执行 `self.db.rollback()` —— 这一 rollback 把**尚未提交的部门插入一并撤销**，
于是后续所有员工的 `department_id` 外键全部失败。

最小复现输出：
```
rollback 后 department 行数: 0     ← 部门被连带撤销
rollback 后 employee 行数: 0
E3 插入: *** 失败 *** IntegrityError: FOREIGN KEY constraint failed
```

**佐证**
- 失败批次 `ORG-20261114-d8fe0dfc5c`：`departments_synced=30`、
  `employees_synced=0`、`employees_failed=92`
- 下一批次 `ORG-20261114-e75a1f6d26`（full）`employees_synced=92` 成功
- 92 条错误消息全部是 `FOREIGN KEY constraint failed`，
  且 `error_category` 为 `None`（这些行早于 0010 迁移，未回填分类）

**待修**
`organization_sync.py` 的事务边界：部门写入应在员工写入前**独立提交**，
或改用 savepoint 隔离单条失败。→ 归入 P1 待办（用户已列为 P1 任务）。

## ✅ R6 期间飞书同步观察结论

### 92 条 FK 约束错误 —— 根因确认且已修复

**根因**（最小复现脚本验证过）
`organization_sync.py` 的 `_upsert_department()` 只调 `self.db.flush()`
（发 SQL 但**不 commit**）；随后 `_sync_employees()` 里某条员工插入异常时
执行 `self.db.rollback()` —— 这一 rollback 把**尚未提交的部门插入一并撤销**，
于是后续所有员工的 `department_id` 外键全部失败。

**修复**
`_savepoint()` 改用 **SAVEPOINT 子事务**：
每条记录的写入落在自己的子事务里，单条失败只回滚该 savepoint，
外层事务里已写入的数据全部保留。

**当前库实证**

|---|---|---|---|---|---|
| `ORG-20261114-d8fe0dfc5c` | 11-14 06:56 | full | 30 成功 | **92 失败** | `partial_failed` |
| `ORG-20261114-e75a1f6d26` | 11-14 06:57 | full | 30 成功 | 92 成功 | `ok` |

92 条 `organization_sync_item_error` 记录**已全部 `resolved`**（补偿重试成功）。

### 🟡 遗留观察（未修复，登记在待完善清单）

1. **`snapshot_complete` 恒为 `False`** ——
   `_advance_cursors` 里 `complete = snapshot_complete AND mode=='full'`，
   而最近所有成功批次都是 `incremental`。
   后果：「远端缺失 = 离职」这一判定的前提**从未成立**。
   这是**保守**方向（不会误停用员工），但意味着离职判定链路从未被真实验证过。

2. **历史脏批次** —— 11-16 07:46 ~ 08:31 有 6 组「一条 failed + 一条 ok」的
   重复批次对。`failed` 的那条 `error_message` 是
   「同步超时未完成（实例异常退出或重启）」，
   且 `started_at` 与配对的 `ok` 批次只差 0.1 秒。
   → 这是**旧代码**（`sync_all()` 自己新建批次，路由建的那条永远停在 running）
   留下的历史数据，30 分钟自愈机制把它标成了 failed。
   现已修复（`sync_all(batch=batch)` 复用既有批次行），但历史脏数据未清理。

3. **批次历史未分页** —— `organization_sync_batch` 已 26 行，
   同步状态接口一次性返回全部游标（32 条），数据量再涨需要分页。
