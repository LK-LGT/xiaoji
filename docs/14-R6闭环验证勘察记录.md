## 🔴 BUG-R6-06：审批详情把十六进制主键 ID 强转 int，全部塌成 0

**现象**
`GET /v1/leader/month-plan-approvals/{planId}` 返回：

```json
{ "plan": { "ownerId": 0, "orgId": 0,
            "items": [ { "id": 0, ... }, { "id": 0, ... } ] } }
```

实际主键是 `2aaf32ea`、`486d98d57d1c6b14`、`7db40cf4-0fe5-...` 这类**十六进制字符串**。

**根因**
`backend/app/services/plan_approval.py` 的 `_as_int()`：
```python
def _as_int(value: Any) -> int:
    """把字符串主键转成 int（前端 TS 类型是 number）。失败回退 0。"""
    try:
        return int(str(value))
    except (TypeError, ValueError):
        return 0
```
十六进制串 `int()` 必抛 ValueError → 一律回退 **0**。
`serialize_month_plan_approval_item()` 里 `ownerId` / `orgId` / `items[].id` 全走它。

**影响**
- 所有审批项的 `ownerId` / `orgId` / 条目 `id` 都是 0，**互相无法区分**；
- 前端 `el-table` 的 `row-key` 若用条目 id → 主键冲突；
- 任何依赖 `ownerId` / `orgId` 的前端逻辑（按人筛选、按组织筛选）都会失效。

**前端类型其实是对的**（`frontend/src/api/department.ts`）：
```ts
export interface MonthPlanApprovalItem {
  id: string
  /** 归属人 ID（飞书 user_id，string）。 */
  ownerId: string
  /** 组织 ID（飞书 department_id，string）。 */
  orgId: string
  ...
}
```
→ 是后端 `_as_int` 与前端类型**长期不一致**，注释里的「前端 TS 类型是 number」已过时。

**待修**
`plan_approval.py`：`_as_int` 改为原样返回字符串（并同步 `MonthPlanApprovalItem.items[].id`
的前端类型 `number` → `string`）。同类 `_as_int` 调用点一并排查。

## 🔴 BUG-R6-08：审批状态枚举前后端不一致 → 中文标签全部失效

**现象**
审批列表 / 详情里状态栏直接显示英文 `submitted`（应为「待审批」）、
审批意见区显示「待审批」但状态列是 `submitted`。

**根因**
- 后端 `backend/app/domain/enums.py` `PlanStatus`（`StrEnum`）用的是**小写**：
  `draft` / `submitted` / `approved` / `rejected`
- 前端 `frontend/src/views/performanceAdapters.ts` 的标签表用的是**大写**：
  ```ts
  const approvalStatusLabels: Record<string, string> = {
    PENDING_APPROVAL: '待审批',
    RETURNED: '待补正',
    APPROVED: '已通过',
    REJECTED: '已驳回',
  }
  ```
  `approvalStatusLabels['submitted']` → `undefined` → 回退显示原始英文。

**连带影响（关键）**
`frontend/src/views/department/MonthPlanApproval.vue`：
```ts
function canProcess(row) { return row.status === '待审批' }
function canApprove(row) { return row.aiCheck === '正常' && canProcess(row) }
```
后端给的是 `submitted` → `canProcess` 恒为 false → **审批按钮永远不可用**。

**待修**
统一枚举口径：后端序列化时输出前端认识的值（或前端标签表补小写别名）。
`confirmStatusLabels` / `reviewStatusLabels` / `riskLevelLabels` 需同样核对。

## 🔴 BUG-R6-10：`aiCheckResult` 恒为空 → `canApprove` 恒 false → 审批按钮永久禁用

**现象**
审批抽屉里「通过」按钮 `is-disabled`，且 tooltip 提示「必要字段缺失或已审批，不能直接通过」。

**根因（两条独立原因）**
1. `plan_approval.py` 两个序列化函数都**硬编码**：
   ```python
   "aiCheckResult": "",
   ```
   前端 `canApprove()` 要求 `row.aiCheck === '正常'`，
   而 `aiCheckLabels` 的键是 `NORMAL`（大写）→ 永远匹配不上 → 恒 false。
2. 就算第 1 条修了，**审批人（上级）也无法给下属计划跑 AI 检查**（见 BUG-R6-11）。

**待修**
- `aiCheckResult` 改为读取真实 AI 复核结果（`ai_review` 表最近一条），
  或在后端按「无复核记录 → `NOT_RUN`」显式给值；
- 前端 `aiCheckLabels` 与后端取值口径对齐；
- `canApprove` 的准入条件改为「无高风险 + 无缺失字段」，不要把「AI 已跑且正常」
  当作硬前置。

## 🔴 BUG-R6-11：AI 检查只允许计划本人，审批人给下属跑 AI 检查报「月计划不存在」

**现象**
```
POST /v1/ai/reviews/plans/MONTH_PLAN/{planId}/check   （以主管身份）
-> 404 {"detail":"月计划不存在"}
```

**根因**
`backend/app/routes/ai_review.py` 的 `_load_plan_items()`：
```python
plan = planning.get_month_plan(db, user.id, plan_id)   # 校验 owner_id == user.id
```
`planning.get_month_plan()` 内部是 `if plan.owner_id != owner_id: raise PlanNotFound`。
即：**AI 检查只对计划所有者开放**，主管看下属计划时必然 404。

**待修**
AI 复核的读权限应与审批读权限一致：本人 **或** 对该计划有审批权
（`access_control.can_access_employee`）都应放行。

## 🔴 BUG-R6-04：`GET /v1/department/employees` 恒 500（orgId 类型不匹配）

**现象**
```
GET /v1/department/employees -> 500
{"detail":"获取部门员工失败: 1 validation error for DepartmentEmployeeSummary
 orgId  Input should be a valid string [type=string_type, input_value=1, input_type=int]"}
```

**根因**
`backend/app/routes/department.py` `list_department_employees()`：
```python
org_id_int = 1                                  # 默认 org_id
if emp.department_id:
    try:
        org_id_int = int(emp.department_id) if isinstance(emp.department_id, str) else emp.department_id
    except (ValueError, TypeError):
        org_id_int = 1                           # 十六进制部门 ID → 回退成 int 1
...
result.append(DepartmentEmployeeSummary(
    orgId=org_id_int,                           # ← int 塞进 str 字段 → Pydantic 报错
```
而 `DepartmentEmployeeSummary.orgId: str`。
部门主键是 `912ecd8a7f82e638` 这类十六进制串，`int()` 必失败 → 恒回退 `1`（int）→ 校验炸。

**影响**
部门工作台「员工」列表整块 500，页面拿不到任何员工。

**待修**
`orgId` 直接用 `str(emp.department_id or "")`，删掉 `int()` 转换；
根节点哨兵值按既有约定用字符串 `"0"`（同文件 `_empty_leader_employee_summary` 的写法）。

## 🔴 BUG-R6-05：`project-*-packages` 参数名 camelCase/snake_case 不一致 → 422

**现象**
```
GET /v1/department/project-month-plan-packages?planMonth=2026-11 -> 422
{"detail":[{"type":"missing","loc":["query","plan_month"],"msg":"Field required"}]}
```

**根因**
前端 `frontend/src/api/department.ts` 由调用方传 `{ planMonth }`（camelCase），
后端 `department.py` 声明的是：
```python
plan_month: str = Query(..., regex=r"^\d{4}-\d{2}$"),
```
FastAPI 按**下划线名**取 query 参数 → `plan_month` 缺失 → 422。

> 同文件 `/month-plan-approvals/page` 早已踩过同一个坑并修过，注释写着
> 「⚠️ 回归点：此前用 snake_case，前端传的 camelCase 会被静默忽略」，
> 但 `project-month-plan-packages` / `project-result-packages` **漏改了**。

**待修**
两处 `Query` 参数改为 camelCase（`planMonth`），或用 `alias` 兼容两种。

## 🟡 观察项 R17：92 条同步错误 = 部门外键被 rollback 连带撤销

**根因（已用最小复现脚本验证）**
`organization_sync.py` 的 `_upsert_department()` 只调 `self.db.flush()`
（发 SQL 但**不 commit**）；随后 `_sync_employees()` 里某条员工插入异常时
执行 `self.db.rollback()` —— 这一 rollback 把**尚未提交的部门插入一并撤销**，
于是后续所有员工的 `department_id` 外键全部失败。

最小复现输出：
```
rollback 后 department 行数: 0     ← 部门被连带撤销
rollback 后 employee 行数: 0
E3 插入: *** 失败 *** IntegrityError: FOREIGN KEY constraint failed
```

**佐证**
- 失败批次 `ORG-20261114-d8fe0dfc5c`：`departments_synced=30`、
  `employees_synced=0`、`employees_failed=92`
- 下一批次 `ORG-20261114-e75a1f6d26`（full）`employees_synced=92` 成功
- 92 条错误消息全部是 `FOREIGN KEY constraint failed`，
  且 `error_category` 为 `None`（这些行早于 0010 迁移，未回填分类）

**待修**
`organization_sync.py` 的事务边界：部门写入应在员工写入前**独立提交**，
或改用 savepoint 隔离单条失败。→ 归入 P1 待办（用户已列为 P1 任务）。
