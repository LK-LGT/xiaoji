# 飞书自动发现 —— IT 操作指引

> 目标：让本应用能**自动扫描**飞书知识空间，自动发现所有部门的绩效方案文档，
> 自动建立「部门 ↔ 方案」绑定，无需人工逐个填写链接。

---

## 一、现状（2026-11-20 实测）

权限已全部开通（247 个 scope，含 `wiki:wiki:readonly`），
但**应用没被加入任何知识空间**，所以：

| 接口 | 结果 |
|---|---|
| `GET /wiki/v2/spaces`（空间列表） | OK，但 **0 个空间**，`has_more=false` |
| `GET /wiki/v2/spaces/{id}/nodes`（节点列表） | **131006** 权限拒绝 |
| `GET /wiki/v2/spaces/get_node`（单节点） | OK ✅ |

⚠️ **官方文档明确说明了这个现象**：

> *"please make sure that the application/bot has access to part of the Wiki space,
> otherwise the return list is easy to be empty"*

⇒ **这不是 scope 问题，是「加成员」问题。**

---

## 二、两种加成员方式

### 方式一：手工加群（推荐，5 分钟，无需改代码）

官方推荐路径，适合没有管理员 API 权限的情况。

**第 1 步｜确认应用已开「机器人」能力**

> 飞书开放平台 → 开发者后台 → 你的应用 → **添加应用能力** → 机器人 → **添加**

⚠️ 如果已经加过，跳过这步。

**第 2 步｜发布应用新版本**

> 开发者后台 → **版本管理与发布** → 创建版本 → 发布

⚠️ **必须发布** —— 不发布的话群机器人不生效。
⚠️ 发布时确认**可用范围**包含知识库的所有者。

**第 3 步｜建群并把应用拉进群**

> 飞书客户端 → 新建群（如「绩效系统机器人群」）
> → 群设置 → 群机器人 → 添加 → 选择你的应用

⚠️ **必须是「应用机器人」，不是「自定义机器人」** —— 这是官方文档特别标注的坑。

**第 4 步｜把群加为知识空间成员**

> 打开绩效方案所在的知识库 → **设置** → **成员设置**
> → 添加成员 → 搜索**刚才那个群**
> → 角色选「**可阅读的成员**」（或「管理员」）

> 💡 空间 ID 在知识库设置页 URL 里：
> `https://xxx.feishu.cn/wiki/settings/6870403571079249922`
> 最后那串数字就是 `space_id`。

**验证**

```powershell
python backend/scripts/probe_feishu_docs.py
```

期望看到：

```
wiki 空间列表 → OK, N 个空间
   · 绩效方案库 | space_id=7702734617867635710
```

### 方式二：用 API 自动加成员（更全自动）

如果希望**连加成员这一步也自动化**，可以调：

```
POST /open-apis/wiki/v2/spaces/{space_id}/members
```

**请求体**：

```json
{
  "member_type": "appid",
  "member_id": "<应用的 app_id>",
  "member_role": "member"
}
```

**前提条件**（缺一不可）：

| 条件 | 说明 |
|---|---|
| `wiki:member:create` scope | 新增知识空间成员权限，**需申请** |
| **知识库管理员的 user_access_token** | ⚠️ 调用身份必须是该空间的**管理员** |
| 应用数据范围 | tenant token 需配置可访问范围 |

⚠️ **注意 `member_type` 的坑**：
- `appid` → 加应用本身（我们需要的）
- `openid` → 加用户（应用要用用户身份时）

⚠️ **公开空间**（`visibility=public`）**不支持加成员**，但可以加管理员。

**实现位置建议**：加进 `feishu_scheme_source.py` 的 `discover()` 之前，
做成一个「首次自动授权」的引导流程 —— 检测到 `131006` 时，
提示 HR 用知识库管理员的 token 触发一次授权，成功后永久生效。

⚠️ 但这需要**存储 user_access_token 并处理 refresh_token**，
复杂度明显上升。**建议先用方式一打通，再考虑要不要自动化这一步。**

## 三、加完之后，代码侧已经就绪（无需改动）

我已把自动发现接进同步轮次 —— `run()` 现在是：

```
① 自动发现（扫空间 → 补齐没绑定的部门）   ← 新增
② 同步（逐个来源：查变化 → 抓正文 → 建版本 → 发布）
```

⚠️ **顺序刻意设计成「先发现再同步」** ——
本轮新发现的文档，本轮就能同步，不用多等一个周期。

**实测行为**（空间未授权时）：

```
批次状态: failed | 来源 1 | 变更 0 | 发布 0 | 失败 1

=== 自动发现结果 ===
status = skipped
reason = 缺少 wiki 空间读权限：应用未被加入该飞书知识空间（需在知识库设置里把应用加为成员），
        空间 7702734617867635710
discovered 数 = 0
```

⇒ **优雅降级**：发现跳过，但已绑定来源照常同步，不会拖垮整轮。

**加完之后**，`discover()` 会返回：

```json
{
  "status": "ok",
  "discovered": [
    {"title": "短视频剪辑岗位绩效考核方案", "department_name": "短视频", ...},
    {"title": "采购部绩效考核方案",       "department_name": "采购部", ...}
  ]
}
```

自动建立的绑定 `binding_mode = auto`。
⚠️ **人工绑定优先** —— 自动发现只填空位，不会覆盖已有的人工绑定。

## 四、标题规范要求（决定能自动对上几个部门）

自动发现靠**文档标题**匹配部门。实测用系统里 30 个真实部门名测试：

```
✔ 短视频剪辑岗位绩效考核方案  →  短视频
✔ 采购部绩效考核方案          →  采购部
✔ 财务部月度考评办法          →  财务部
✔ 仓储部绩效考核细则          →  仓储部
✔ 客服部绩效考核制度          →  客服部
✔ 直播部月度考核方案          →  直播部
✔ 包装小组绩效考核方案        →  包装小组
✔ 版房绩效考核方案            →  版房
✔ 总经办绩效考核办法          →  总经办
✔ 运营部绩效考核方案（2026版）→  运营部
✔ 跨境部绩效考评方案          →  跨境部
✔ 短视频岗位考核标准          →  短视频
✘ 视频剪辑绩效考核系统        →  未匹配（这是多维表格，不是方案文档）
```

**命中率 12/13，唯一未匹配的是多维表格 —— 属于正确拒绝。**

### 标题规范

✅ **能自动匹配**：

```
{部门名}绩效考核方案
{部门名}月度考评办法
{部门名}绩效考核细则
{部门名}绩效考评方案
{部门名}岗位考核标准
```

⚠️ **标题里必须含部门名**，且**必须唯一命中** —— 猜错部门比匹配不上严重得多。

❌ **不会匹配**（当噪音处理，不是方案文档）：

```
员工手册
日汇报表单
短视频剪辑绩效考核系统   ← 多维表格
```

### 关键词识别

标题需含以下任一关键词才会被当作方案文档：

```
绩效 / 考核 / 方案 / 考评
```

## 五、两个独立的坑（别混淆）

| 错误码 | 含义 | 解决 |
|---|---|---|
| `99991672` | 应用**没申请**对应 scope | 开发者后台申请 + **发布新版本** |
| `131006` | scope 有，但**应用没被加入该知识空间** | 加成员（本文档第二、三步） |

⚠️ `131006` 的官方排查提示原文：

> *"注意：应用访问或操作文档时，除了申请 API 权限，
> 还需授权具体文档资源的阅读、编辑或管理权限。"*

⇒ **两个条件是「与」的关系**，只满足一个都不行。

## 六、验证清单

```powershell
# 1. 空间列表（应能看到空间）
python backend/scripts/probe_feishu_docs.py

# 2. 节点扫描 + 正文抓取
python backend/scripts/probe_feishu_docs.py M41sw6DwOipVJukEYGIcQlianXb
#    [2] 正文抓取          → OK
#    [3] 知识空间扫描      → OK   ← 加成员前是 ERROR 131006

# 3. 触发一次自动发现（只报告不落库）
#    POST /v1/feishu/scheme/sources/discover  {"dry_run": true}

# 4. 触发完整同步
#    POST /v1/feishu/scheme/sync
```

**判定标准**：第 2 步的 `[3] 知识空间扫描` 从 `ERROR 131006` 变成 `OK` = 成功。

## 七、结论

- **代码侧 100% 就绪** —— 自动发现已接进定时同步轮次，加成员后立刻生效，**一行代码都不用改**。
- **只需要 IT 做一件事**：把应用（或含应用的群）加为知识空间的**可读成员**。
- **标题规范要提前对齐** —— 否则扫出来了也对不上部门。
