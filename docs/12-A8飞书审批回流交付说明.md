## 三、核心设计

### 3.1 幂等：飞书是「至少一次」投递

飞书 webhook 可能重复推送同一事件。幂等做在**三层**：

```
第 1 层  dedup_key 唯一约束    → 同一事件只写一条流水
第 2 层  计划已是终态检查      → approved/rejected 后不再流转
第 3 层  状态机合法性校验      → 非法迁移跳过而非报错
```

幂等键用**独立命名空间**：

```python
# 飞书回流
f"feishu:{plan_type}:{plan_id}:{action}:{version_no}:{instance_id}"
# 本系统手动审批（原有）
f"{plan_type}:{plan_id}:{action}:{version_no}"
```

⚠️ 两者**必须分开**，否则飞书回流会吞掉本系统的审批流水（或反之）。

### 3.2 三种计划的列名差异（最容易踩的坑）

回流时必须分别处理，**不能想当然套用月计划**：

| 计划类型 | 状态字段 | 时间字段 | 意见字段 | 特殊语义 |
|---|---|---|---|---|
| 月计划 | `status` | `approved_at` | `approval_comment` | — |
| 周计划 | `status` | **`approve_at`** | `approval_comment` | 注意是 `approve_at`，少个 `d` |
| 日计划 | **`status` 不动** | `reviewed_at` | `leader_comment` | 抽检语义，只写 `review_status` |

日计划尤其特殊：**主管抽检不改主状态机**，只记录抽检结论，否则会阻塞员工的计划流程。

### 3.3 通知是旁路动作，失败绝不影响主流程

```python
feishu_approval_sync.notify_plan_submitted_safe(...)  # 路由层调用
```

- 飞书未配置 → 直接跳过
- 任何异常 → 只记日志，**不外抛**
- 员工提交计划**永远成功**，不会因为发不出通知而报错

### 3.4 Webhook 鉴权：宁可不放行

```python
if not settings.feishu_approval_webhook_token:
    raise HTTPException(503)   # 未配置 → 端点不可用
```

⚠️ **未配置 token 时返回 503 而不是放行** —— 这是审批状态的**写入入口**，
一旦无鉴权放开，任何人都能改审批状态。

当前实现采用**明文 Verification Token** 比对模式。
飞书的 **Encrypt Key（AES 加密）模式未实现** —— 需额外解密依赖，复杂度更高；
当前部署走明文模式已足够。

## 九、A8 补强：计划 ↔ 飞书实例持久绑定

> 补强日期：2026-11-16　提交：`dcfefe4`

### 9.1 要解决的问题

A8 首批实现的审批回流依赖 webhook 事件**自带** `plan_type` / `plan_id`。
这只覆盖了「本系统提交 → 飞书收到通知」这一半：

- **员工从飞书侧发起审批**时，事件里只有飞书实例信息（instance_code /
  approval_code / 发起人），**没有本系统的计划 ID** —— 那条链完全接不上；
- 即便是本系统发起的，回流也依赖事件方「记得」带上计划标识，
  一旦事件来源变化（飞书工作流、第三方转发）就会断。

### 9.2 两条独立关联通道

```
┌──────────────────────────────────────────────────────────────┐
│ 通道 A：instance_code 精确匹配                              │
│   本系统提交计划 → 建绑定 → 回流时按实例 code 反查计划       │
│   适用：本系统发起的审批                                    │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ 通道 B：correlation_key 关联键匹配                          │
│   本系统生成 8 位短码 → 随通知发给员工                       │
│   员工在飞书审批表单填入该码 → 回流时按码反查计划            │
│   适用：飞书侧发起的审批 ← 本次补强的核心                    │
└──────────────────────────────────────────────────────────────┘
```

反查优先级：**`instance_code` > `correlation_key` > 均无**（记日志忽略，
返回成功避免飞书反复重试）。

### 9.3 表结构

新增 `plan_feishu_binding`：

| 列 | 说明 |
|---|---|
| `plan_type` / `plan_id` | 多态关联三张计划表（不建物理外键，与 `plan_approval` 同模式） |
| `instance_code` | 飞书审批实例 code（通道 A） |
| `approval_code` | 飞书审批定义 code |
| `correlation_key` | 关联码（通道 B），形如 `PPAB12CD34` |
| `bind_source` | `local_submit` / `feishu_match` / `manual` |
| `instance_status` | 最后一次同步到的飞书实例状态 |

**三个唯一约束保证 1:1**，反查不会歧义：

| 约束 | 保证 |
|---|---|
| `uq_plan_feishu_binding_plan` | 一个计划只能绑一个实例 |
| `uq_plan_feishu_binding_instance` | 一个实例不能绑多个计划 |
| `uq_plan_feishu_binding_corr` | 一个关联码全局唯一 |

### 9.4 关联码的设计考量

- **格式**：`PP` + 8 位大写字母数字，共 10 字符
- **字符集刻意剔除易混字符**（`0`/`O`、`1`/`I`/`L`）——
  员工在飞书表单里**手输**时不易出错
- **归一化容错**：大小写、空格、连字符、前缀缺失都能识别
  （员工只抄了主体码也能匹配上）
- **员工可见**：关联码随 IM 通知发给员工，通知文案里明确写
  「在飞书发起审批时填写此码」

### 9.5 新增端点

| 端点 | 方法 | 鉴权 | 说明 |
|---|---|---|---|
| `/v1/feishu/approval/bindings` | GET | 管理员 | 列绑定关系 |
| `/v1/feishu/approval/bindings` | POST | 管理员 | 手工绑定（补建历史 / 人工关联） |
| `/v1/feishu/approval/bindings/by-plan/{plan_type}/{plan_id}` | GET | 管理员 | 查某计划的绑定与关联码 |

`POST /v1/feishu/approval/reflow` 的 `plan_type` / `plan_id` 也改为**可选** ——
留空时按 `instance_id` 走绑定反查。

## 十一、A8 补强二：事件格式适配 + Encrypt Key 支持

> 补强日期：2026-11-16　提交：见 git log

### 11.1 发现的问题：webhook 此前**收不到任何真实事件**

这不是推测，是**实测复现**的。用飞书官方文档的 v2.0 事件格式投递：

```
=== 用飞书真实 v2.0 事件格式投递 ===
  HTTP 状态码: 401
  响应体: {"detail":"Verification Token 校验失败"}
```

**根因是字段名完全对不上**。原实现读的是 body 顶层的
`token` / `instance_code` / `instance_status`，而飞书**真实的 v2.0 信封**是：

```json
{
  "schema": "2.0",
  "header": {
    "token": "xxxx",              ← token 在 header 里，不在顶层
    "event_type": "approval.approval.updated_v4"
  },
  "event": {
    "object": {
      "approval_id": "74333067777841234",    ← 实例 ID 叫 approval_id
      "approval_code": "5B43240B-...",       ← 审批定义 code
      "status": "APPROVED"                    ← 状态在这里
    }
  }
}
```

而且**后台已配置 Encrypt Key**（加密策略）—— 这意味着飞书推送的根本不是
上面这个 JSON，而是：

```json
{ "encrypt": "<base64密文>" }
```

**连 `header.token` 都读不到，必须先解密。**

> ⚠️ 为什么之前 35 个测试全绿？因为**测试 payload 是照着实现自己构造的**
> —— 自证自洽，测不出「实现和真实协议不符」这类问题。
> 这类缺陷只能靠**对着官方文档的原始格式**验证才能发现。

### 11.2 三个必修项

| # | 问题 | 修复 |
|---|---|---|
| 1 | **字段名对不上** | 新增 `services/feishu_event.py`，把 v2.0 / v1.0 / 扁平三种信封归一化成统一结构 |
| 2 | **加密模式完全不支持** | 实现 AES-256-CBC 解密 + SHA-256 签名校验 |
| 3 | **缺 `url_verification` 握手** | 实现握手处理 —— 不实现的话**飞书后台根本保存不了回调地址** |

第 3 项是**「鸡生蛋」闭环**的关键：飞书保存回调地址前会先发一个带
`challenge` 的探测请求，要求 **1 秒内**原样返回。没这一步，
后台的「加密策略」页也就无从启用，Encrypt Key 自然拿不到。

### 11.3 两种推送模式的自动切换

```
飞书推送 body
      ↓
  含 "encrypt" 字段？
      ├── 是 ──→ 验签(sha256) ──→ AES-256-CBC 解密 ──→ 明文 JSON
      └── 否 ──→ 直接用明文 body
      ↓
  归一化（v2.0 / v1.0 / 扁平）
      ↓
  比对 Verification Token
      ↓
  回流
```

**任何一步失败都直接拒绝，不做降级放行**：

| 情况 | 返回 |
|---|---|
| 收到密文但没配 Encrypt Key | 503 |
| 签名不匹配 | 401 |
| 密文解不开 | 400 |
| Token 不匹配 | 401 |
| 未配置 Token | 503 |

### 11.4 官方算法（逐字照抄）

**解密**（`decrypt_event`）：
```
key = SHA256(Encrypt Key)          # 32 字节
blob = base64decode(encrypt)
iv, ciphertext = blob[:16], blob[16:]
plain = AES-256-CBC(key, iv).decrypt(ciphertext)
result = plain[:-plain[-1]]          # PKCS7 去填充
```

**签名校验**（`verify_signature`）：
```
b1 = (timestamp + nonce + encrypt_key).encode("utf-8")
b  = b1 + 原始 body 字节
s  = sha256(b).hexdigest()
校验 s == X-Lark-Signature
```

⚠️ **body 必须用原始字节** —— 反序列化再序列化会得到不同的字节序列，
签名就对了不上。这是官方明确标注的坑。

### 11.5 回归向量

## 十二、给领导的书面汇报版本

> **A8 飞书审批回流与 IM 通知已开发完成**
>
> **背景**：系统内部的计划、审批、成果链路（A1~A7）此前已全部打通，
> 但与飞书之间仍是「单向隔离」——员工在飞书的审批结果进不来，
> 本系统提交的计划也通知不到飞书。A8 就是补齐这段跨系统链路。
>
> **一个重要的核查结论**：立项时文档记录「飞书审批与 IM 权限尚未开通，需等待 IT 申请」。
> 2026-11-16 我们用系统已配置的凭据直接调用飞书开放平台逐一实测，
> **确认这些权限其实早已开通**。原因是早前的判断只依据文档记录、未做实际验证，
> 而飞书的权限不足会返回明确的错误码、与「参数没传对」返回的错误码形态完全不同。
> 这个结论直接让 A8 从「等待外部审批的阻塞任务」变成了「可立即开工的开发任务」，
> 并已交付。
>
> **交付内容**：
> - 8 个接口端点，其中 1 个是接收飞书审批事件的入口（带令牌校验）
> - 2 条跨系统链路打通：飞书审批结果自动回流本系统并触发状态流转；
>   本系统计划提交后自动给主管发飞书待办消息
> - 90 个验收测试全部通过；接口契约零缺失
>
> **一个关键的补强**：首批实现只打通了「本系统发起 → 飞书通知」这一半 ——
> 员工**从飞书侧发起**审批时，系统认不出这是哪个计划。
> 本次新增「计划 ↔ 飞书实例」的持久绑定表，用两条通道解决：
> 一是按飞书实例编号精确匹配；二是生成一个 8 位**关联码**随通知发给员工，
> 员工在飞书表单里填入即可自动关联（该编码刻意剔除了容易看错的字符，
> 便于手输）。至此，**两个方向的审批都能自动回流**。
>
> **另一个更重要的核查结论**：对照飞书官方文档逐一核对事件格式时，
> 发现接收端点**此前实际上收不到任何真实事件** —— 飞书的推送报文结构
> 与最初理解的并不相同（凭据藏在报文头里、实例编号与状态字段名称也不同），
> 且后台已启用加密推送，报文是密文，必须解密才能读取。
> 原有的测试之所以全绿，是因为**测试数据是照着代码自己构造的**，
> 属于「自己证明自己正确」，测不出与真实协议不符的问题。
> 本次按官方原始格式重写了解析与校验逻辑，并补上了**回调地址握手**
> （这是飞书后台能保存回调地址的前提），同时实现了官方标准的
> **加密解密与数字签名校验**，并用官方公布的测试向量做回归锁定。
> 修正后，真实加密事件、伪造签名拦截、明文兼容、地址握手
> 四项均已实测通过。
>
> **技术要点（供技术评审）**：
> - **幂等**：飞书事件可能重复推送，做了三层幂等保护，重复事件只更新状态不重复写流水
> - **关联无歧义**：数据库唯一约束保证「一个计划只绑一个实例、一个实例只绑一个计划」，
>   反查不会出现二义
> - **双重来源校验**：启用加密时同时校验数字签名与令牌，任何一步失败都直接拒绝，
>   **不做降级放行** —— 不存在未鉴权的审批写入入口
> - **状态机一致性**：回流失效时不强行改状态，跳过并记录，避免脏数据
> - **通知不影响主流程**：飞书通知失败绝不影响员工提交计划的成功
>
> **价值**：主管可以在飞书里看到审批待办，不必专门登录本系统；
> 无论审批从哪一侧发起，结果都能自动同步，审批口径保持一致。
>
> **后续**：用户态令牌链路（仅影响「列出审批定义」这类管理功能，
> 不影响审批回流）、定时补偿拉取，均已在交付文档中列明。
