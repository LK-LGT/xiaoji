## 三、核心设计

### 3.1 幂等：飞书是「至少一次」投递

飞书 webhook 可能重复推送同一事件。幂等做在**三层**：

```
第 1 层  dedup_key 唯一约束    → 同一事件只写一条流水
第 2 层  计划已是终态检查      → approved/rejected 后不再流转
第 3 层  状态机合法性校验      → 非法迁移跳过而非报错
```

幂等键用**独立命名空间**：

```python
# 飞书回流
f"feishu:{plan_type}:{plan_id}:{action}:{version_no}:{instance_id}"
# 本系统手动审批（原有）
f"{plan_type}:{plan_id}:{action}:{version_no}"
```

⚠️ 两者**必须分开**，否则飞书回流会吞掉本系统的审批流水（或反之）。

### 3.2 三种计划的列名差异（最容易踩的坑）

回流时必须分别处理，**不能想当然套用月计划**：

| 计划类型 | 状态字段 | 时间字段 | 意见字段 | 特殊语义 |
|---|---|---|---|---|
| 月计划 | `status` | `approved_at` | `approval_comment` | — |
| 周计划 | `status` | **`approve_at`** | `approval_comment` | 注意是 `approve_at`，少个 `d` |
| 日计划 | **`status` 不动** | `reviewed_at` | `leader_comment` | 抽检语义，只写 `review_status` |

日计划尤其特殊：**主管抽检不改主状态机**，只记录抽检结论，否则会阻塞员工的计划流程。

### 3.3 通知是旁路动作，失败绝不影响主流程

```python
feishu_approval_sync.notify_plan_submitted_safe(...)  # 路由层调用
```

- 飞书未配置 → 直接跳过
- 任何异常 → 只记日志，**不外抛**
- 员工提交计划**永远成功**，不会因为发不出通知而报错

### 3.4 Webhook 鉴权：宁可不放行

```python
if not settings.feishu_approval_webhook_token:
    raise HTTPException(503)   # 未配置 → 端点不可用
```

⚠️ **未配置 token 时返回 503 而不是放行** —— 这是审批状态的**写入入口**，
一旦无鉴权放开，任何人都能改审批状态。

当前实现采用**明文 Verification Token** 比对模式。
飞书的 **Encrypt Key（AES 加密）模式未实现** —— 需额外解密依赖，复杂度更高；
当前部署走明文模式已足够。

## 四、飞书权限实测（2026-11-16）

用项目已配置的凭据直接调飞书 OpenAPI，观察服务端返回：

| 接口 | 返回 | 判定 |
|---|---|---|
| `GET /contact/v3/users` | `200` | 通讯录读权限**已开通** |
| `GET /approval/v4/instances` | `400 99992402` | 鉴权通过 → **权限已开通** |
| `GET /approval/v4/instances/tasks` | `400 1390003` | 已进业务层 → **权限已开通** |
| `GET /approval/v4/approvals` | `400 99991663` | **需 user_access_token**（非权限缺失） |
| `GET /calendar/v4/calendars` | `400 99992402` | **权限已开通** |
| `GET /im/v1/messages` | `400 230001` | **权限已开通** |
| `POST /attendance/v1/user_tasks/query` | `400 99992402` | **权限已开通** |

**判据**：飞书权限不足返回 `99991668`（未获得通讯录权限）、`99991672`（缺少权限或版本未发布）
等**明确的权限错误码**；而 `99992402 field validation failed` 出现在**鉴权通过之后**的参数校验层，
`1390003` 更是**已进入业务逻辑** —— 都说明权限是通的。
实测中权限错误码一个都没出现。

### 4.1 两个实现坑（实测发现）

1. **审批定义列表真实路径是 `/approval/v4/approvals`**（不是 `approval_definitions`），
   且**要求 `user_access_token`**（用户态），用 tenant token 调会报 `99991663`。
2. **考勤任务是 `POST /attendance/v1/user_tasks/query`**，不是 GET。

### 4.2 复查命令

```bash
cd backend && python scripts/check_feishu_scopes.py
```

脚本按六类结果精确区分：

| 判定 | 含义 |
|---|---|
| ✅ 权限已开通 | 调用成功 |
| ⚠️ 权限已开通（参数待调） | `99992402` / `230001` / `1390003` |
| ⚠️ 权限已开通（需用户态 token） | `99991663` |
| ⚠️ 探测路径有误 | 404 |
| ⚠️ 服务端故障 | 5xx |
| ❌ 权限不足 | `99991668` / `99991672` 等 —— **这才需要申请** |

当前实测：**权限不足 0 项**。

> **A8 飞书审批回流与 IM 通知已开发完成**
>
> **背景**：系统内部的计划、审批、成果链路（A1~A7）此前已全部打通，
> 但与飞书之间仍是「单向隔离」——员工在飞书的审批结果进不来，
> 本系统提交的计划也通知不到飞书。A8 就是补齐这段跨系统链路。
>
> **一个重要的核查结论**：立项时文档记录「飞书审批与 IM 权限尚未开通，需等待 IT 申请」。
> 2026-11-16 我们用系统已配置的凭据直接调用飞书开放平台逐一实测，
> **确认这些权限其实早已开通**。原因是早前的判断只依据文档记录、未做实际验证，
> 而飞书的权限不足会返回明确的错误码、与「参数没传对」返回的错误码形态完全不同。
> 这个结论直接让 A8 从「等待外部审批的阻塞任务」变成了「可立即开工的开发任务」，
> 并已交付。
>
> **交付内容**：
> - 5 个接口端点，其中 1 个是接收飞书审批事件的入口（带令牌校验）
> - 2 条跨系统链路打通：飞书审批结果自动回流本系统并触发状态流转；
>   本系统计划提交后自动给主管发飞书待办消息
> - 35 个验收测试全部通过；后端全量 598 个测试零失败；接口契约零缺失
>
> **技术要点（供技术评审）**：
> - **幂等**：飞书事件可能重复推送，做了三层幂等保护，重复事件只更新状态不重复写流水
> - **状态机一致性**：回流失效时不强行改状态，跳过并记录，避免脏数据
> - **通知不影响主流程**：飞书通知失败绝不影响员工提交计划的成功
> - **安全**：事件入口未配置令牌时直接拒绝服务，不存在无鉴权的审批写入入口
>
> **价值**：主管可以在飞书里看到审批待办，不必专门登录本系统；
> 员工在飞书发起的审批结果能自动同步，审批口径保持一致。
>
> **后续**：加密模式接入、用户态令牌链路、计划与飞书实例的持久绑定，
> 以及定时补偿拉取，均已在交付文档中列明。
