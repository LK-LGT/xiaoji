| 项 | 内容 |
|---|---|
| 现象 | 前端点「生成日计划」直接报 `Request failed with status code 422`，抽屉里没有任何草稿 |
| 抓法 | 浏览器里 hook `window.fetch` + `XMLHttpRequest`，把**请求体和响应体**一起截下来 |

| 修复 | 后端改 `str \| int \| None`（只放宽不收紧）；前端 `aiConversations.ts` 等 6 处类型从 `number` 改 `string` |
| ⚠️ 为什么能活很久 | 后端**从没把 `conversationId` 传给智能体**（纯会话元数据）⇒ 测试里看不出问题；只有前端把 UUID 回传才炸 —— **只有真机联调才会炸** |
| 护栏 | `backend/app/tests/test_plan_ai_endpoints.py` 新增 4 例（UUID 必收 / 历史 int 也收 / 月周日三端点） |

### CI-5 · 前端 E2E（Playwright）· 重新评估

⚠️ **台账原描述低估了门槛**。实际调研发现（2026-11-24）：

**现有 43 个前端测试文件、337 例，没有一个是真正的组件测试。**

它们是**读 `.vue` 源文件做正则断言**：

```typescript
const weekApproval = await readFile(new URL('WeekPlanApproval.vue', leaderRoot), 'utf8')
assert.match(weekApproval, /white-space:\s*pre-wrap/)
```

⇒ 这验证的是「文件里有没有这个 CSS 字符串」，不是「组件渲染出来对不对」。

**后果**：
- 组件**逻辑**改了但 CSS 类名没变 → 测试**照样通过**（假绿）；
- CSS 改名了但行为没变 → 测试**变红**（假红）。

⇒ CI-5 要补的不只是「加 Playwright」，而是**补上整个渲染层测试能力**：

| 前置 | 现状 |
|---|---|
| `@vue/test-utils` | ❌ 未安装 |
| `jsdom` | ❌ 未安装 |
| Playwright + 浏览器二进制 | ❌ 无配置（CI 需 `npx playwright install`） |
| 后端服务 + 测试库 | 需在 CI 里起（现有 `verify_plan_approval_e2e.py` 是后端 E2E） |

⚠️ **架构约束**：Playwright 再写一遍完整业务流，等于**同一套流程维护两份**（后端脚本 + 前端 E2E），极易两边漂移。

⇒ **建议分两步**：
- **5a · 组件测试层**（成本中，收益高）：先补 `@vue/test-utils` + `jsdom`，把「读源码断言」逐步换成「真实挂载断言」；
- **5b · 端到端**（成本高）：只覆盖**跨角色的关键路径**，且尽量**复用**后端 E2E 的数据准备逻辑，而不是重写一遍。

### BUG-R6-45 专项：离职链路首次真实验证（2026-11-16）

**结论**：台账里挂了很久的「离职链路从未真实验证过」，本轮**已验证**。

**根因**：`snapshot_complete` 有三个写入点，其中**分部门粒度**
（`employee:<部门ID>`）那个**从未被写入**：

| 游标粒度 | 写入点 | 修复前 | 修复后 |
|---|---|---|---|
| `department` | `_advance_cursors` | ✅ True | ✅ True |
| `employee` | `_advance_cursors` | ✅ True | ✅ True |
| `employee:<部门ID>` | **无人写入** | ❌ 恒 False | ✅ True |

分部门游标由 `save_page_token` 维护（分页续传用），
而它**只写 `page_token`、从不碰 `snapshot_complete`** —— 于是永远保持初始值 False。

**真实库实测**：30 条 `employee:<dept>` 游标**全部**为 False。

**影响**：`snapshot_complete` 是「远端缺失 = 离职/删除」的**唯一前提**。
前提不成立 → `_deactivate_missing_employees` 每次都直接 return →
**离职链路从未真正跑过一次**。

**修复**：
- `sync_cursor.py::save_page_token` —— 清掉 `page_token`（= 拉完最后一页）
  时置 `snapshot_complete=True`；新增显式 `snapshot_complete` 参数。
- `organization_sync.py::_fetch_employees_for_one_department` ——
  分页回调传 `snapshot_complete=not token`；部门拉完后显式置 True。

**验证**（`backend/app/tests/test_snapshot_complete_bug_r6_45.py`，8 例）：
- ✅ 全量同步后**所有**游标 `snapshot_complete=True`

- ✅ **反向保护**：快照不完整（部门拉取失败）时**绝不**误判离职
- ✅ **安全边界**：没有 `feishu_user_id` 的本地手工账号不会被判离职

**数据清理**：`backend/scripts/clean_snapshot_complete_cursors.py`
（默认演练，加 `--apply` 才写库）—— 真实库 23 条脏游标已修正，

### 📐 BUG-R6-26 专项：周期格式统一（2026-11-17 已修）

### 📄 BUG-R6-46 专项：同步游标接口分页（2026-11-17 已修）

**根因**
`GET /v1/feishu/sync-organization/cursors` **一次性返回全部游标**，没有分页。

### 🧹 BUG-R6-47 专项：历史脏批次清理（2026-11-17 已修）

**根因查清了** —— 台账里记的「6 组重复批次对」**不是重复数据**，
而是「一次异常 + 一次成功重试」的历史痕迹：

```
进程被 kill → 批次卡在 running
  ↓ 下次调度前 recover_stale_batches() 自愈
标成 failed（错误信息「同步超时未完成（实例异常退出或重启）」）
  ↓ 紧接着的重试
又落一条 ok 批次
```

所以每组长这样（时间戳只差 0.1 秒）：

| failed | ok |
|---|---|
| 07:46:17.607 | 07:46:17.738 |
| 07:58:46.487 | 07:58:46.597 |
| 08:05:39.390 | 08:05:39.498 |
| 08:11:32.750 | 08:11:32.884 |
| 08:23:57.733 | 08:23:57.935 |
| 08:31:54.109 | 08:31:54.324 |

**修复**：`backend/scripts/clean_dirty_sync_batches.py`
（默认演练，加 `--apply` 才写库）

| 脏批次类型 | 处理 |
|---|---|
| 超时失败，且**其后有成功批次** | → `superseded`（新增状态，区分于真失败） |
| 卡在 `running` 且**超过超时阈值** | → `failed` |
| **真正的失败历史** | **不动** —— 那是证据，不是垃圾 |
| `partial_failed` | **不动** —— 表示「部分同步成功」，不是脏数据 |

> ⚠️ **只改状态、不物理删除** —— 批次是审计链的一环
> （`organization_sync_audit.batch_id` / `organization_sync_item_error.batch_id` /
> `organization_sync_cursor.last_batch_id` 都指向它），
> 删掉会留下悬空外键，审计记录也断链。

**真实库执行结果**
```
清理前：failed 7 / partial_failed 1 / running 1 / ok 18
清理后：failed 2 / partial_failed 1 / superseded 6 / ok 18
悬空外键：0        二次运行：幂等（"无需清理"）
```
保留的 2 条 `failed` 是**真失败**（`database is locked`）与
卡死的 `running` —— 都不是历史痕迹，是真实记录。

**验证**：`backend/app/tests/test_clean_dirty_sync_batches_script.py`（12 例），
含「演练模式不写库」「真失败必须保留」「绝不删行」「幂等」四类护栏。


### 🔐 BUG-R6-32 专项：登录页明文密码落盘（2026-11-17 已修）

**现象**
`Login.vue` 的「记住密码」复选框会把 `{ username, password, expiresAt }`
写进 `localStorage['planning_login_password_memory']`，有效期 **7 天**。

**危害**
- `localStorage` 对**同源 JS 完全可读** → 任何 XSS / 第三方脚本 /
  浏览器插件都能直接拿到**可直接登录的明文口令**（不是哈希）；
- 密码会留在浏览器磁盘快照、devtools、用户主动「导出站点数据」里；
- 用户在公用电脑上退出登录后，**密码仍然在磁盘上**。

**修复**
| 项 | 修复前 | 修复后 |
|---|---|---|
| 存储 key | `planning_login_password_memory` | `planning_login_username_memory` |
| 存的内容 | `{username, **password**, expiresAt}` | `{username, expiresAt}` |
| 有效期 | 7 天 | 30 天（只存账号，风险低，可以久一点） |
| 加载回填 | 用户名 + **密码** | 只回填用户名，**密码框留空** |
| 复选框文案 | 「记住密码」 | 「记住账号」 |
| 旧数据 | — | `purgeLegacyPasswordMemory()` **主动删除**旧 key |

> ⚠️ 迁移是**必须**的：老版本已经在用户浏览器里写过明文密码，
> 只改新逻辑不管旧数据，风险窗口会一直开着。
> 所以 `loadRememberedUsername()` 第一件事就是
> `localStorage.removeItem('planning_login_password_memory')`。

**回归**
- `frontend/tests/login-remember-username.test.ts`（6 例）——
  断言 `localStorage.setItem` 的实参里**永不出现 password**、
  旧 key 只被 `removeItem` 不被 `getItem`、加载时不回填密码框；
- `frontend/tests/login-remember-username-sensitivity.test.ts`（2 例）——
  **敏感度自检**：在内存里构造「又存了密码」的回归样本，
  证明断言真的能抓到（避免测试写成永远通过的样子）。

> ⚠️ 顺带修了一个**测试自身的缺陷**：
> 第一版断言用了 `localStorage\.[a-zA-Z]+\([^)]*password`，
> 会把 `removeItem(LEGACY_PASSWORD_MEMORY_KEY)` 也算成违规 ——
> 常量名里带 `PASSWORD` 是刻意的（它只删不读）。
> 已收窄到只查 `setItem` / `getItem`。

### 5.2.6 B2 · 测试账号别名去歧义 ✅ **已交付（2026-11-24）**

**问题**：`manager`（杨飞）与 `leader`（别嘧咪）这组名字有**三个**毛病：

| # | 毛病 | 实测证据 |
|---|---|---|
| ① | **两个不同的人，权限完全一样** | 两人都是「总经理 / 总经办」，`access_control` 给的角色集与权限集**逐项相同（零差异）** ⇒ 写「主管权限」还是「直属领导权限」的用例**根本测不出差别** |
| ② | **登录名与 RBAC 角色名撞车** | RBAC 里的 `manager` = 「有直属下属」，`department_leader` = 「部门 `leader_id`」⇒ 看到 `manager` 分不清是账号还是角色 |

### 5.2.7 B3 · 配置类端点读权限收紧 ✅ **已交付（2026-11-24）**

**问题**：`GET /v1/baidu/workload/bindings` 用 `_require_leader`（主管即可），
而同一资源的 `POST /bindings` 用 `_require_admin`（HR/管理员）
⇒ **能读不能写**的不对称；
且 `_require_leader` 只问「你是不是**某个**主管」，
过了之后 `select(PanAccountBinding)` **不带任何范围过滤**
⇒ 任意主管（含**外部门**主管）都能拿到**全公司**的「目录 → 人员」对照表。

**为什么按「要管理员」而不是「按管辖范围过滤」**

| # | 理由 |
|---|---|
| ① | **读写口径必须一致** —— 同一个资源，读写用同一个鉴权函数 |
| ② | **它是配置数据，不是业务数据** —— `PanAccountBinding` 是「网盘目录 → 员工」的映射表，由 HR/管理员维护（写端点**早就**限定了） |
| ③ | **主管看自己范围内的绑定没有业务价值** —— 一个目录绑给谁是**公司级决策**（改错了全公司工作量都算错）；只让人看到「改一下就能把工作量算到自己名下」反而是误导 |

⇒ 与同模块的 `POST /collect` / `POST /aggregate` 口径一致。

**改动**：`backend/app/routes/pan_workload.py` —— `GET /bindings` 改用 `_require_admin`。

**护栏测试**（7 例，加在 `backend/app/tests/test_admin_data_scope.py::TestBindingsReadScope`）：

| # | 用例 | 作用 |
|---|---|---|
| 1 | 主管不能读绑定列表 | `E_ZJ`（张洁，编导，两位剪辑的直属上级）⇒ **能过**旧 `_require_leader` ⇒ 正是越权入口 |
| 2 | **外部门**主管不能读 | 防「改成按范围过滤」——那样外部门主管仍会拿到自己那几条（口径仍不一致） |
| 3 | 员工不能读 | 防回退 |
| 4 | HR 能读 | **配对** ⇒ 证明 1~3 不是「端点坏了」 |
| 5 | 管理员能读 | **配对** ⇒ 与既有的 `test_管理员仍能管理配置`（写）配成一对 ⇒ 不会死锁 |
| 6 | **读写鉴权口径一致**（静态） | 用 `ast` 扫全模块 ⇒ 锁住「GET 的鉴权函数 == POST 的鉴权函数」 |

⚠️ **敏感度自检已做** —— 把 `_require_admin` 改回 `_require_leader` 后，

⇒ 证明这组测试测的是**差异**，不是「端点恰好坏了」。
