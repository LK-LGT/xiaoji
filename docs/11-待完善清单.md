**原问题**：`GET /system/workday-rules` **硬编码**恒定返回一条 `2024-01-01 元旦`，

**已交付**：

| 项 | 位置 |
|---|---|
| 表模型 | `backend/app/domain/workday_models.py` |
| 服务层 | `backend/app/services/workday_rule.py` |
| 迁移 | `backend/migrations/versions/0006_phase5_workday_rule.py` |
| 端点 | `backend/app/routes/v1/system.py` |
| 消费方 | `services/planning.py` / `routes/employee_plans.py` / `routes/employee.py` |
| 前端 | `frontend/src/api/system.ts` / `frontend/src/views/system/WorkdayRules.vue` |
| 测试 | `backend/app/tests/test_workday_rule_api.py`（30 例） |

**表设计**：
- **全局 / 个人共用一张表**，用 `employee_id` 区分（`NULL` = 全局节假日；
  非空 = 个人请假 / 出差）。两者结构、版本化、生效逻辑一致，分表会让查询翻倍。
- **版本化**：同一 `(rule_date, rule_type, employee_id)` 保存调整时**新增一版**，
  `version_no` 递增，历史版本保留可追溯。
- **默认规则不落库**：周一~周五工作日、周六日周末，由服务层推导。
  落库反而要维护成千上万行。前端契约的 `explicit` 字段表达「有没有显式配过」。
- **主键用整型自增**：前端契约 `WorkdayRule.id: number`。用 UUID 字符串会被
  前端类型转换抹成 `0`，导致后续更新 / 删除全部 404。

**规则解析优先级**：个人规则 > 全局规则 > 默认推导。

**消费方接线**（这是价值所在，不只是建表）：
- `calendarRule` —— 日计划详情返回真实日历口径，替掉写死的 `WORKDAY`。
- `workdayCalendar` —— 员工工作台生成当月完整日历。
- `missingRequiredDayPlanCount` —— 真实统计「应填未填」的缺报日。

### BUG-R6-45 专项：离职链路首次真实验证（2026-11-16）

**结论**：台账里挂了很久的「离职链路从未真实验证过」，本轮**已验证**。

**根因**：`snapshot_complete` 有三个写入点，其中**分部门粒度**
（`employee:<部门ID>`）那个**从未被写入**：

| 游标粒度 | 写入点 | 修复前 | 修复后 |
|---|---|---|---|
| `department` | `_advance_cursors` | ✅ True | ✅ True |
| `employee` | `_advance_cursors` | ✅ True | ✅ True |
| `employee:<部门ID>` | **无人写入** | ❌ 恒 False | ✅ True |

分部门游标由 `save_page_token` 维护（分页续传用），
而它**只写 `page_token`、从不碰 `snapshot_complete`** —— 于是永远保持初始值 False。

**真实库实测**：30 条 `employee:<dept>` 游标**全部**为 False。

**影响**：`snapshot_complete` 是「远端缺失 = 离职/删除」的**唯一前提**。
前提不成立 → `_deactivate_missing_employees` 每次都直接 return →
**离职链路从未真正跑过一次**。

**修复**：
- `sync_cursor.py::save_page_token` —— 清掉 `page_token`（= 拉完最后一页）
  时置 `snapshot_complete=True`；新增显式 `snapshot_complete` 参数。
- `organization_sync.py::_fetch_employees_for_one_department` ——
  分页回调传 `snapshot_complete=not token`；部门拉完后显式置 True。

**验证**（`backend/app/tests/test_snapshot_complete_bug_r6_45.py`，8 例）：
- ✅ 全量同步后**所有**游标 `snapshot_complete=True`
- ✅ 完整快照下，远端缺失的飞书员工**确实**被判定为 `exited` + `disabled`
- ✅ **反向保护**：快照不完整（部门拉取失败）时**绝不**误判离职
- ✅ **安全边界**：没有 `feishu_user_id` 的本地手工账号不会被判离职

**数据清理**：`backend/scripts/clean_snapshot_complete_cursors.py`
（默认演练，加 `--apply` 才写库）—— 真实库 23 条脏游标已修正，
现 `snapshot_complete=0` 的游标 **0 条**。

> ⚠️ **顺带澄清一个语义**（避免以后误改）：
> `_deactivate_missing_employees` 只处理 **`feishu_user_id` 非空**的员工。
> 本地手工建的账号（测试数据、管理员）**不在**判定范围内 ——
> 否则会被大面积误判离职。回归测试里对此有专门断言。

> 与本轮浏览器实测新发现的 `BUG-R6-43`（查看自评白屏）/ `BUG-R6-44`（数组字段渲染）
