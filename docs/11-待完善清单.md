### 🧹 BUG-R6-47 专项：历史脏批次清理（2026-11-17 已修）

**根因查清了** —— 台账里记的「6 组重复批次对」**不是重复数据**，
而是「一次异常 + 一次成功重试」的历史痕迹：

```
进程被 kill → 批次卡在 running
  ↓ 下次调度前 recover_stale_batches() 自愈
标成 failed（错误信息「同步超时未完成（实例异常退出或重启）」）
  ↓ 紧接着的重试
又落一条 ok 批次
```

所以每组长这样（时间戳只差 0.1 秒）：

| failed | ok |
|---|---|
| 07:46:17.607 | 07:46:17.738 |
| 07:58:46.487 | 07:58:46.597 |
| 08:05:39.390 | 08:05:39.498 |
| 08:11:32.750 | 08:11:32.884 |
| 08:23:57.733 | 08:23:57.935 |
| 08:31:54.109 | 08:31:54.324 |

**修复**：`backend/scripts/clean_dirty_sync_batches.py`
（默认演练，加 `--apply` 才写库）

| 脏批次类型 | 处理 |
|---|---|
| 超时失败，且**其后有成功批次** | → `superseded`（新增状态，区分于真失败） |
| 卡在 `running` 且**超过超时阈值** | → `failed` |
| **真正的失败历史** | **不动** —— 那是证据，不是垃圾 |
| `partial_failed` | **不动** —— 表示「部分同步成功」，不是脏数据 |

> ⚠️ **只改状态、不物理删除** —— 批次是审计链的一环
> （`organization_sync_audit.batch_id` / `organization_sync_item_error.batch_id` /
> `organization_sync_cursor.last_batch_id` 都指向它），
> 删掉会留下悬空外键，审计记录也断链。

**真实库执行结果**
```
清理前：failed 7 / partial_failed 1 / running 1 / ok 18
清理后：failed 2 / partial_failed 1 / superseded 6 / ok 18
悬空外键：0        二次运行：幂等（"无需清理"）
```
保留的 2 条 `failed` 是**真失败**（`database is locked`）与
卡死的 `running` —— 都不是历史痕迹，是真实记录。

**验证**：`backend/app/tests/test_clean_dirty_sync_batches_script.py`（12 例），
含「演练模式不写库」「真失败必须保留」「绝不删行」「幂等」四类护栏。


### 🔐 BUG-R6-32 专项：登录页明文密码落盘（2026-11-17 已修）

**现象**
`Login.vue` 的「记住密码」复选框会把 `{ username, password, expiresAt }`
写进 `localStorage['planning_login_password_memory']`，有效期 **7 天**。

**危害**
- `localStorage` 对**同源 JS 完全可读** → 任何 XSS / 第三方脚本 /
  浏览器插件都能直接拿到**可直接登录的明文口令**（不是哈希）；
- 密码会留在浏览器磁盘快照、devtools、用户主动「导出站点数据」里；
- 用户在公用电脑上退出登录后，**密码仍然在磁盘上**。

**修复**
| 项 | 修复前 | 修复后 |
|---|---|---|
| 存储 key | `planning_login_password_memory` | `planning_login_username_memory` |
| 存的内容 | `{username, **password**, expiresAt}` | `{username, expiresAt}` |
| 有效期 | 7 天 | 30 天（只存账号，风险低，可以久一点） |
| 加载回填 | 用户名 + **密码** | 只回填用户名，**密码框留空** |
| 复选框文案 | 「记住密码」 | 「记住账号」 |
| 旧数据 | — | `purgeLegacyPasswordMemory()` **主动删除**旧 key |

> ⚠️ 迁移是**必须**的：老版本已经在用户浏览器里写过明文密码，
> 只改新逻辑不管旧数据，风险窗口会一直开着。
> 所以 `loadRememberedUsername()` 第一件事就是
> `localStorage.removeItem('planning_login_password_memory')`。

**回归**
- `frontend/tests/login-remember-username.test.ts`（6 例）——
  断言 `localStorage.setItem` 的实参里**永不出现 password**、
  旧 key 只被 `removeItem` 不被 `getItem`、加载时不回填密码框；
- `frontend/tests/login-remember-username-sensitivity.test.ts`（2 例）——
  **敏感度自检**：在内存里构造「又存了密码」的回归样本，
  证明断言真的能抓到（避免测试写成永远通过的样子）。

> ⚠️ 顺带修了一个**测试自身的缺陷**：
> 第一版断言用了 `localStorage\.[a-zA-Z]+\([^)]*password`，
> 会把 `removeItem(LEGACY_PASSWORD_MEMORY_KEY)` 也算成违规 ——
> 常量名里带 `PASSWORD` 是刻意的（它只删不读）。
