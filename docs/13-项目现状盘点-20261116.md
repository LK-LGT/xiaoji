## 二、整体架构设计

### 2.1 五层模型（设计意图）

```
L0  飞书              入口：组织架构源 / 审批表单 / IM 通知     不自建登录、不自建消息
L1  前端              Vue3 + Vite + Element Plus + Pinia     渲染 / 交互 / 表单采集
                     axios baseURL=/api → Vite 代理重写 → /v1
L2  业务后端          FastAPI（backend/app）                 ★ 唯一事实源，分数只在这里产生
                     ├─ routes/    HTTP 边界（26 router / 352 端点）
                     ├─ services/  业务编排（25 个服务）
                     ├─ domain/    领域模型 + 枚举（4 文件 / 53 表）
                     └─ core/      配置 / DB / 迁移
L3  智能体服务        FastAPI（agent-service）                辅助判断、辅助写作
L4  模型层            当前 = EchoModelClient（确定性假模型）   可切 DeepSeek / 通义
```

**横切能力**：权限（`access_control`）、审计（`audit_log` + `organization_sync_audit`）、脱敏（响应头兜底）、幂等（批次 / 审批 / 回流三层）、降级（AI 挂 → 模板兜底）。

### 2.4 飞书对接链路（4 条）

```
① 组织架构（读，主事实源）
   定时(feishu_scheduler) / 人工(POST /v1/feishu/sync-organization)
     → 建批次 + 抢分布式锁 → 拉部门/员工 → 落库 → 对账 → 审计
   幂等：idempotency_key（唯一索引）
   失败：error_category 分级 / 单条错误入 organization_sync_item_error
   自愈：recover_stale_batches()

② 审批回流（写回）
   飞书 Webhook POST /v1/feishu/approval/events (Verification Token)
     → 事件去重 → 匹配 plan_feishu_binding（instance_code 或 PP+8位关联码）
     → 更新计划状态 → 触发 IM 通知（旁路，失败只记日志，不影响提交成功）
   补偿：POST /v1/feishu/approval/reflow（手工触发）

③ 身份绑定
   feishu_identity 表 276 条
   端点：unbound / conflicts / bind / unbind / disable-account / set-login-account / audits

④ 考勤
   attendance_record 2351 条真实数据
   六类异常（迟到/早退/缺卡/外勤/请假/加班）全部 reference_only，永不进算分集
```

### 2.5 前端 / 后端 / 存储职责边界

| 层 | 负责 | 不负责 |
|---|---|---|
| 前端 | 渲染、交互、表单采集、视图编排、AI 会话 UI | **不算分、不判等级**；不做权限判定（只做显示层隐藏） |
| 后端 L2 | 状态机流转、权限判定、算分、证据管理、对外契约 | **不做 UI 逻辑**；不直接信任 URL/Body 里的 `employee_id` |
| 后端 L3 | 评级建议、评语草稿、证据缺口、公平性报告 | **不写业务表、不定状态、不产生数字** |
| 存储 | 持久化、约束、审计留痕 | 不含业务规则 |

## 七、协作流程约定（后续开发适用）

> 口诀：**先看全景 → 确认方案 → 再拿代码**

1. **先问设计 / 影响范围**
   这个功能属于哪个模块？依赖哪些接口 / 数据表？会不会影响飞书同步、鉴权、其他页面？
2. **再要方案、验收标准**
   先给方案思路 + 验收自测点，确认思路没问题再写代码。
3. **最后才要代码**
   实现代码附带注释，说明**这个改动改了什么、为什么这么改**。

每次做完一个模块，同步更新第六节的进度表。
