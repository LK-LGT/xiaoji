#### 0.0.1 STEP 0 期间的三个技术发现（直接影响 FS-1 实现）

| # | 发现 | 影响 |

| **F1** | **`GET /contact/v3/users/{id}` 必须带 `user_id_type=user_id`** | ⚠️ **漏了会踩坑**：缺此参数时飞书按 **open_id** 解析，传 user_id 返回 `99992351「not a valid {open_id}」` → **免登查不到人**。已在探测脚本中固化 |

### 0.1 查身份绑定覆盖率

**为什么先查这个**：免登靠 `feishu_identity` 表把 `open_id` 映射到 `Employee`。如果表里绑定不全，**上线当天就会有人登不进来**。

Write-Output "token 获取: $($token.Length) 字符"

Invoke-RestMethod -Uri "http://127.0.0.1:8000/v1/feishu/identities/unbound" `
  -Headers @{ Authorization = "Bearer $token" } | ConvertTo-Json -Depth 5

# 查冲突

### 2.2 🔴 关键实现约束（照做，别自己发挥）

**约束 A：token 必须独立缓存**

现状是**单槽位**：

```python
self._access_token: str | None = None
self._token_expires_at: datetime | None = None
```

**必须**改成独立槽位，**不能复用** `_access_token`：

```python
# ✅ 正确：三类 token 各有各的槽位
self._tenant_token: str | None = None
self._tenant_token_expires_at: datetime | None = None
self._user_token: str | None = None
self._user_token_expires_at: datetime | None = None
self._app_ticket: str | None = None
self._app_ticket_expires_at: datetime | None = None
```

**为什么这条是硬约束**：若用户态 token 写进 `_access_token`，租户态的
组织架构同步、审批回流会**随机 401**（谁后调用谁中毒）——
而且是**间歇性故障**，极难排查。

**约束 B：`user_access_token` 只在后端内存活**

- 用完即弃，**绝不返回给前端**
- 前端最终只拿**本系统签发的 HMAC token**（复用 `routes/auth.py::_generate_token`）
- 复用即自动继承 `token_version` 失效机制 → 离职/禁用后免登 token 立即失效 ✅

**约束 C：state 必须一次性 + 短时效 + 绑 redirect**

- 存服务端（session/Redis），TTL ≤ 10 分钟
- 校验后**立即删除**（防重放）
- 绑定发起时的 `redirect_uri`（防开放重定向）

**约束 D：复用 `resolve_employee`，不要自己写查询**

`FeishuIdentityService.resolve_employee()` 已实现「只认在职且启用账号」防线，
**免登必须走它**，不要绕过。

#### ⚠️ 实施期踩出的 4 个坑（都是「不踩就不知道」的坑）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| **P1** | **state 字段分隔符撞上小数点** | `issued_at` 用 `float` → `1794888912.9136994` 的小数点把 state 拆成 **5 段** → `split(".", 3)` 解析错位 → 报「state 签名无效」 | 时间戳改 **`int(time.time())`**；nonce 用 base64url（不含 `.`）；已在 docstring 写明「每个字段都不能含 `.`」 |
| **P2** | **签名载荷两边不一致** | 签发时签**明文** redirect_uri，校验时签**base64** 后的 → HMAC 永远对不上 | 统一签 base64 串（`payload = f"{nonce}.{issued_at}.{encoded}"`） |
| **P3** | ⚠️ **state 存实例字段 = 必然全站失败** | 签发 state 的请求与消费 state 的请求是**两个不同请求**，路由每次都 new 一个 service → 第二个请求看不到 state → **每个用户都**报「state 无效或已被使用」 | state 存储改**模块级共享** `_STATE_STORE`。⚠️ 多实例部署需换 Redis（FS-7 任务 7.3） |
| **P4** | **飞书用户信息响应多一层** | `/contact/v3/users/{id}` 返回 `{"data":{"user":{...}}}`，而 `_request_with_token` 已剥掉外层 `data` → open_id 在**再一层** | 兼容两种形状：优先取 `info["user"]`，否则取 `info` |

> 💡 **P3 是本轮最有价值的发现** —— 它是**架构级**问题，不修的话 FS-2 免登上线后
> **100% 失败**，且报错信息（「state 无效或已被使用」）完全指向错误方向
> （会让人以为是重放攻击或密钥问题）。
> 这正是「先写测试」的价值：P3 是被 `test_feishu_token_never_leaks_to_response`
> 这个**走真实 HTTP 路由**的用例抓出来的 —— 纯服务层单测发现不了。

## 二·五、🔑 `redirect_uri` 配合指南（FS-2 必读，**需要 IT 配合**）

> 这是一份**可以直接转发给 IT / 飞书管理员**的说明。
> 位置放在这里是因为：**它挡住了 FS-2 真机验证**，但**不挡住前端开发**。

### 2.5.1 为什么需要配合（以及为什么你无法自己搞定）

飞书免登是**三方跳转**：

```
浏览器 ──① 跳转──→ 飞书授权页 ──② 用户点「同意」──→ 飞书 ──③ 302 跳回──→ 我们的 callback 页
                    ↑
              这一步要校验 redirect_uri 是否在
              飞书后台的「重定向 URL」白名单里
```

**校验发生在飞书服务器上**。我们能改 `.env`，但**改不了飞书后台**——那需要飞书应用管理员权限。

⚠️ **实测发现（2026-11-17）**：这个校验**无法在授权页阶段探测出来**。
用 `httpx` 请求 `/authen/v1/index`，**任何** redirect_uri（换成别的域名、加端口、
改协议、加子路径）都返回**完全一样的 200 + 5931 字节 HTML**（飞书是 SPA，
校验在页面加载后由 JS 发起）。

> 💡 **推论**：**别指望本地日志能看到 redirect_uri 不匹配的提示** ——
> 错误只出现在飞书授权页的界面上。后台没配对 = 用户点「同意」后看到飞书的报错页，
> 而我们的后端**完全没有收到请求**（连日志都没有）。
> 这就是 Runbook 里「错误只在飞书侧，本地日志看不到」的确切含义。

### 2.5.2 需要 IT 做的**唯一**一件事

**位置**：飞书开发者后台 → 应用 `cli_aa7f2e3902385d0e` → **应用能力** → **网页应用**

在「重定向 URL」里添加：

```
https://<你们的域名>/feishu/callback
```

**如果开发环境也要用**，再额外加一条：

```
http://localhost:5180/feishu/callback
```

### 2.5.3 ⚠️ 「逐字一致」到底指什么（最容易踩的坑）

飞书做的是**字符串精确匹配**（不是前缀匹配）。以下**任何一处**不同都会被拒：

| # | 差异点 | ✅ 正确 | ❌ 错误（会被拒） |
|---|---|---|---|
| 1 | **协议** | `https://` | `http://`（生产） |
| 2 | **末尾斜杠** | `.../callback` | `.../callback/` |
| 3 | **端口** | `https://perf.example.com/feishu/callback` | `https://perf.example.com:443/feishu/callback` |
| 4 | **大小写** | `/feishu/callback` | `/Feishu/Callback` |
| 5 | **www** | `https://perf.example.com/...` | `https://www.perf.example.com/...` |
| 6 | **尾部参数** | 无 | `?from=xxx` |
| 7 | **路径大小写/层级** | `/feishu/callback` | `/feishu/Callback` |

> 💡 **第 3 条最容易中招**：URL 里写不写 `:443` **在浏览器里看起来一样**，
> 但在字符串比较里**是两个不同的值**。**建议一律不写默认端口。**

### 2.5.4 我们这边怎么配（后端 `.env`）

```powershell
# backend/.env —— 与飞书后台的值**逐字一致**
FEISHU_OAUTH_REDIRECT_URIS=https://perf.example.com/feishu/callback
# 开发环境追加（逗号分隔）：
# FEISHU_OAUTH_REDIRECT_URIS=https://perf.example.com/feishu/callback,http://localhost:5180/feishu/callback
```

**后端的白名单是第二道防线**（第一道是飞书后台）：

- 不在 `FEISHU_OAUTH_REDIRECT_URIS` 里的地址 → 后端直接拒绝（400）
- 这道防线防的是**开放重定向** —— 攻击者构造一个带自己域名的 redirect_uri，
  诱导用户授权后被弹到恶意站点

### 2.5.5 ⚠️ 前端有个坑：回调 URL 是**前端页面**，不是后端接口

**路由模式是 `createWebHistory()`**（history 模式，非 hash）——
这意味着回调 URL 必须是**真实的静态路径**，且**服务器要支持 SPA fallback**
（访问 `/feishu/callback` 时直接返回 `index.html`，而不是 404）。

| 环境 | redirect_uri | 说明 |
|---|---|---|
| 开发 | `http://localhost:5180/feishu/callback` | Vite dev server 默认支持 history fallback ✅ |
| 生产 | `https://perf.example.com/feishu/callback` | ⚠️ **Nginx 必须配 `try_files $uri $uri/ /index.html;`**，否则直接 404 |

**为什么回调落在前端而不是后端**：
飞书回调带 `code` + `state` 回来 → 前端拿到后调 `POST /v1/feishu/auth/exchange`
把 code 换成本系统 token。
（**飞书的 code 是一次性的、且只能换一次**，所以必须立刻转发，不能在页面里刷新重试。）

### 2.5.6 配合完成的验证步骤（**飞书侧配完必做**）

配完后按顺序验：

```powershell
# ① 后端能生成授权 URL（不报 503，说明白名单已配）
#    在项目根目录执行：
cd backend
python -c "from app.core.config import settings; print('白名单:', settings.feishu_oauth_redirect_uris)"
```

| # | 检查 | 期望 | 不符合时 |
|---|---|---|---|
| ① | 后端 `.env` 的 `FEISHU_OAUTH_REDIRECT_URIS` 非空 | 非空 | 没配 → 接口 503 |
| ② | 飞书后台「重定向 URL」已添加**同一个**字符串 | 一致 | 不一致 → 用户点同意后看到飞书报错页 |
| ③ | 点「飞书登录」能跳到飞书授权页 | 跳过去了 | 没跳 → 后端 503 或前端没接对 |
| ④ | 飞书页面上**没有**红色报错 | 无报错 | 有报错 → **redirect_uri 没匹配上**（改 2.5.3 逐项核对） |
| ⑤ | 授权后跳回 `/feishu/callback?code=...&state=...` | 跳回来了 | 没跳回 → 飞书后台 redirect_uri 配错 |
| ⑥ | 前端把 code 换成 token 并进系统 | 进系统了 | 没进 → 看**后端**日志（此时飞书侧已通） |

> ⚠️ **只有第 ④ 步能区分「后台没配」和「配置不一致」**——
> 前 ③ 步跳过去了只能说明**后端**白名单 OK，不代表**飞书后台**也 OK。

### 2.5.6.1 ⚠️⚠️ 报 20029 时的**决定性诊断方法**（2026-11-17 实测确立）

> 🚨 **2026-11-17 真机踩坑**：后台明明配了 redirect_uri，
> 真机授权仍报 **20029「重定向 URL 有误」**。
> 本文先前给的「逐项核对 7 个差异点」是**猜测式排查**——
> 实测证明它**不够用**：第 ② 步的核对无法回答「到底配没配上」。

#### 🔑 一行命令定位根因（**取代所有猜测**）

飞书有**官方 API 能直接读出后台配的 redirect_urls**：

```powershell
# 在项目根目录执行
python -c @"
import httpx, json
from backend.app.core.config import settings

tok = httpx.post(
    'https://open.feishu.cn/open-apis/auth/v3/app_access_token/internal',
    json={'app_id': settings.feishu_app_id, 'app_secret': settings.feishu_app_secret},
    timeout=30,
).json()['app_access_token']

r = httpx.get(
    f'https://open.feishu.cn/open-apis/application/v6/applications/{settings.feishu_app_id}',
    headers={'Authorization': f'Bearer {tok}'},
    params={'lang': 'zh_cn'}, timeout=30,
)
app = r.json()['data']['app']
print('应用名    :', app['app_name'])
print('redirect_urls:', app['redirect_urls'])
"@
```

**输出示例（这次踩坑的真实结果）**：

```
应用名    : 小绩
redirect_urls: []          ← 空数组！这就是 20029 的真凶
```

| `redirect_urls` | 结论 |
|---|---|
| `[]`（空） | ⚠️ **后台根本没配上** —— 可能配到了**另一个应用**，或**没点保存**，或**加错了位置**（加在了「事件订阅」而不是「安全设置」） |
| 有值但不含你那条 | ⚠️ **逐字不一致** —— 对照 §2.5.3 的 7 个差异点核对 |
| 含你那条 | ✅ 后台没问题 —— 问题在**客户端发出的 redirect_uri**（查 §2.5.6.2） |

> 💡 **为什么这个方法比「去后台看」更好**：
> 1. **可脚本化** —— 能进 CI、能进巡检脚本；
> 2. **消除歧义** —— 人工在后台可能看错应用（多应用时尤其容易）；
> 3. **能证明「已配好」** —— 而不只是「我以为配好了」。

#### 2.5.6.2 ⚠️ 为什么「去后台看」也可能看错

官方排查文档给的第一步是「**获取报错页面的 URL**，从里面解析 `app_id`」。

⚠️ **实测坑**：报错页面 URL 里的参数名是 **`app_id`**（旧版 `index` 端点的写法），
而官方文档给的新版 `authorize` 端点用的是 **`client_id`**。

⇒ 两个端点参数名不同，**照着报错 URL 里的 `app_id` 去反查应用**，很容易对错。

#### 2.5.6.3 ⚠️⚠️ 关于「参数名不符」的**重要澄清**

排查 20029 时曾怀疑：授权 URL 用了 `app_id=` 而不是官方的 `client_id=`。

**实测结论（浏览器实测，不是推断）**：

| 授权 URL 写法 | 结果 |
|---|---|
| `?app_id=<ID>&redirect_uri=...` | ❌ 20029 |
| `?client_id=<ID>&response_type=code&redirect_uri=...` | ❌ 20029（**同样**） |

⇒ **参数名不是 20029 的触发条件**（两者都报错）。
但**参数名仍然必须改对** —— 官方文档是唯一权威，写错就是错；
且 `response_type=code` 是**必填**，漏了会让飞书无法确定流程。

⇒ **教训**：**不要在同一个错误码上同时假设多个原因** ——
先用一个能区分假设的实验（这里是「读 `redirect_urls` 字段」）把原因**定位**，
再动手改代码。否则很容易「改了一堆，错误依旧，还以为改对了」。

#### 2.5.6.4 ⚠️ 另一个容易误判的现象

排查时曾用「遍历各种 redirect_uri 变体，看哪个不报错」来定位 ——
**这个方法无效**：所有变体（含**必然没配过**的假域名）返回**完全相同**的错误页。

⇒ 飞书在**更早的阶段**就判定出错了，**根本没走到 redirect_uri 匹配**。
所以「换个 redirect_uri 试试」这种试探法在这里**得不出任何结论**。

### 2.5.7 如果 IT 短期内配不了

**不影响前端开发**。可以先按 FS-2 把前端做完，用 mock 测：

#### ⚠️ 实施期踩出的 3 个坑

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| **P5** | ⚠️ **「登录后跳回哪」没有 URL 能带** | 直觉做法是把 `redirect` 拼进 `redirect_uri` 的 query —— **行不通**：飞书做 `redirect_uri` **字符串精确匹配**，多了 `?redirect=...` 就是另一个字符串 → **直接拒绝授权**。而挂在授权 URL 上也不行 —— 飞书**只**透传 `code` + `state` | 改用 **sessionStorage** 带走跳转意图（发起时存，回调时读并清）。同源同标签页可见、关标签页即失效、刷新仍在 —— 恰好匹配 OAuth 跳转的语义 |
| **P6** | ⚠️ **401 全局拦截器会吃掉免登的失败原因** | 通用规则是「非登录请求 401 → 清凭证 + 跳 `/login`」。但 `/feishu/auth/exchange` 失败时用户正**站在回调页**上，被跳走就只剩「闪回登录页」，**没有任何提示** | `isLoginRequest` 扩成 `isLoginLikeRequest`（含 exchange）→ 登录类接口失败**原样抛给页面**，由页面展示可操作提示 |
| **P7** | ⚠️ **回调路由漏标 `public` 会死循环** | 用户此刻**还没有本系统 token**（token 是回调页里用 code 换出来的）。走全局守卫 → 被拦回 `/login` → 「回调 → 踢去登录 → 回调永不发生」 | 回调路由标 `meta.public: true`，且守卫**先判 public 再放行**（顺序也不能反） |

> 💡 **P7 是那种「不跑真机绝对看不出来」的坑** —— 单元测试全绿、路由注册正确，
   > 但真机上就是「点了飞书登录 → 闪回登录页 → 再点再闪」。

### 3.5 ⚠️⚠️ 真机验收踩出的 3 个坑（2026-11-17 免登打通）

> 🚨 **这三个坑，单靠单元测试全绿是发现不了的** —— 契约写错了，
> 但代码「自洽地错着」：参数名错、端点错，测试也跟着错。

#### 三坑全貌（一次真机验收，三次连续失败）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| **P8** | 授权页报 **20029「重定向 URL 有误」** | ① 后台 `redirect_urls` 是**空的**（没保存生效）；② 代码用 `app_id=` 而非官方 `client_id=`，且漏了必填的 `response_type=code` | 后台补配置（见 §2.5.6.1 诊断脚本）+ 改用官方参数名 |
| **P9** | 授权页报 **20029**（改了参数名仍报） | 同上的 ① —— **参数名不是触发条件**（实测 `app_id`/`client_id` 两种写法**都**报 20029） | 用官方 API 读 `redirect_urls` 字段定位（**不要靠猜**） |
| **P10** | 免登失败：**「飞书用户信息获取失败：缺少 user_id」** | 用了**通讯录接口** `/contact/v3/users/{user_id}`（路径里必须有 user_id），而 OAuth 令牌响应**不含 user_id** ⇒ 必然走不通 | 改用**登录用户接口** `/authen/v1/user_info`（不需 user_id，直接返回当前登录用户身份） |

#### 💡 P10 的教训（**最值得记住的一条**）

> **「查询用户 A 的信息」和「查询当前登录用户的信息」是两个不同的接口。**
> 免登场景要的是后者 —— 语义是「我手上的 token 就代表这个人」，
> 所以**根本不需要先知道 user_id**。

⚠️ 官方给通讯录接口加了 `user_id_type=user_id` 参数后，
「路径里的 ID 是哪种 ID」这个坑被盖住了（F1 回归测试就是为此加的），
于是更容易让人以为「通讯录接口也能用于免登」—— **它不能**。

#### ⚠️ 三坑的共同点：**症状都不指向真正的根因**

| 症状 | 看起来像 | 实际是 |
|---|---|---|
| 20029「重定向 URL 有误」 | redirect_uri 字符串没对上 | 后台**压根没配**；或授权 URL 参数名错 |
| 「缺少 user_id」 | 少传了个字段 | **接口选错了** —— 那个接口压根不该用于免登 |

⇒ **排查方法论（比具体修法更重要）**：

1. **先定位，再改代码** —— 用一个能**区分假设**的实验把原因钉死，
   再动手。不要同时假设多个原因（我这次就同时假设了「参数名 / 后台没配 / 末尾斜杠」，
   结果改了一堆代码，错误依旧，还一度以为改对了）。
2. **官方文档是唯一权威** —— 端点路径、参数名、必填项，
   都以文档为准，别凭印象。
3. **契约写错，测试也会跟着错** —— 「自洽地错着」的代码测试全绿。
   ⇒ 关键契约**要么打真实 API 验证，要么照文档逐字比对**。

## 十一、常见卡点与处理

| 卡点 | 现象 | 处理 |
|---|---|---|
| **飞书回调 503** | 端点返回「未配置 Verification Token」 | 配 `FEISHU_BOT_EVENT_TOKEN` / `FEISHU_APPROVAL_WEBHOOK_TOKEN`。**注意：这是刻意设计（宁可不放行）** |
| **飞书回调 401** | Token 校验失败 | 检查是不是 v2.0 信封（token 在 `header` 里，不在顶层）；开了加密策略则 body 是 `{"encrypt": "..."}` |
| **卡片渲染空白** | 飞书里卡片不显示 | JSON 2.0 字段层级错。用飞书卡片调试工具核对；本地加渲染快照测试 |
| **飞书收不到机器人消息** | 事件没进来 | 查：机器人能力是否启用、事件订阅是否配对、**应用可见范围是否覆盖该用户** |
| **免登 `open_id` 解析不到员工** | 换 token 失败 | `GET /v1/feishu/identities/unbound` 看是不是没绑定；用 `open_id` 类型绑定（不是 `user_id`） |
| **同步随机 401** | 组织同步时好时坏 | ⚠️ **多半是 token 串味** —— 检查 user token 有没有写进 `_access_token` |
| **alembic 打到错误的库** | 迁移日志成功但数据没变 | ⚠️ **已知坑**：用绝对路径 `DATABASE_URL`；跑前 `Remove-Item Env:\DATABASE_URL` |
| **PowerShell 环境变量残留** | 上次的 `DATABASE_URL` 影响本次 | 跑前 `Remove-Item Env:\DATABASE_URL` |
| **agent-service 测试报错** | `ModuleNotFoundError: No module named 'app'` | 必须在 `agent-service/` 目录下跑 |
| **飞书权限看着"不通"** | 返回 400 | ⚠️ **先看错误码**：`99992402` = 参数不对（权限是通的）；`99991668/99991672` = 真缺权限 |
