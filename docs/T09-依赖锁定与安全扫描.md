# T09 · 依赖锁定与安全扫描（CI-6）

> 2026-11-24 交付。
> 解决的核心问题：**依赖不可复现 + 无 CVE 视野**。

---

## 一、为什么要「先锁版本、再扫描」

⚠️ **只扫描不锁 = 扫的是个随时会变的快照**

本项目原来的 `requirements.txt` 全是 `>=` 下界：

```ini
fastapi>=0.115
uvicorn[standard]>=0.30
pydantic>=2.7
```

⇒ **CI 每次构建装到的依赖版本都可能不同**。
今天装到安全的 `fastapi 0.115.x`，下周可能装到带 CVE 的 `0.116.0` —— 而你**不知道**它引入了什么。

⇒ 所以顺序是：**先锁版本（让 CI 装的东西固定），再扫描（对固定的东西做安全审计）**。

⚠️ **反过来做更糟**：只扫描不锁 ⇒ 下周重跑结果可能不同 ⇒
给出的是**虚假的安全感**（"上次扫过没问题"）。

## 二、锁版本

### 2.1 生成方式

用 `pip-tools` 从 `requirements.txt` 解析传递依赖：

```bash
python -m piptools compile backend/requirements.txt \
  --output-file backend/requirements.lock.txt \
  --generate-hashes --strip-extras --no-header
```

| 参数 | 作用 |
|---|---|
| `--generate-hashes` | 每个包带 sha256 hash —— **供应链防篡改保证** |
| `--strip-extras` | 去掉 `uvicorn[standard]` 的 extras 标记（它只影响 extras 解析，不影响锁定） |
| `--no-header` | 不写 pip-tools 自己的命令头（里面会带上本机的 index-url） |

产出：

| 文件 | 包数 | 行数 |
|---|---|---|
| `backend/requirements.lock.txt` | 45 | 1086 |
| `agent-service/requirements.lock.txt` | 27 | — |

### 2.2 ⚠️ 踩到的坑：本地镜像源被写进 lock 文件

⚠️ **真实发生过**。

`pip-tools` 会把**本机 pip 的配置**原样写进文件头。本地开发者配了清华镜像：

```ini
--index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

⇒ **CI 也会走这个源**：

- CI 速度被拖慢（境外访问国内镜像）；
- 镜像挂了 ⇒ **整个 CI 挂掉**（而它本该用官方源）；
- 本地环境配置泄漏进仓库。

**处置**：生成后**手工剥掉** `--index-url` / `--extra-index-url` / `--trusted-host` / `--only-binary` 四类行，并写清原因。

> hash 是**内容哈希**，与从哪个源下载无关 ⇒ 剥掉源配置不影响完整性保证。

⚠️ `--only-binary :all:` 也不能留 —— 它会让**平台专属的 wheel**（`colorama` 在 Windows、`tzdata` 在部分 Linux 镜像）因为没有对应 wheel 而装不上。

### 2.3 CI 改用 lock 安装

```bash
pip install --require-hashes -r backend/requirements.lock.txt
```

⚠️ `--require-hashes` 强制 pip **校验每个包的 hash** ⇒ 供应链攻击者无法在 PyPI 上投毒同名版本。

✅ **已本地验证**（`--dry-run`）：Windows 平台所有 wheel 齐全，hash 校验无冲突。

## 三、扫描

### 3.1 后端 · `pip-audit`

```bash
pip-audit -r backend/requirements.lock.txt --progress-spinner off --desc off
```

⚠️ **扫 lock 文件，不扫整个环境**

这是本次调研的**关键发现**：

```bash
$ pip-audit                     # 扫整个环境
Found 12 known vulnerabilities in 1 package
Name Version ID              Fix Versions
pip  24.3.1  PYSEC-2026-1795 25.3
pip  24.3.1  PYSEC-2026-1796 26.0
...（12 条全是 pip 自己）
```

⇒ 扫环境会把 **pip 工具自身的 CVE** 也算进来，而 pip **不是项目依赖** ⇒ 噪音淹没信号。

```bash
$ pip-audit -r backend/requirements.lock.txt
No known vulnerabilities found
```

⇒ **项目依赖本身是干净的**（这也是能把门槛设成硬门槛的前提）。

⚠️ **Windows 编码坑**：`pip-audit` 按系统默认编码读文件，本机是 GBK，读 UTF-8 的 lock 文件会抛
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x80`。
⇒ CI（Ubuntu）无此问题；本地脚本已通过 `PYTHONUTF8=1` 环境变量解决。

### 3.2 前端 · `npm audit`

```bash
npm audit --audit-level=high
```

**修复前：12 个漏洞（3 moderate + 9 high）**，全在 `vite` / `vue` / `postcss` / `source-map-js` / `nanoid` / `follow-redirects` 的传递依赖链上。

用 `npm audit fix`（**不带 `--force`**）修复 —— 只升级能安全升的：

| 包 | 修复前 | 修复后 | 是否破坏性 |
|---|---|---|---|
| `vite` | 6.4.3 | **6.4.6** | ❌ 否 |
| `vue` | 3.5.41（漏洞区间内） | **3.5.46** | ❌ 否 |
| `postcss` / `source-map-js` / `nanoid` / `follow-redirects` | 漏洞版 | 已修 | ❌ 否 |
| `vue-tsc` | 2.2.12 | 2.2.12（不变） | — |

✅ **`package.json` 零改动** —— 修复全部发生在 `package-lock.json`（102 增 / 104 删）。

**修复后：3 个 moderate，0 个 high**。剩下的 3 个全在 `vue-tsc` → `minimatch` 链上，修它需要把 `vue-tsc` 升到 `3.3.14`（**破坏性升级**，会连带改 TypeScript 版本要求）⇒ **故意不阻断**，作为已知待办。

✅ **已验证**：`npm test` 337 passed / 0 failed；`npm run build`（含 `vue-tsc --noEmit`）成功。

## 四、护栏

新增 `backend/app/tests/test_dependency_lock_guard.py`（10 例），守住四条线：

| # | 断言 | 防的是什么 |
|---|---|---|
| 1 | 每个服务都有 lock 文件 | 有人删了 / 新增服务忘了生成 |
| 2 | **lock 文件不含 `--index-url` / `--extra-index-url` / `--trusted-host`** | ⭐ **本地镜像源混进 CI**（本次真实踩过） |
| 3 | lock 文件不含 `--only-binary` | 平台专属 wheel 装不上 |
| 4 | **每个包都有 sha256 hash** | 供应链防篡改保证被削弱 |
| 5 | lock 版本满足 `requirements.txt` 的下界 | lock 与 requirements 漂移 |
