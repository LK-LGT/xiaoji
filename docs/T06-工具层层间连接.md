## 二、逐层说明

### 2.1 L2 → L3：既有通道，**完全不动**

**这是最重要的一点：工具层不需要改 L2→L3 的连接方式。**

| 项 | 现状 | 工具层是否改 |
|---|---|---|
| 认证头 | `Authorization: Bearer <AGENT_SHARED_SECRET>` | ❌ 不改 |
| 依赖函数 | `require_service_token()` | ❌ 不改 |
| HTTP 客户端 | `review_service.AgentClient` | ⚠️ **只加一个 `qa()` 方法** |
| 既有端点 | `/v1/agent/draft` `/v1/agent/rating` `/v1/agent/evidence-check` | ❌ 不动 |

`review_service.AgentClient` 现有代码（`review_service.py:125`）：

```python
    def draft(self, payload: dict[str, Any]) -> dict[str, Any]:
        """调 POST /v1/agent/draft。失败抛异常，由调用方降级。"""
        with httpx.Client(timeout=30.0) as client:
            resp = client.post(
                f"{self.base_url.rstrip('/')}/v1/agent/draft",
                json=payload,
                headers=self._headers(),
            )
            resp.raise_for_status()
            return resp.json()
```

Step 4 只在旁边加一个同构的方法（`review_service.py`）：

```python
    def qa(self, payload: dict[str, Any]) -> dict[str, Any]:
        """调 POST /v1/agent/qa。失败抛异常，由调用方降级。"""
        with httpx.Client(timeout=30.0) as client:
            resp = client.post(
                f"{self.base_url.rstrip('/')}/v1/agent/qa",
                json=payload,
                headers=self._headers(),
            )
            resp.raise_for_status()
            return resp.json()
```

> ⚠️ **`draft()` 不动** —— 它跑通了、测试全绿，改它就是引入风险。
> 工具层是**新增一条平行通道**，不是改造既有通道。

### 2.2 L3 → L2：新增通道（★ 核心）

这是工具层**唯一新增的层间连接**。

```
L3 (agent-service)  ──HTTP POST──▶  L2 (backend)
   POST {L2}/v1/agent-tools/{tool_name}
   Authorization: Bearer <工具令牌>
   Body: {"period": "202611", ...}   ← 无 employee_id
```

**三个设计要点**：

| 要点 | 做法 | 为什么 |
|---|---|---|
| **地址不来自请求体** | `AGENT_TOOL_BASE_URL` 环境变量 | 防 SSRF —— 否则攻击者能让 L3 去调任意地址 |
| **身份不来自请求体** | 工具令牌里的 `sub` | 边界 B3 —— agent 查别人 |
| **工具名在路径里** | `/v1/agent-tools/get_metric_values` | 网关按路径分发，模型选不了别的端点 |

**L3 侧的 handler**（`agent-service/app/tools.py`）：

```python
def http_handler(base_url: str, token: str, name: str) -> Callable[[dict[str, Any]], dict[str, Any]]:
    def handler(args: dict[str, Any]) -> dict[str, Any]:
        with httpx.Client(timeout=8.0) as client:
            response = client.post(
                f"{base_url.rstrip('/')}/v1/agent-tools/{name}",
                json=args,
                headers={"Authorization": f"Bearer {token}"},
            )
            response.raise_for_status()
            body = response.json()
            if body.get("code") != 0:
                raise RuntimeError(body.get("message") or "工具返回错误")
            return body.get("data") or {}
    return handler
```

> ⚠️ **`httpx` 是新依赖**：`agent-service/requirements.txt` 目前只有
> `fastapi / uvicorn / pydantic`。需要加 `httpx>=0.27`，
> **或者**改用标准库 `urllib.request`（零依赖兜底方案，见 T03 §2.1）。

**循环调用会怎样**（关键 —— 这不是一次调用，是多轮）：

```
L2  ──▶ L3  POST /v1/agent/qa
              body: { question, context, tool_token, allowed_tools }
L3  ──▶ L2  POST /v1/agent-tools/get_metric_values   ← 工具调用 1
              body: { period: "202611" }
L2  ──▶ L3  200 { code:0, data:{ metrics:[...] } }
L3  ──▶ L2  POST /v1/agent-tools/get_evidence        ← 工具调用 2
              body: { period: "202611", usage: "scoring" }
L2  ──▶ L3  200 { code:0, data:{ evidence:[...] } }
L3  ──▶ L2  200 { answer, citations, tool_calls }      ← 最终答案
```

**L2 侧是同步阻塞的**：L2 发一个 HTTP 请求给 L3，L3 在这个请求的处理期间
回头调 L2 的另一个端点。这在 FastAPI 里是**允许的**（不同 worker / 不同线程池），
但有两个必须注意的点：

> ⚠️ **数据库会话不能跨层复用**。
> L2 的 `/v1/agent/qa` 处理过程中会调 L3，L3 又调回 L2 的 `/v1/agent-tools/*`。
> 这**不是**同一个请求，所以 `Depends(get_db)` 会开**新的 Session** —— 这是对的，
> 但意味着：工具查询看到的可能是「比外层查询稍晚」的快照。
> 对本场景（读同一批已确认数据）无影响，但**将来若工具涉及写操作就是死锁风险**。
> 这也是「工具层只读」这条边界的**工程价值**：它把死锁风险挡在外面。

> ⚠️ **超时预算要叠得上**。
> `AgentClient.qa()` 用 30 秒；L3 的 `ToolUsingAgent.total_timeout_s = 30`；
> 工具单次 8 秒；`max_tool_calls = 8`。
> 最坏情况：8 次 × 8 秒 = 64 秒 > 30 秒。
> **所以 T03 的 `ToolUsingAgent` 必须真的实现总超时**（`total_timeout_s`），
> 否则外层 30 秒先超时，L3 还在跑 —— 白白消耗资源。
> 这是 T03 §2.4 里 5 处修正的第 1 条。

### 2.3 L1 → L2：走既有通道，**只加一个端点**

前端调用形态完全不变：

```typescript
// frontend/src/api/http.ts:74
export const http = axios.create({ baseURL: '/api', timeout: 15000 })
// Vite 代理：/api/xxx → /v1/xxx
```

新增的端点是 `POST /v1/qa/ask`：

```
前端  ──POST /api/qa/ask──▶  Vite rewrite  ──▶  POST /v1/qa/ask
     Authorization: Bearer <登录令牌>
```

> ⚠️ **但目前没有任何前端代码调用 `/qa/`**（本次核对确认）。
> 也就是说：`/v1/api/qa/query` 这个接口**前端也没在用** ——
> 它是给「未来做问答页」预留的。
>
> 这意味着 Step 4 完成后，**还需要一个前端页面**才能让用户真正用上。
> T03 Step 4 的验收是「curl 能通」，前端页面是**后续独立任务**。

### 2.4 L0 ↔ 工具层：**不连接**

边界 B1 明确：Agent 不得直接触达 L0。

| 场景 | 谁负责 | 工具层的角色 |
|---|---|---|
| 飞书组织架构同步 | `organization_sync.py` | ❌ 不参与 |
| 飞书审批回流 | `feishu_approval_sync.py` | ❌ 不参与 |
| 考勤同步 | `attendance_sync.py` | ❌ 不参与 |
| IM 通知推送 | `feishu_bot.py` | ❌ 不参与 |

**如果将来要加「飞书机器人问答」**（`02-问答功能设计.md` §7 已提到），
正确形态是：

```
飞书用户 @机器人
   → L0 收到消息
   → L0 调 L2 的 POST /v1/qa/ask     ← L2 签发工具令牌
   → L2 调 L3
   → L3 调 L2 的 /v1/agent-tools/*   ← 工具调用
   → L3 返回答案
   → L2 返回给 L0
   → L0 用飞书机器人回消息
```

**注意**：即使做飞书机器人，**L0 也不直接调 L3** —— L0 只是消息的出入口，
业务编排始终在 L2。这是五层架构的纪律。

### 2.5 L4：模型层在循环的**最内层**

```
L3 的循环：
  ├─ complete_with_tools(messages, tools)   ← 调 L4
  │    └─ L4 可能返回 tool_calls
  ├─ registry.call(...)                     ← 调 L2
  ├─ 把结果追加进 messages
  └─ 再调 L4 ...（直到 L4 返回最终答案）
```

**L4 完全不知道 L2 的存在** —— 它只看到 `tools` 的 JSON Schema。
这是「模型不可信」原则的技术基础：**模型能做的事，被 schema 限死。**

## 三、关键问题：工具令牌为什么不经过前端？

这是一个容易搞错的设计点。

### 3.1 两种可能的链路

**❌ 错误链路（工具令牌经前端）**

```
前端 → L2: 问 "我绩效怎么样"
前端 → L2: 要工具令牌
前端 → L3: 带工具令牌问   ← 令牌暴露给浏览器
L3 → L2: 带工具令牌调工具
```

**问题**：
1. 令牌出现在浏览器 Network 面板里
2. 令牌一旦泄漏，攻击者可以直接调工具（虽然只有 5 分钟窗口）
3. 令牌被前端代码看到 → 前端成了令牌分发方，增加泄漏面

**✅ 本方案链路（工具令牌只在 L2↔L3 之间流动）**

```
前端 → L2: 问 "我绩效怎么样"（带登录令牌）
  L2: 鉴权 → 解析权限范围 → 【内部签发工具令牌】
  L2 → L3: 问 + 工具令牌（服务端到服务端）
    L3 → L2: 调工具（带工具令牌）
  L3 → L2: 答案
  L2 → 前端: 答案（不含令牌）
```

**好处**：
1. 工具令牌**从不离开服务端**
2. 令牌由 L2 自己签、自己用 —— 攻击者拿到登录令牌也只能问问题，
   而工具令牌是 L2 在**每次请求内**现签的，用完即弃
3. 令牌的有效期（≤5 分钟）与单次请求绑定，不存在「发一张长期通行证」

### 3.2 两类令牌的对照

| | 登录令牌 | 工具令牌 |
|---|---|---|
| 签发方 | L2 (`routes/auth.py::_generate_token`) | L2 (`services/agent_tool_token.py::issue_agent_tool_token`) |
| 密钥 | `settings.auth_token_secret` | `settings.agent_tool_secret`（**独立**） |
| 有效期 | 7 天 | **≤ 5 分钟**（硬钳制 300s） |
| 携带者 | 浏览器 → L2 | **仅 L2 → L3** |
| 载荷 | `sub/username/ver/iat/exp` | `sub/task/allow/scope/iat/exp` |
| 用途 | 证明「你是谁」 | 证明「你可以查什么」 |
| 编码 | `base64url(payload).hmac-sha256` | **同上**（刻意一致，便于审计） |

> ✅ **编码风格刻意与 `auth.py:396` 的 `_generate_token` 保持一致**
> （`base64.urlsafe_b64encode` + `hmac.sha256` + `f"{encoded}.{signature}"`）。
> 理由不是省事，而是**运维审计时看两种令牌格式一致，不用怀疑是不是两套机制**。

## 四、鉴权链条全图

一次完整问答请求，经过的**全部**鉴权检查：

```
【第 1 层】前端 → L2 /v1/qa/ask
  dependencies.get_current_user(authorization)
    → 解签名 + 查库 + 校验离职/禁用
    → 失败：401
  ↓
【第 2 层】L2 内部：范围推导
  qa_permission.resolve_scope(current_user, task_id, target_employee_id, db)
    → access_control.build_access_context(db, current_user)
    → 决定 employee_ids / department_ids / allowed_tools
    → 越权目标：403
  ↓
【第 3 层】L2 → L3 /v1/agent/qa
  require_service_token(authorization)
    → hmac.compare_digest 与 AGENT_SHARED_SECRET 比对
    → 失败：401
  ↓
【第 4 层】L3 → L2 /v1/agent-tools/*
  agent_tool_ctx(authorization)
    → verify_agent_tool_token：签名 + exp
    → 失败：401（签名错）/ 403（过期）
  ↓
【第 5 层】L2 工具层：白名单
  assert_tool_allowed(ctx, tool_name)
    → tool_name 必须在这个令牌的 allow 里
    → 失败：403
  ↓
【第 6 层】L2 工具层：权限二次复核  ★ 关键
  _assert_scope_permitted(ctx, db)
    → access_control.can_view_score_of(ctx.employee_id)
    → 失败：403
  ↓
【第 7 层】L2 工具层：业务校验
  周期格式 / 任务存在 / 快照存在 / k-匿名
    → 失败：200 + 结构化错误（不是 500）
```

**第 6 层为什么必要**：令牌里的 `allow` 是**能力声明**，
但**权限判定必须回到 `access_control`** —— 它才是单一事实源。
令牌可能因为业务逻辑变更而过期（比如员工换了岗），access_control 会立刻反映。

> ⚠️ **这正是 T02 的 C2 冲突项说的**：
> 「令牌 `sub` 之外的权限**必须回到 `access_control` 复核**，不能只信令牌里的 `allow`」。

```
 │                      │                                 │                │
 │◀─200 {answer, citations, data_quality}───────────────│                │
 │                      │                                 │                │
```

**注意第 ⑨ 步**：审计写的是**每一次**工具调用（2 次调用 = 2 条记录），
不是「一次问答 = 1 条」。

## 七、启动与配置

### 7.1 环境变量

```bash
# backend/.env
AGENT_TOOL_SECRET=<64位随机hex>        # 必填，32位下限 + 弱密钥黑名单
AGENT_TOOL_TOKEN_TTL_SECONDS=300       # 可选，硬钳制 [30, 300]
AGENT_SHARED_SECRET=<既有>             # 既有，L2↔L3 通道

# agent-service/.env
AGENT_SHARED_SECRET=<同上，必须一致>    # 既有
AGENT_TOOL_BASE_URL=http://127.0.0.1:8000  # 新增，L3→L2 的网关地址
MODEL_MODE=echo                        # 既有；真模型时改 openai
```

### 7.2 启动顺序

```bash
# 终端 1 —— 先起 L2（工具网关在这里）
cd backend
uvicorn app.main:app --port 8000

# 终端 2 —— 再起 L3（要调 L2 的工具）
cd agent-service
python -m uvicorn app.main:app --port 8800

# 终端 3 —— 前端
cd frontend
npm run dev
```

> ⚠️ **顺序重要**：L3 启动时**不检查** L2 是否可达（fail-fast 只对 `AGENT_SHARED_SECRET` 做）。
> 因为 L3 可能比 L2 先起 —— 工具调用失败会**降级**而不是崩溃（边界 B4）。
>
> 但 **`AGENT_TOOL_SECRET` 没配时 L2 会启动失败** —— 这是刻意的：
> 宁可不提供工具能力，也不要裸奔的网关。

### 7.3 本地开发的安全网

```bash
# backend/.env（仅本机开发）
AGENT_TOOL_SECRET=<64位随机hex>   # 至少要满足长度校验
```

> ⚠️ agent-service 侧有 `AGENT_ALLOW_INSECURE=true` 逃生舱（跳过 `AGENT_SHARED_SECRET` 校验），
> 但它**只作用于 L2↔L3 的服务令牌**，不涉及工具令牌。
> 工具令牌**没有逃生舱** —— 未配置 `AGENT_TOOL_SECRET` 时 L2 直接起不来。

## 八、一句话总结

> 工具层只新增**一条**层间连接：**L3 → L2 的只读工具网关**。
>
> - **L2 → L3** 复用既有服务令牌通道（只加一个 `qa()` 方法）
> - **L1 → L2** 复用既有登录令牌通道（只加一个 `/v1/qa/ask` 端点）
> - **L0** 完全不碰（边界 B1）
> - **L4** 只见 schema，不见数据源
>
> 而**工具令牌只在 L2↔L3 之间流动，从不经过浏览器** ——
> L2 在每次请求内现签现用，用完即弃。
