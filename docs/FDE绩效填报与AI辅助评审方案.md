# FDE 岗位绩效填报与 AI 辅助评审方案

> 依据：《电商女装 FDE 绩效考核方案》五维度 + 加减分规则
> 扩展对象：在现有员工绩效智能体之上，扩展 FDE 岗位的填报评审能力
> 权限底座：复用飞书组织架构（通讯录同步 + OAuth 免登 + 角色推导）
>
> **第一性原则（继承框架既有四条不可破原则）**
> 1. **AI 只出线索，不出分数。** AI 质检的唯一产物是「风险标签 + 待核实清单」，
>    分数 100% 由主管或人事主管人工写入。AI 的任何输出都不得进入 `Score` 表。
> 2. **能量化的由系统自动拿，不可量化的绑定可核验证据。**
>    系统客观数据（响应时效、周报提交、工单、模板沉淀、上线记录）自动回填且**员工不可编辑**；
>    质量类、沟通协调类内容由员工填写 + 强制附证据。
> 3. **每项得分必须有可回溯的依据来源。** 分数 ← 依据 ← 证据/客观数据，两者都不可为空。
> 4. **飞书是入口与消息层，不是事实源。** 组织架构事实源 = 飞书通讯录；
>    绩效数据事实源 = 本系统 L2。飞书卡片只做采集通道。

---

## 〇、为什么 FDE 不能照搬现有「自评表单」

FDE 的工作形态决定了它与现有岗位模型的冲突点：

| 冲突点 | 现状（数值型考核） | FDE 现实 |
|---|---|---|
| 产出形态 | 指标有明确 target 值，直接算达成率 | 需求对接、方案设计、排期协调、排障、培训、风险预警 —— **过程型、无自然数值口径** |
| 成果证据 | 指标值本身就是证据 | 「协调了 3 个部门排期」无法用数字表达，但**过程材料**（会议纪要、排期表、验收记录）可核验 |
| 现有自评表单 | 单个 `self_comment` 自由文本（10~2000 字） | 一个自由文本框无法承载 FDE 的多条工作，**也无法审计**（无法定位到「哪条工作、哪个维度」） |
| AI 预审 | `ai_review_engine` 只对**计划**和**成果**做规则复核，无「工作条目」粒度 | 需要新增**条目级**预审，且要能判断条目与五维度的对应关系 |

**结论**：FDE 需要的是 **「工作条目（work item）+ 结构化字段 + 条目级证据」** 的填报模型，
而不是把自由文本框换个名字。本方案的核心设计是把「一件事」作为最小填报单元，
每条工作条目自带维度归属、证据、影响、卡点，AI 在条目粒度上做预审。

## 一、FDE 绩效填报表单结构

### 1.1 设计原则：约束表达形式，而非禁止文本

不禁止写文字，但要求文字**回答四个固定问题**，且每个问题都有**结构化约束**：

| 原则 | 落地方式 |
|---|---|
| 文本必须挂靠到具体工作条目 | 不存在「整篇自由文本」，只有条目内的四个定长字段 |
| 每个字段问一个明确问题 | 「做了什么事 / 交付物 / 业务影响 / 卡点风险」四问分离 |
| 可枚举的尽量枚举 | 工作类型、协作方、影响对象类型等用下拉，员工不写分类词 |
| 影响必须可判断大小 | 影响等级用「量级 + 受影响范围」半结构化，不写「显著提升」 |
| 证据是必填门槛 | 条目无证据无法提交（系统级拦截，不是提醒） |

### 1.2 表单整体结构

```
FDE 绩效填报
├── A. 系统自动回填区（只读，员工不可编辑）★ 自动抓取
├── B. 工作条目填报区（员工填写）★ 核心
│    ├── B1. 基础信息（枚举为主）
│    ├── B2. 四问内容（受约束文本）
│    └── B3. 证据挂载（系统内链接 + 附件）
├── C. 自评补充区（受限文本，≤300 字，仅用于"整体说明/无法归因的说明"）
└── D. 自评打分（1-5，仅作参考，不进算分集）
```

> **D 区的重要约定**：沿用现有 `self_review_service` 的 `self_score` 语义 ——
> 自评分**只作为主管打分的对照参考**，不进入算分集。这与 `distribution_qc` 的
> 「强制分布仅作参考」是同一条边界。

### 1.3 A 区：系统自动回填区（只读）

员工打开表单即自动生成，字段带「系统数据 · 不可编辑」标识，附数据截至时间（`as_of`）。

> **「可否进算分集」列的口径**：FDE 五维度全部是 `manager_review` + `narrative`
> ⇒ **客观数据本身不直接折算分数**（见 §2.5.3）。本列表示「该数据是否被允许进算分集」
> （由 HR 在 `DataSourcePolicy` 配置），**不是**「FDE 当前会不会用它算分」。
> 实际作用是：**作为主管打分时的依据锚点**。

| 字段 | 数据来源 | 采集方式 | 对应维度 | 允许进算分集 | FDE 实际作用 |
|---|---|---|---|---|---|
| 周报提交及时率 / 逾期次数 | 飞书周报文档（§1.7） | 变更检测 + 抓正文 | 智能体搭建交付度 | ✅ | 打分依据锚点 |
| 月报提交情况 | 飞书月报文档 | 同上 | 智能体搭建交付度 | ✅ | 打分依据锚点 |
| **周报风险暴露次数** | 周报「风险/卡点」段解析 | 解析器 | **对上汇报与透明度** | ✅ | **该维度主要依据** |
| **周报求助次数 / 未响应数** | 周报「需要支持」段 + 工单 | 解析器 + 工单 | **对上汇报与透明度** | ✅ | **该维度主要依据** |
| 需求响应时效中位数 / 超时单数 | 工单系统 | 定时任务 | 智能体搭建交付度 | ✅ | 打分依据锚点 |
| 故障排障平均响应时长 / 未按时闭环数 | 工单系统 | 定时任务 | 智能体效果与完善度 | ✅ | 打分依据锚点 |
| 智能体上线数 / 迭代版本数 | 发布记录 | 定时任务 | 智能体搭建交付度 | ✅ | 打分依据锚点 |
| 模板/方案沉淀数 | 知识库文档目录快照 | 定时任务 | AI专业度 | ✅ | 打分依据锚点 |
| 培训场次 / 参训人数 | 培训签到记录 | 定时任务 | 跨部门沟通协作 | ⚠️ 建议仅参考 | 打分依据锚点 |
| 跨部门协作方覆盖数 | 工单/审批参与方去重 | 定时任务 | 跨部门沟通协作 | ✅ | 打分依据锚点 |
| 风险预警上报条数 | 预警记录 | 定时任务 | 智能体效果与完善度 | ✅ | 打分依据锚点 |
| 飞书审批实例数（发起） | `feishu_approval_sync` | 已实现 | 跨部门沟通协作 | ⚠️ 仅参考 | 打分依据锚点 |
| 考勤异常 | `attendance_sync` | 已实现 | — | ❌ 永不扣分（沿用决策②） | 仅展示 |

**回填硬规则**：

1. 所有自动回填字段 `usage = reference_only` 或 `scoring` **由 HR 在数据源策略里配置**
   （复用 `data_source_service` 的 `DataSourcePolicy`），**员工无写权限**（前端不渲染输入框，
   后端 `Employee` 角色校验拒写）。
2. 每条回填带 `as_of`（数据截至时间），迟到数据重跑时**追加留痕不覆盖**（沿用
   `evidence_service` 的 `source_ref` 幂等键设计）。
3. 回填值为 0 或缺失时**显式展示"未采集到"**，不能静默显示 0 —— 静默 0 会被员工
   误解为"我表现差"，是投诉高发点。

### 1.4 B 区：工作条目填报区（核心）

每个条目对应**一件具体的事**。建议每期 3~8 条，上限 12 条（避免变成日志）。

#### B1 基础信息（以枚举为主）

| 字段 | 类型 | 取值 | 说明 |
|---|---|---|---|
| `work_type` | 单选枚举 | 需求对接 / 方案设计 / 协调排期 / 故障排障 / 业务培训 / 风险预警 / 智能体搭建 / 智能体优化 / 其他 | 枚举而非自由文本，避免分类词污染 |
| `dimension` | 单选枚举（联动） | 智能体搭建交付度 / 智能体效果与完善度 / AI专业度 / 对上汇报与透明度 / 跨部门沟通协作 | 由 `work_type` 联动推荐，员工可改；**每期每维度至少 1 条**（否则该维度无依据，主管只能凭印象打分） |
| `related_agent` | 关联智能体 | 下拉（从智能体台账选） | 支撑「智能体搭建交付度」维度的实体锚点 |
| `collaborators` | 多选 | 从飞书部门树选（可多选） | 支撑「跨部门沟通协作」；**自动回填区会给出去重后的实际协作方**供比对 |
| `period_start` / `period_end` | 日期区间 | — | 与周期比对，识别「跨期」条目 |

#### B2 四问内容（受约束文本）

这是替代「自由大文本」的核心。每个字段长度上限固定、必填规则明确。

| 字段 | 标签 | 长度 | 必填 | 校验规则（系统级） |
|---|---|---|---|---|
| `what_done` | 做了什么事 | 20~200 字 | ✅ | 不得为空；命中空洞词表 → 阻断提交（见 §2.1）；须包含**至少 1 个具体动作动词 + 1 个具体对象** |
| `deliverable` | 交付物 / 证据链接 | 枚举 + 链接 | ✅ | 交付物类型单选（方案文档 / 排期表 / 会议纪要 / 代码或配置 / 上线记录 / 培训材料 / 故障复盘 / 预警报告 / 其他）+ **至少 1 条可点开链接或系统内附件 ID** |
| `business_impact` | 业务带来什么影响 | 15~150 字 | ✅ | 影响等级单选（高/中/低）+ 影响对象单选（GMV / 人效 / 履约时效 / 转化率 / 售后 / 其他）+ 一句话说明；**不得只写"提升了效率"** |
| `blocker_risk` | 遇到的卡点风险 | ≤150 字 | ⚠️ 条件必填 | 若 `work_type` ∈ {需求对接, 协调排期, 故障排障, 风险预警} **则必填**；其余可填「本期无卡点」一键选项（避免为填而填） |

**"卡点风险"是 FDE 岗位的关键设计**：FDE 的价值很大一部分体现在「提前暴露并推进解决卡点」。
把它设为条件必填，同时用「本期无卡点」选项防止应付式填报。

#### B3 证据挂载

| 证据类型 | 说明 | 校验 |
|---|---|---|
| 系统内证据 | 从智能体台账、工单、发布记录、审批实例中**直接引用**（带 ID） | ✅ 优先，自动校验存在性与归属 |
| 飞书文档链接 | 飞书云文档/表格/多维表格链接 | ✅ 格式 + 域名白名单校验 + **可选可达性探测** |
| 附件 | 上传文件（≤ 20MB/个，≤ 10 个/条） | ✅ 落 `Evidence` 表，带 hash |
| 外部链接 | 钉钉/其他系统/看板 | ⚠️ 仅提示不阻断（很多是内网地址，系统探测不到） |

**证据落库约束**（复用 `Evidence` 表）：

- `usage` 取值：`scoring`（可作结论支撑）/ `reference_only`（仅参考）
- `visibility`：默认 `share_with_manager`，**员工必看**（主管打分依据要能被员工看到）
- `status`：`pending` / `approved` / `rejected`
- `as_of`：录入时间，**永久留存**
- 引用即产生 `Evidence` 行 + `source_ref` 幂等键 —— 同一链接重复提交不产生重复行

### 1.5 C 区：自评补充区

| 字段 | 长度 | 用途 |
|---|---|---|
| `overall_statement` | ≤300 字 | 仅用于：本期整体说明、**无法归因到具体条目的补充**、需申请调整目标值的理由。**不重复已有条目内容**（AI 会检查重复度） |
| `goal_adjust_request` | 结构化 | 若认为目标值本身不合理，在此提出（走 HR 目标调整流程，**不在本表内改目标**） |

### 1.6 填报负担控制（避免过于繁琐）

| 控制手段 | 具体做法 |
|---|---|
| 条目数上限 | 3~8 条常规，12 条硬上限 |
| 模板预填 | 提供 6~8 条 FDE 常用条目模板（"XX 需求对接上线"、"线上故障排查闭环"），一键带入 |
| 草稿自动保存 | 飞书卡片会话 + Web 端双通道草稿（复用 `bot_session` 机制） |
| 证据就近选 | 系统内证据一键挂载，不要求员工自己找链接 |
| 客观数据代填 | 员工不用自己统计周报次数、响应时长 —— 系统算好 |
| 条件必填而非全必填 | 只有卡点风险和交付物是硬门槛 |
| 移动端友好 | 飞书卡片填写；Web 端作为复杂补录兜底（沿用 D3 双轨决策） |

**预估填写时长**：单条目约 3~5 分钟（打字 1.5 分钟 + 选证据 1.5 分钟 + 选枚举 1 分钟），
8 条条目 ≈ **30~40 分钟**。对比现状：写一篇 1000 字自评 ≈ 25 分钟但**无结构、无证据、不可审计**。

### 1.7 周报 / 月报：员工在飞书上填，系统自动回收

> **岗位决定**：FDE 岗位**不要求日报**，只保留**周报 + 月报**。
> 员工在**飞书**填写（本系统不重复造一套填报表），系统自动回收并结构化。

#### 1.7.1 定位：周报月报是「证据流」，不是「填报项」

**这是整个设计能否跑通的关键。** 主管不可能逐条读周报月报原文 —— 
10 人 × 4 周 = 40 份周报 + 10 份月报。所以：

```
❌ 主管逐条读 50 份周报月报 → 看不过来 → 放弃 → 凭印象打分
✅ 系统把 50 份压成 10 行聚合表 → 主管看表 → 只看异常行 → 只读被过滤出的那几份
```

| 数据层 | 频次 | 谁看 | 作用 |
|---|---|---|---|
| **原始周报/月报** | 高频 | ❌ 主管从不逐条看 | 留痕 + 参与 AI 预审 |
| **周期聚合表** | 每期 1 行/人 | ✅ 主管看这个 | 客观可算的统计 + 异常标记 |
| **工作条目** | 每期 3~8 条/人 | ✅ 主管看这个 | 解释工作值多少分 |

**周报月报负责「证明干了什么」，工作条目负责「解释值多少分」。两件事分离。**

#### 1.7.2 采集路径（飞书侧）—— ★ 首选：飞书原生「汇报」模块

飞书工作台里的 **周报** / **汇报** 应用就是原生「汇报」模块（`oa.feishu.cn/report`），
**有正式的只读 API**，比抓文档干净得多：

| 接口 | 方法 | 路径 | 用途 |
|---|---|---|---|
| 查询任务 | `POST` | `/open-apis/report/v1/tasks/query` | **拉取已提交的周报/月报记录 + 表单字段值** |
| 查询规则 | `GET` | `/open-apis/report/v1/rules/query` | 列出汇报规则（周报模板定义） |
| 移除规则看板 | `POST` | `/open-apis/report/v1/rule_views/remove` | 管理类，用不到 |

**权限**：`report:task:readonly`（查看汇报任务）+ `contact:user.employee_id:readonly`（取 user_id，仅自建应用）

**查询任务返回的关键字段**：

```json
{
  "items": [{
    "task_id": "6969507459119693826",
    "rule_id": "6894419345318182932",
    "rule_name": "FDE周报",
    "from_user_id": "ou_xxx",
    "from_user_name": "张三",
    "department_name": "FDE组",
    "department_ids": ["dept_xxx"],
    "commit_time": 1622714908,
    "to_user_ids": ["ou_yyy"],
    "to_user_names": ["李四"],
    "form_contents": [
      {"field_id": "f1", "field_name": "本周进展", "field_value": "..."},
      {"field_id": "f2", "field_name": "风险/卡点", "field_value": "..."},
      {"field_id": "f3", "field_name": "需要支持", "field_value": "..."}
    ]
  }],
  "has_more": false
}
```

> **★ 这个接口的五个优势**：
> 1. **`form_contents` 是结构化的**（字段名 + 字段值），**不需要写文档解析器**（N18 可省）
> 2. **自带 `commit_time`** → 提交及时性**直接就是权威数据**，不用猜文档更新时间
> 3. **自带 `rule_name` / `rule_id`** → 周报模板是**飞书原生配置**，HR 在飞书后台改模板，
>    **系统零改代码自动跟随**
> 4. **自带 `from_user_id` / `department_ids`** → 归属判定**天然准确**，不用猜
> 5. **支持按 `rule_id` / `user_id` / 时间窗过滤** → 可只拉 FDE 部门的周报
>
> ⚠️ **关键限制（必须先实测，见 §1.7.6）**：
> - **`user_access_token` 只能读「当前用户发起 + 收到的」汇报，且不分页** ⇒ 主管本人授权即可读自己收到的
> - **`tenant_access_token` 能读全公司但受应用数据权限范围约束** —— 需要 IT 开通 + 确认可见范围
> - **`page_size` 上限 20**，10 次/秒 ⇒ 拉全公司需分页，量不小
> - **⚠️⚠️ 没有写入接口** —— `report` 模块只开放了 3 个接口，**全是只读/管理类**。
>   ⇒ **系统无法代员工提交周报**，只能读。填报仍由员工在飞书原生界面完成（这正是我们要的）

**四条路径对比**：

| 路径 | 员工填写方式 | 系统读取方式 | 依赖 | 推荐度 |
|---|---|---|---|---|
| **A. 飞书原生「汇报/周报」** | 飞书原生周报界面 | `POST /report/v1/tasks/query` | `report:task:readonly` | ⭐⭐⭐ **首选** |
| **B. 飞书多维表格** | 表格里填一行 | 表格 API 读行 | `bitable` 相关 scope | ⭐⭐ 备选 |

> **实测权限现状（2026-11-20 探针，`scripts/probe_feishu_docs.py`）**：

**绑定机制**：

- 路径 B/C：复用 `feishu_scheme_source` 的「人工绑定优先」模式，新建 `feishu_report_source` 表：

employee_id | obj_token | obj_type | report_kind(weekly|monthly) | period_type | active

- HR 手工填链接 → **立刻可用**，不依赖自动发现
- `last_edit_time` 存飞书 `obj_edit_time` → **变更检测**（复用 `get_node`，只依赖 wiki 节点权限，稳定）
- `last_content_hash` → 幂等去重，同内容不重复入库

#### 1.7.3 解析：把周报解析成结构化记录

**关键：周报必须能被机器解析成字段，否则聚合统计做不了。**

**路径 A（原生汇报）解析**：`form_contents` 已经是 `field_name → field_value` 的结构，
只需做**字段名映射**（按 `field_name` 匹配到语义槽位），比解析文档简单一个数量级：

| 语义槽位 | 匹配 `field_name`（示例，需按实际模板确认） |
|---|---|
| `progress[]` | 本周进展 / 本周工作 / 工作进展 |
| `risks[]` | 风险/卡点 / 风险预警 / 遇到的问题 |
| `support_requests[]` | 需要支持 / 需要的帮助 / 待协调 |
| `related_items[]` | 关联事项 / 关联工单 / 相关智能体 |
| `raw_text` | 全部字段拼接（留存 + 哈希） |
| `submitted_at` | **`commit_time`（原生权威值）** |
| `content_hash` | `form_contents` 拼接后 sha256（幂等） |

**路径 B/C（多维表格/云文档）解析**：需要从自由文本中提取，参考模板：

```markdown
# FDE 周报 2026-W45
## 本周进展
- 客服助手智能体灰度上线，覆盖 12 个客服会话场景
## 风险 / 卡点
- 数据看板需求与BI侧排期冲突，预计延后 3 天
## 需要支持
- 需要产品经理确认话术口径
## 关联事项
- 工单 WO-20261115-023
```

解析成结构化行：

| 字段 | 来源 | 用途 |
|---|---|---|
| `progress[]` | 本周进展 | 条目数、内容质量预审 |
| `risks[]` | 风险/卡点 | **风险暴露次数**（对 FDE 极重要） |
| `support_requests[]` | 需要支持 | 求助次数 + 响应情况 |
| `related_items[]` | 关联事项 | 与工单/智能体台账关联 |
| `raw_text` | 全文 | 留存 + 哈希 |
| `submitted_at` | 飞书文档更新时间 | **及时性判定** |
| `content_hash` | 正文 sha256 | 幂等 |

> ⚠️ **模板不强制时的降级**：若解析不出结构，只落 `raw_text` + 标记
> `parsed=false` → 该期聚合表的「风险暴露数」等字段显示 **"未采集到"**，
> **绝不用 0 冒充**（沿用 §1.3 的回填硬规则）。
>
> ★ 路径 A 天然规避这个问题 —— **字段是飞书后台配好的，HR 改模板系统自动跟随**。

#### 1.7.5 自动异常检测（省下主管时间的关键）

系统主动标出，主管不用自己找：

| 异常 | 判定逻辑 | 严重度 |
|---|---|---|
| `REPORT_MISSING` | 应交 N 份，实交 M 份 | MEDIUM |
| `REPORT_LATE` | 文档更新时间晚于截止时点 | MEDIUM |
| `CONTENT_VAGUE` | 命中空洞词表（复用 `semantic_qc._VAGUE_PHRASES`） | MEDIUM |
| `CONTENT_REPEAT` | 连续多期正文相似度 > 0.85 | MEDIUM |
| `RISK_SILENCE` | 连续 K 期零风险暴露，但同期有工单/需求推进 | **HIGH**（疑似未识别风险） |
| `SUPPORT_UNANSWERED` | 求助超 N 小时无响应（**需工单系统配合**） | **HIGH** |
| `SCALE_ANOMALY` | 条目数偏离近 K 期均值 > 2 倍 | LOW |

> **`RISK_SILENCE` 与 `SUPPORT_UNANSWERED` 是 FDE 岗位特有的高价值检测**：
> FDE 天天帮别人解决问题，**如果 FDE 自己暴露的风险没人管、自己的求助没人应，
> 这本身就是绩效问题** —— 而这个检测完全自动，不增加主管任何阅读负担。

#### 1.7.6 周报月报是否进算分？

**结论：几乎不进。只有「对上汇报与透明度」维度把它当依据，且不折算成数字。**

| 维度 | 周报月报的作用 |
|---|---|
| 智能体搭建交付度 | ❌ 不进 —— 汇报频次 ≠ 交付质量 |
| 智能体效果与完善度 | ❌ 不进 |
| AI专业度 | ❌ 不进 |
| **对上汇报与透明度** | ✅ **进** —— 该维度的定义就是"汇报与透明度" |
| 跨部门沟通协作 | ❌ 不进（用协作方数/工单，不用汇报频次） |

「对上汇报与透明度」维度打分时，主管界面**自动展示**：

```
【系统检测】本期风险暴露 3 次（均在周报中提前提出，未见事后补报）
           求助 2 次，响应及时率 100%（平均 4.2 小时）
           主动同步决策 5 次
           ⚠️ 1 次求助超 24 小时未响应
           周报及时率 100%（4/4）
```

主管据此打分，**理由可一键引用这些检测结果**（写入 `reviews[dim].auto_data_ref`）。

> **关键区别**：周报月报不是「变成一个数字参与加权」，而是
> **「变成主管打分时的依据」**。这与 §2.5 的算分边界完全一致。

## 二、AI 质检规则与风险标签分类

### 2.1 AI 质检的硬边界

沿用 `ai_review_engine` / `semantic_qc` 的既有约定，**逐条对齐**：

```
✅ AI 可以做：
   - 判定"这段文字是否空泛"          （确定性词表 + 可选模型交叉校验）
   - 判定"证据是否缺失"              （结构检查，非主观）
   - 判定"条目内容与所选维度是否匹配"（关键词 + 语义相似度）
   - 比对填报内容与系统客观数据        （数值/计数比对，确定性）
   - 识别加减分线索                  （关键词触发）

❌ AI 绝对不做：
   - 不输出分数、不输出等级、不输出绩效结论
   - 不判定"这条工作值多少分"
   - 不自动写入 Score 表、不推进状态机
   - 不替主管做取舍决定
```

**产出形状**（与现有 `AiReview.issues` 完全同构，直接复用落库与前端渲染）：

```json
{
  "overallRisk": "MEDIUM",
  "issues": [
    {
      "code": "FDE_EVIDENCE_MISSING",
      "severity": "HIGH",
      "field": "items[2].deliverable",
      "title": "条目「故障排障闭环」未挂载证据",
      "ruleId": "R-FDE-004",
      "quote": "……",
      "basis": "《FDE 绩效填报规范》第 3.2 条：每条工作条目须绑定至少 1 条可核验证据。",
      "suggestion": "请补充故障单号或复盘文档链接。",
      "confidence": 0.9,
      "source": "RULE",
      "references": ["item_2"]
    }
  ],
  "disclaimer": "本结果为 AI 预审线索，不构成评分结论；所有条目须由主管人工复核。"
}
```

> **`confidence` 的用法**：主管界面按置信度排序。`confidence < 0.6` 的条目标记为
> 「仅供参考」，主管可一键忽略 —— 避免低质量线索消耗主管注意力。

### 2.2 风险标签分类

分两大类：**内容质量类（C）** 和 **事实一致性类（F）**。
每类标签带 `severity`（LOW/MEDIUM/HIGH/BLOCKING）和 `ruleId`。

#### C 类 —— 内容质量（对应问题 3 的"空泛套话 / 证据缺失 / 维度不匹配"）

| 标签 | ruleId | severity | 判定逻辑 | 处理 |
|---|---|---|---|---|
| `FDE_TEXT_VAGUE` | R-FDE-001 | MEDIUM | 命中空洞词表（复用 `semantic_qc._VAGUE_PHRASES`：表现良好/尽职尽责/再接再厉…），或 `what_done` 无具体动词+对象 | **阻断提交**（提交前提示重写） |
| `FDE_TEXT_TOO_SHORT` | R-FDE-002 | LOW | `what_done` < 20 字 | 提交前提示 |
| `FDE_TEXT_TOO_LONG` | R-FDE-003 | LOW | `what_done` > 200 字 | 提交前提示（超长往往在讲故事而非陈述事实） |
| `FDE_EVIDENCE_MISSING` | R-FDE-004 | HIGH | 条目 `evidence` 为空 | **阻断提交** |
| `FDE_EVIDENCE_WEAK` | R-FDE-005 | MEDIUM | 仅有附件无链接，或仅有"其他"类型，或链接为裸 URL 无标题 | 提交前提示 |
| `FDE_EVIDENCE_UNREACHABLE` | R-FDE-006 | MEDIUM | 探测飞书链接不可达/无权限 | 标记待核实（不阻断，可能内网或权限问题） |
| `FDE_DIMENSION_MISMATCH` | R-FDE-007 | MEDIUM | `dimension` 与 `work_type` 联动推荐值不一致，或正文关键词与所选维度无交集 | 待核实（人工改选维度即可） |
| `FDE_DIMENSION_UNCOVERED` | R-FDE-008 | HIGH | 五维度中某维度本期 0 条目 | 主管评分页高亮提示"该维度无填报依据" |
| `FDE_IMPACT_UNMEASURED` | R-FDE-009 | MEDIUM | `business_impact` 未选影响等级，或只写"提升效率"无对象 | 提交前提示 |
| `FDE_BLOCKER_MISSING` | R-FDE-010 | MEDIUM | `work_type` ∈ {需求对接,协调排期,故障排障,风险预警} 但 `blocker_risk` 为空且未选"本期无卡点" | **阻断提交** |
| `FDE_DUPLICATE_ITEM` | R-FDE-011 | MEDIUM | 两条目 `what_done` 相似度 > 0.85 | 提示合并 |
| `FDE_OVERALL_DUPLICATES_ITEM` | R-FDE-012 | LOW | `overall_statement` 与某条目内容重复 > 0.7 | 提示 |

#### F 类 —— 事实一致性（对应问题 3 的"对比系统客观数据找出事实不一致"）

| 标签 | ruleId | severity | 判定逻辑 | 处理 |
|---|---|---|---|---|
| `FDE_FACT_WEEKLY_LATE` | R-FDE-020 | MEDIUM | 填报称"周报全部按时提交"，但客观数据显示逾期 ≥ 1 次 | **待核实**（附具体次数） |
| `FDE_FACT_RESPONSE_MISMATCH` | R-FDE-021 | HIGH | 填报"需求响应均在 SLA 内"，但工单超时单数 > 0 | **待核实**（附单号） |
| `FDE_FACT_AGENT_COUNT_MISMATCH` | R-FDE-022 | MEDIUM | 填报"本期上线 3 个智能体"，发布记录为 5 个 或 1 个 | **待核实** |
| `FDE_FACT_TEMPLATE_MISMATCH` | R-FDE-023 | MEDIUM | 填报"沉淀 5 套模板"，知识库实际 2 套 | **待核实** |
| `FDE_FACT_COLLAB_MISMATCH` | R-FDE-024 | LOW | 填报协作方为 A/B 部门，客观数据的协作方里没有 A | 提示（非硬错，可能是对方没登记） |
| `FDE_FACT_TRAINING_MISMATCH` | R-FDE-025 | LOW | 填报培训场次与签到记录不符 | 提示 |
| `FDE_UNVERIFIED_CLAIM` | R-FDE-026 | MEDIUM | 正文含无据推断词（可能/大概/应该…）且无证据引用（复用 `semantic_qc._UNSUPPORTED_SIGNALS`） | 提示 |

#### D 类 —— 加减分线索（对应问题 3 的"识别潜在加减分线索"）

**原则：AI 只提示"这条可能被套用哪条加减分规则"，不做加减分建议，更不做加减分。**

| 标签 | ruleId | severity | 判定逻辑 | 处理 |
|---|---|---|---|---|
| `FDE_BONUS_HINT` | R-FDE-030 | MEDIUM | 正向线索命中（跨部门协作显著/重大风险提前预警/模板被复用/故障快速闭环/超额交付） | 提示主管核对原文加分条款 |
| `FDE_PENALTY_HINT` | R-FDE-031 | HIGH | 负向线索命中（关键交付延期/方案评审未通过/线上故障影响 GMV/未按要求预警/跨部门投诉） | **待核实**，主管须核对原文扣分条款 |
| `FDE_PENALTY_RULE_MISSING` | R-FDE-032 | MEDIUM | 命中负向线索但方案中对应扣分条款无引用 | 提示补引用 |

> **D 类的关键约束**：`FDE_PENUSALTY_HINT` 只输出「疑似命中原文第 X 条，请核实」，
> **绝不输出扣几分**。加减分分值只能由主管在 `reviews._adjustment.score` 写入，
> 且受 `scheme_points.score_points` 的 `adjustment_min/max` 封顶校验（已实现）。

### 2.3 加减分线索与原文规则的绑定

方案（`PerformanceSchemeVersion.payload`）中新增一个 `bonus_penalty_rules` 段：

```json
{
  "bonus_penalty_rules": [
    {
      "code": "BP-CROSS_DEPT",
      "direction": "bonus",
      "points": 3,
      "quote": "跨部门协作项目获得业务方书面认可",
      "trigger_keywords": ["业务方书面认可", "跨部门立项", "联合交付"],
      "requires_evidence": true,
      "requires_confirmation": true
    },
    {
      "code": "BP-DELAY",
      "direction": "penalty",
      "points": 5,
      "quote": "关键节点交付延期且未提前预警",
      "trigger_keywords": ["延期", "未按期", "逾期"],
      "requires_evidence": true,
      "requires_confirmation": true
    }
  ]
}
```

AI 匹配到 `trigger_keywords` 时，产出 `FDE_BONUS_HINT` / `FDE_PENALTY_HINT`，
`basis` 字段引用 `quote` 原文 + 命中片段，`references` 挂上触发它的条目 ID。
**主管在打分时必须显式确认或驳回**（见 §3.4），驳回也要留痕。

### 2.4 规则引擎落地方式

**沿用 `ai_review_engine` 的 `RULE_ONLY` 模式**（确定性、可复现、可测试）：

```python
# backend/app/services/fde_precheck.py  （新增）
def review_fde_items(
    *,
    items: list[dict],              # 员工填报的工作条目
    auto_filled: dict,              # 系统客观数据回填结果
    bonus_penalty_rules: list[dict],# 方案中的加减分规则
    evidence_index: list[dict],     # 可核验证据清单（系统内 + 已挂载链接）
) -> tuple[list[RuleIssue], str]:
    """FDE 填报预审。只产出 issues 与 overall_risk，绝不产出分数。"""
```

**分工**：
- **确定性规则**（R-FDE-001~012、020~026）：纯 Python，无模型依赖，`RULE_ONLY` 即可跑通
- **语义匹配**（R-FDE-007 维度匹配、011 相似度）：先用关键词 + Jaccard，命中不了再走模型
- **加减分线索**（R-FDE-030~032）：关键词触发，规则来自方案 payload

**模型介入的边界**（继承 `docs/21-真模型幻觉引文压测报告.md` 的教训）：
- 模型只做**分类**（这段是否空泛 / 维度是否匹配），不做**生成**
- 模型输出必须带 `quote`（原文片段）+ `basis`（规则条款），缺任一 → 丢弃该条结果
- 模型输出不产生数字
- 模型不可用时 → 降级到确定性规则 → 主流程继续（原则 P4）

### 2.5 ★ 算分与结算边界：谁产生什么、哪些算数

> 这一节回答最容易被误解的问题：**填报的文本、证据、客观数据、AI 预审，到底哪些参与算分？**
> 结论先行：**AI 预审完全不参与；填报文本不直接参与；客观数据默认不参与。**

#### 2.5.1 四类数据的算分地位

| 数据 | 是否进算分集 | 存在哪 | 谁产生 |
|---|---|---|---|
| **AI 预审结果**（风险标签） | ❌ **完全不进** | `AiReview.issues` | 系统/模型 |
| **员工填报文本**（`what_done` 等） | ❌ **不直接进** | `Evidence`（`usage=scoring`，供主管阅读） | 员工 |
| **工作条目证据** | ❌ 不自动进 | `Evidence` | 员工/系统 |
| **系统客观数据**（工单/上线数等） | ⚠️ **取决于指标类型** | `MetricValue` | 采集器 |
| **主管人工打分** | ✅ **进（唯一来源）** | `SchemeResponse.reviews` → `Score` | 主管/HR |
| **主管确认后的加减分** | ✅ 进 | `reviews._adjustment.score` | 主管/HR |

#### 2.5.2 机制上的三重保障

**① 算分函数根本不读 AI 的东西**

`compute_score` 在 `direct_points` 模式下只读 `SchemeResponse.reviews`（`scheme_points.score_points`），
而 `reviews` 里只有主管手填的 `score`。AI 的 `issues` 在这张表里**没有位置**。

**② 落分函数显式拒绝 AI 来源**

`review_service.persist_score` 的 docstring 原文：
> 「落分。**这个函数不接受任何 AI 来源的数据。**」

**③ 框架既有约定**

`review_service` 模块头：「原则三（模型永远不产生数字）：`compute_score` 只用规则引擎；
AI 评级建议写进 `RatingDraft`，**绝不写进 `Score`**」。

#### 2.5.3 为什么「客观数据默认不进」

FDE 五个维度全部是 `scoring_method: "manager_review"` + `type: "narrative"`：

- `manager_review` 指标**不读 `MetricValue`**，分数来自 `reviews[code].score`
- 只有 `scoring_method: "ratio"` 的指标才吃 `MetricValue` 算达成率

⇒ **客观数据对 FDE 分数没有任何影响**，它的作用是让主管打分**有据可依**，
而非替主管打分。这正是 §3.4「每项得分必须绑定依据来源」中 `auto_data_ref` 的含义。

#### 2.5.4 若将来要做「折算分」的三条硬约束

折算分（`ratio` 模式）的安全性**不取决于「AI 不给分」，而取决于 `MetricValue.value` 的来源是否可信**。
风险不在算分环节，在**采集环节** —— 若采集器读员工填报文本，AI 就间接控分了。

| # | 约束 | 说明 |
|---|---|---|
| **① 采集器只从外部系统 API 取数** | 禁止读填报文本 | ✅ 工单 API → 超时单数 = 3<br>❌ 员工写"本期上线2个" → 采集器读这句 → value = 2 |
| **② `source_ref` 指向原始单据** | 不指向填报记录 | 写 `WO-20261115-023`，不写 `record_id`；任何时候可回原系统核对 |
| **③ 只用于"可数的事实型"子项** | 质量型维度不折算 | ✅ 响应超时单数、上线数<br>❌ 方案设计质量、排期协调合理性、排障彻底程度、培训效果、预警前瞻性 |

> 现有正确写法参照 `plan_execution_metric.py`：
> `source_ref=f"{employee_id}|{period}|plan_execution_rate"` —— **指向原始数据源，可回溯、可重算**。
> 另注：`evidence_service.add_metric_value` 对考勤来源直接抛 `AttendanceEvidenceRejected`，
> 且 `DataSourcePolicy.allowed` 决定该源能否进算分集 —— **默认不信任**。

**首期建议**：FDE 全维度保持 `manager_review`，客观数据做锚点、主管做判断。
待积累 2~3 周期数据、用 `distribution_qc` 确认主管间松紧度稳定后，
再对个别"数得清"的子项引入 `ratio` 混合计分。

### 3.1 关键状态机对齐

现有 `scheme_workflow.transition` 的 phase 已覆盖：

```
filling → awaiting_interview → awaiting_employee → awaiting_hr → finalized → archived
                    ↑                │
                    └── disputed ────┘（HR reopen 退回重评）
```

**FDE 需要的扩展**：

| 扩展 | 说明 |
|---|---|
| `phase = prechecking` | 提交后到 AI 预审完成之间（AI 预审是异步的，不能卡住提交） |
| `phase = evidence_pending` | AI 预审发现 HIGH 级证据缺失 → 回退到员工补充（可带截止时间） |
| `manager_review` 阶段的**强制约束** | 打分理由为空 → 拒收；加减分未逐条确认 → 拒收 |

**不新增顶层状态机**，复用现有 `RecordStatus` + `_workflow.phase`，
这样 `review_center` / `distribution_qc` / `trend_report` 全部无需改动。

### 3.2 填报提交的事务与幂等

沿用 `review_service.submit_self_review` 的语义：

- 幂等键：`dedup_key`（现有）→ FDE 用 `f"{record_id}:fde:{revision}"`
- 提交后 `record.submit_locked` 锁表，员工再改需走「退回重填」路径
- AI 预审可重跑（`AiReview` 按 `(biz_type, biz_id, rule_version)` 去重，保留历史版本）

### 3.3 客观数据回填的时序

```
T-3天  周期开始前   → 预跑一次采集（拿上一期尾部数据，验证采集链路可用）
T0     周期开始     → 建任务、推送通知
T+1天  采集快照 1   → 数据进入暂存区（staging），不出现在填报页
T+7天  采集快照 2   → 增量
...
T+月末 采集终版     → A 区数据封版，标注 as_of
T+月末+3天 填报截止 → 员工提交
T+月末+4天 AI 预审  → 拉取终版客观数据 + 填报内容做比对
```

**关键**：`T+月末` 采集终版与填报截止之间留 3 天缓冲，是为了让**填报时看到的客观数据
已经基本封版**，减少"我填的时候还没数据、后来数据变了"的争议。

### 3.4 主管打分的强制留痕

在现有 `SchemeResponse.reviews` 结构上扩展：

```json
{
  "FDE_DELIVERY": {
    "score": 18,
    "max_score": 20,
    "reason": "本期主导客服助手智能体上线，10 月 12 日完成灰度，验收通过。依据：上线记录 #REL-023、系统内证据 EV-118。",
    "evidence_ids": ["EV-118", "EV-119"],
    "auto_data_ref": ["weekly_on_time_rate=1.0", "agent_releases=2"],
    "confirmed_by": "mgr_001",
    "confirmed_at": "2026-11-25T10:12:00+08:00"
  },
  "_adjustment": {
    "score": 3,
    "reason": "跨部门协同项目获业务方书面认可，符合原文加分条款第 2 条。",
    "evidence_ids": ["EV-130"],
    "rule_code": "BP-CROSS_DEPT",
    "hints": [
      {"hint_code": "FDE_BONUS_HINT", "rule_code": "BP-CROSS_DEPT", "decision": "accepted", "note": "业务方书面确认邮件已附"},
      {"hint_code": "FDE_PENALTY_HINT", "rule_code": "BP-DELAY", "decision": "rejected", "note": "延期 2 天但提前 3 天预警，不符合原文扣分条件"}
    ]
  }
}
```

**强制规则**（后端校验，不依赖前端）：
1. 每个维度 `reason` 非空且 ≥ 10 字
2. `evidence_ids` 或 `auto_data_ref` 至少有一项非空（**每项得分必须有依据来源**）
3. `_adjustment.hints` 中每个 AI 提示都要有 `decision`（accepted/rejected），缺失 → 拒收

这三条校验应加在 `scheme_service` 的评审提交端点，与现有 `score_points` 的
`ScoringError` 同层。

### 3.5 AI 提示的处置闭环

```
AI 提示 → 主管逐条决策（accepted / rejected + note）→ 决策写入 reviews._adjustment.hints
        → 若 accepted：可进入加减分，但仍需主管填数值
        → 若 rejected：note 留档，AI 不得二次提醒
        → 全部 AI 提示决策完成后才允许提交评审
```

**可追溯**：每条提示的"AI 提出时间、规则、依据原文、原文片段、主管决策、决策理由"全程留痕。
若后续申诉，复核人能看到"AI 当时提示了什么、主管为什么采纳或驳回"。

### 3.6 ★ 校准会议：FDE 的横向可比机制（**必经环节，非可选**）

> 解决的核心问题：**FDE 打分主观性强，"怎么统计"？**
> 答案不是算出一个更精确的数字，而是**把主观性制度化** —— 让同岗位的人横向对照。

#### 3.6.1 「不算分」不等于「不算绩效」—— 四层结算链

| 层 | 产出 | 谁产生 | 是否主观 |
|---|---|---|---|
| **① 维度分 → 加减分 → 总分** | 算术求和 | 系统（`scheme_points.score_points`） | ❌ 纯算术 |
| **② 总分 → 等级** | 区间映射或逐条确认 | 主管依据原文（`grading_mode: "manager_confirmed"`） | ⚠️ 有判断，但有锚点 |
| **③ 横向对照 → 校准决议** | KEEP / REVIEW / ADJUST / POLICY | 校准会议集体 | ⚠️ 集体判断，**有依据留痕** |
| **④ 版本化留痕** | 谁改的、改了多少、为什么 | `ScoreVersion` | ❌ 客观记录 |

> **第 ② 层的硬约束**（现有代码已强制）：
> `scheme_service.validate_payload` 要求 `grading_mode == "manager_confirmed"`，
> 否则发布失败 ——「文档等级目前须由主管依据原文确认，**不自动猜测区间**」。

#### 3.6.2 校准会议流程

```
主管各自独立打分（互不参照，各自写理由）
    ↓
HR 组织校准会议
    ↓ 先看分布统计：谁打松了 / 谁打紧了 / 异常分是谁 / 区分度够不够
    ↓ 逐人过：主管陈述依据 → 集体讨论 → 形成决议
    ↓ 决议必须写 basis（依据）
    ↓
会议关闭 → 结果锁定
```

**四种决议动作**（复用 `review_center.resolve_meeting`）：

| 动作 | 含义 | 后续联动 |
|---|---|---|
| `KEEP` | 维持原分 | 记录依据 |
| `REVIEW` | 需进一步复核 | 自动开复核案件（`create_case`） |
| `ADJUST` | 调整分数 | 走 `ScoreAdjustment` → `append_score_version` **版本化留痕** |
| `POLICY` | 制度层面调整 | 记录，不动分数 |

#### 3.6.3 会议前必须先看分布统计

复用 `distribution_qc`，按 **(部门, 岗位, 冻结方案版本)** 分组：

| 指标 | 阈值 | 告警 | 含义 |
|---|---|---|---|
| 变异系数 CV | < 0.15 | `TOO_LENIENT` | 组内区分度不足 —— **"所有人都打 80 分"** |
| 异常分 \|z\| | > 2.0 | `SCORE_OUTLIER` | 偏离组内均值过大 |
| 等级分布偏差 | > 15% | `DISTRIBUTION_GAP` | 与目标分布不符 |
| 组内分差 | ≥ 30 分 | `LARGE_SPREAD` | 同岗位同规则组分差大 |

> ⚠️ **FDE 场景下 CV 检测比量化方案更必要** —— 主观打分最典型的失败模式
> 就是「不敢拉开差距，所有人都打中间分」。`distribution_qc` 的
> `limitations` 已明确写：「异常分与分布差异仅作为核查线索，**不自动调整分数**」。

#### 3.6.4 FDE 特有：按「需求难度分档」分组比较

**FDE 的横向对照有个独特困难**：不同 FDE 面对的需求难度差异巨大。
同样是"上线 1 个智能体"，跨 5 部门重构和单点 bug 修复天差地别。

建议在 `distribution_qc` 的分组键上，**FDE 额外按需求复杂度分档**：

```
分组键 = (部门, 岗位, 冻结方案版本, 需求复杂度分档)
```

复杂度分档可从客观数据推：`工单数 × 平均协作部门数 × 平均响应时长` → 高/中/低三档。
这样"高难度组"与"低难度组"分开比，**避免高难度的人被系统性低估**。

> ⚠️ 需要积累 2~3 个周期数据才做得出分档，**首期不做**。

## 五、方案自身的风险与规避建议

### 5.1 证据链接失效

| 风险 | 场景 | 影响 | 规避建议 |
|---|---|---|---|
| **链接失效** | 文档被删/改权限/换链接 | 主管无法核验 → 回到"凭印象打分" | ① **提交时可达性探测**（`feishu_docs` 探测权限），不可达 → 标记待核实并提示员工改挂系统内证据<br>② **优先系统内证据**：智能体台账/工单/发布记录生成的证据带 ID，不受链接失效影响<br>③ **快照留存**：提交时把证据正文快照落 `Evidence`（含 hash），链接失效后仍可回溯<br>④ **期末归档检查**：定稿前扫一遍链接存活率，失效项在归档前提示 |
| **链接失效** | 飞书文档权限变更 | 同上 | 提交时把证据可见范围设为「部门及以上可见」提示员工；不可见 → 降级为附件 |
| **证据时效** | 文档被覆盖更新，原始内容消失 | 无法证明提交时的状态 | 证据入库时存 `content_hash` + `snapshot_at`；快照内容归档 |

### 5.2 证据质量参差不齐

| 风险 | 场景 | 影响 | 规避建议 |
|---|---|---|---|
| **凑数证据** | 挂一张无关截图 | 形式合规但无实质 | ① **交付物类型枚举** + 类型与 `work_type` 的**匹配校验**（故障排障挂"培训材料"→ 标记异常）<br>② AI 检测文本与证据内容不相关（标题/正文关键词无交集）→ `FDE_EVIDENCE_WEAK`<br>③ **主管评审时看到证据摘要**（不是只有链接），降低盲点 |
| **证据质量分层** | 有人挂 10 页方案，有人挂 1 行结论 | 不可比 | 不做量化打分，只做**存在性 + 匹配度**判断；质量高低由主管在理由中体现 |
| **员工不会选证据** | 不知道该挂什么 | 大量"其他"类型 | 提供按 `work_type` 的**证据推荐清单**（故障排障 → 故障单/复盘/监控截图） |
| **截图不可取证** | 只有截图没有上下文 | 难判断时效与归属 | 证据必填**标题 + 时间**（系统自动取创建时间），AI 检查"证据时间是否落在条目周期内" |

### 5.3 依旧存在主观判断

| 风险 | 场景 | 影响 | 规避建议 |
|---|---|---|---|
| **维度归属主观** | 同一件事归"交付度"还是"效果完善度" | 分数不可比 | ① `work_type → dimension` **联动默认**，员工只在必要时改（改动会被记录）<br>② 改动的条目在主管视图标注"员工调整过维度"<br>③ HR 用 `distribution_qc` 按维度看打分离散度 |
| **打分标准不一致** | 主管 A 给"协调排期"18 分，主管 B 给 12 分 | 公平性质疑 | ① 每维度提供**评分锚点说明**（对应 `scoring_description`）<br>② `distribution_qc` 做同岗位**松紧度**对照（CV > 0.15 提示）<br>③ 校准会议（`review_center` 已有 `校准会议` 关联调分机制）<br>④ 打分理由必填 → 事后可归因 |
| **AI 提示被当作结论** | 主管直接采纳 AI 的加减分线索 | 回到"AI 决定分数" | ① UI 明确标注「AI 预审线索，不构成评分结论」<br>② 加减分线索**不预填数值**，主管必须手填<br>③ 每条 AI 提示必须显式 accepted/rejected<br>④ **审计日志记录**：若主管打分与 AI 提示高度一致，抽样回看（防"橡皮图章"） |
| **过程型工作被低报** | 协调排期、协调资源这类难量化的事，容易写得"不显著" | FDE 价值被低估 | ① 「协调排期」在 `work_type` 里显式存在，并绑定**协作方数量 + 排期表链接**作为证据<br>② 对上汇报维度要求写**决策/影响**而非"汇报了几次"<br>③ 每期**维度覆盖强制**：某维度 0 条目 → 主管评审页高亮"该维度无填报依据"（不是扣分，是提示主管主动确认"本期该维度确实无产出"） |
| **大客户服务量差异** | 有人 20 个需求，有人 4 个 | 量本身影响难度 | 客观数据回填**需求量**作为上下文，分数看**达成与质量**不看绝对量；`work_type` 分布供主管判判读 |

| **周报变成"复制粘贴"** | 每周内容高度雷同 | 表面合规，实则无过程 | ① `CONTENT_REPEAT` 检测（相似度 > 0.85）<br>② 连续多期雷同 → 主管视图高亮<br>③ 不自动扣分 —— 可能是真的稳定产出 |
| **风险沉默** | FDE 遇到问题但不在周报里写 | **最危险的一种** —— 问题被藏起来 | ① `RISK_SILENCE` 检测（连续 K 期零风险暴露 + 同期有工单推进）<br>② 标记 HIGH，**主管必须显式确认"本期确实无风险"**<br>③ 这条检测本身就是"对上汇报与透明度"的打分依据 |
| **求助无响应** | FDE 提了需求没人管 | FDE 价值被消耗、士气受损 | ① `SUPPORT_UNANSWERED` 检测（需工单系统配合）<br>② HIGH 级，**同时提醒主管**（这不只是员工的问题） |
| **汇报量 ≠ 汇报质量** | 用"周报写了 2000 字"当透明度证据 | 形式主义 | ① **周报长度不进任何指标**<br>② 透明度维度看的是「风险暴露 + 求助响应 + 决策同步」的质量维度<br>③ 用「上报了几次汇报」的旧口径替换掉 |
| **飞书文档被改/被删** | 员工交了周报又改掉，或删了 | 历史状态无法证明 | ① 采集时落**内容快照 + `content_hash`**（复用 `Evidence` 快照约定）<br>② `last_content_hash` 幂等，同内容不重复入库<br>③ 删除 → 记录 `missing=true`，**不当作"未提交"** |
| **抓取权限/知识空间受限** | 应用没被加入知识空间（`131006`） | 自动发现失败 | ① **首期走人工绑定**（HR 填链接），不依赖自动发现<br>② 变更检测只依赖 `wiki get_node`，权限更稳定<br>③ 权限不可用时降级为"手动上传周报"，主流程不断 |
| **原生汇报 API 权限未开通** | `report:task:readonly` 未申请（**已实测 99991672**） | 路径 A 不可用 | ① **首期走路径 C（云文档，已实测可用）**，不阻塞上线<br>② 并行提交 scope 申请（§1.7.7 有清单）<br>③ ⚠️ **申请后必须让 IT 发布应用新版本**，否则仍报 99991672 |
| **原生汇报无写入接口** | 想让系统代填周报 | 方案需改 | ⚠️ **飞书 `report` 模块只有 3 个只读/管理接口，没有提交接口** ⇒ 员工必须在飞书原生界面提交，这是既定约束不是缺陷 |
| **原生汇报数据范围受限** | scope 开通后 tenant 态读不到目标部门（应用数据权限范围不含 FDE） | 路径 A 拿不到别人的周报 | ⚠️ 注意此时返回**空 items 而非报错**<br>① 主管用 `user_access_token` 读「自己收到的」—— **FDE 场景主管正是汇报接收人，几乎够用**<br>② 或改走路径 B/C |
| **周报模板被改导致字段映射失效** | HR 在飞书后台改了字段名 | 解析不出语义槽位 | ① 映射表**放数据库不放代码**，改完即生效<br>② 未匹配的字段进 `unmapped_fields` 留档 + 告警<br>③ 核心槽位（进展/风险/支持）映射丢失时该期标 `parsed=false` |
| **主管仍然想逐条看** | 觉得聚合不可靠，想自己读原文 | 工作量没减少，回到原点 | ① 主管视图默认折叠，只在点击异常行时展开明细<br>② 提供"全部展开"但**不默认**；展开行为留痕用于后续统计习惯<br>③ 用 `distribution_qc` 证明聚合够用（异常都抓到了） |

### 5.5 流程与合规风险

| 风险 | 影响 | 规避建议 |
|---|---|---|
| **员工觉得 AI 在"打分"** | 抵触、对抗填报 | ① 填报页**不展示任何 AI 评分暗示**，只展示"格式检查"类提示（证据缺失、必填项）<br>② 术语区分清楚：**「填报校验」（硬拦截）vs「AI 预审」（主管侧提示）**<br>③ 前后端统一 disclaimer 文案 |
| **员工预判 AI 提示而"应付"** | 套话堆积、证据拼凑 | ① 提示只在**主管侧**展开，填报侧只给合规性硬校验<br>② 应付痕迹本身是 AI 预审目标之一（`FDE_TEXT_VAGUE` 在主管侧仍标记） |
| **数据源缺失导致误判** | 工单没接 → F 类规则说"填报与系统数据不一致" | 采集器未接入的源返回 `status=not_collected`，**相关规则整体禁用**并在 UI 说明"该维度无系统数据可校验" |
| **跨周期争议** | "这个成果算上期还是这期" | 条目强制填 `period_start/end`；跨期条目按**主体工作量落在哪期**归属，客观数据按周期封版 |
| **HR 审核成为瓶颈** | HR 要看所有条目 | 只对 AI 标记 HIGH/BLOCKING 的记录做抽查，其余主管自评 + 系统留痕；HR 复核按比例抽检（可配 `distribution_qc` 辅助选样） |
| **个人信息与商业数据泄露** | 证据含 GMV、客户信息 | ① 卡片推送只放分数/等级/关键指标，**评语全文与证据不推飞书**（沿用 D5 决策）<br>② 证据提交时做敏感词提示（客户姓名、手机号、订单号）<br>③ 归档后按保留期策略处理 |
| **规则被套利** | 知道触发词就照着写 | 规则触发词**不在填报页展示**；线索仅供主管核对原文条款；`distribution_qc` + 校准会议兜底 |

### 5.6 方案本身的边界声明（必须写进产品与制度）

```
1. AI 预审只产出风险标签与待核实清单，不产生分数、不产生等级、不产生绩效结论。
2. 所有分数由主管或人事主管人工写入，每一项分数必须绑定依据来源（证据或系统客观数据）。
3. 系统客观数据只作事实锚点，不自动等同绩效结论（考勤异常永不自动扣分）。
4. AI 提示可被主管驳回，驳回需留理由；驳回后 AI 不得二次提醒。
5. 填报内容与证据一经提交锁定，修改需走退回重填路径，全过程留痕。
6. 异议复核由独立复核人处理，原评分人不得独立裁决。
7. 周报月报是「证据流」不是「填报项」—— 主管看聚合表，不逐条读原文。
8. 周报月报长度、频次不进入任何指标；透明度看的是风险暴露与求助响应的质量。
9. 校准会议是必经环节，不是可选 —— 主观打分必须经过同岗位横向对照。
```
