## 零、先说结论：设计稿与本仓库现状的 7 处冲突

`docs/14-工具层设计方案.md` 的**方向是对的**（L2 只读网关 + L3 工具循环 + 只读白名单），但它按"理想态项目"写的，直接照抄会踩坑。下表是逐条核对代码后发现的冲突，**本方案以本表为准**。

| # | 设计稿的写法 | 本仓库的真实情况 | 必须怎么改 |
|---|---|---|---|
| C1 | 「`review_service` 调用 agent 时签发工具令牌」 | `review_service.AgentClient` 只有 `draft()`，**QA 与计划助手根本不走这里**。QA 走 `main.py:1197 /v1/api/qa/query`（返回结构化数据，**从不调 L3**）；计划助手走 `routes/employee_ai.py`，**全部返回空壳**（`_empty_generate_response()`） | 令牌签发**不能挂在 `review_service`**。应新建 `backend/app/services/agent_tool_token.py` + `backend/app/services/agent_tool_gateway.py`（L2 侧工具网关客户端），由 **QA 新路由 `routes/qa.py`** 签发。`review_service` 本期**一行不改** |
| C2 | 「令牌含 `sub=employee_id`，工具参数不接受 `employee_id`」 | 本仓库已有成熟鉴权：`routes/auth.py::_generate_token`（HMAC-SHA256、`base64url(payload).hexsig`）+ `dependencies.get_current_user` + `access_control.build_access_context` | **不要另造一套 token 格式**。新增的 `agent_tool_secret` 必须**独立于** `auth_token_secret`，但签名算法/编码风格与 `_generate_token` 保持一致（便于审计与运维理解）。且令牌 `sub` 之外的权限**必须回到 `access_control` 复核**，不能只信令牌里的 `allow` |
| C3 | 「`settings.agent_tool_secret`」 | `backend/app/core/config.py` 里**没有**这个字段，现有只有 `agent_service_url` / `agent_shared_secret` | 需新增配置项，并遵守现有 `Settings` 的**弱密钥校验模式**（参考 `_validate_auth_secret`：空/弱值直接 `ValueError` 启动失败） |
| C4 | 「每次工具调用写入 `AiTrace`」 | `AiTrace` 模型存在（`domain/models.py:1121`），但**全仓库无任何写入代码**——`grep AiTrace(` 只命中模型定义和 migration。且 `AiTrace` 字段是 `agent/model/prompt_version/input_hash/output_json/latency_ms/status/error`，**装不下** `step/tool/args_hash` | 两种选一（推荐 B）：**A** 扩展 `AiTrace`（加迁移 `0023`，字段 nullable，风险高——会影响既有 `0001_baseline` 表结构）；**B** 新建 `ai_tool_call` 表（迁移 `0023`，独立表，与 `AiTrace` 解耦）。**选 B**：`AiTrace` 语义是"一次模型调用"，工具调用是"一次模型调用内的子事件"，塞进去会污染现有语义 |
| C5 | 「`agent-service/app/base.py` 加 `complete_with_tools`」 | `ModelClient` 是 `Protocol`，但 `EchoModelClient` **只实现 `complete()`**。`NullModelClient` 同理。且 `agent-service/requirements.txt` **只有 fastapi/uvicorn/pydantic**，**没有 `httpx`** —— 设计稿里的 `http_handler` 用 `httpx` 直接会 `ModuleNotFoundError` | `agent-service` 要么加 `httpx>=0.27`，要么改用标准库 `urllib.request`。**推荐加 httpx**（与 backend 一致，连接池/超时语义更好），同时 `backend` 侧 `httpx` 已是既有依赖，版本无冲突 |
| C6 | 「阶段一：接一个真实模型（DeepSeek 或通义）」 | 本仓库 `MODEL_MODE` 现状是 `echo`；`agent-service/app/main.py::_build_client()` **只认 `null` 和 `echo`**，`openai` 分支根本没写；`routes/v1/system_ai.py` 的模型配置全是 `_empty_*` 壳。`docs/11` 台账里 **P3-2 真实大模型接入 = ⬜ 未开始**，被标为 FS-5 的**前置阻塞** | **工具层不能依赖真模型落地**。阶段一必须**先在 `EchoModelClient` 上把工具循环跑通并可测**（确定性 mock 工具调用），再接真模型。真模型是**阶段一的收尾项**，不是开工项 |
| C7 | 「QA agent 声明 `allowed_tools`」「计划生成助手用工具」 | `QAAgent` 已存在于 `agent-service/app/agents.py:250`，但**没有任何 L3 端点调用它**（`agent-service/app/main.py` 只有 `/draft` `/rating` `/evidence-check`）。计划助手则是**前端有完整 UI，后端全空壳** | 阶段一的交付必须是**端到端打通**：`POST /v1/qa/ask`（L2）→ `POST /v1/agent/qa`（L3）→ 工具 → 回答。**只写 `ToolRegistry` 不接端点 = 没交付** |
| C8 | （实现中新发现）`dependencies.check_can_view_score` 用于权限复核 | **该函数签名与调用方不匹配**：定义是 `check_can_view_score(user_id: str, target_employee_id: str, db)`（`dependencies.py:316`），但 `main.py:1251` 传的是 `current_user`（一个 `Employee` **对象**）作为第一个参数 → `user_id` 收到的是 `Employee` 实例 | **工具层不要用 `check_can_view_score`**。改用 `access_control.build_access_context(db, employee).can_view_score_of(target_id)` / `can_access_employee(...)`（这两个是当前唯一签名正确、且被 `access_control` 单一事实源覆盖的路径）。同时把 `main.py:1251` 的调用改为 `current_user.id` —— 这是个**既有 bug**，工具层上线前顺手修掉（它现在会因为 `Employee` 对象无法与 `id` 字符串比较而导致主管查下属时抛异常或误判） |

### 补充：设计稿里 3 处**做对了、不要改**的地方

1. **B1（Agent 不碰 DB/飞书）**：完全符合 `docs/01` 的 L2/L3 分离。保留。
2. **B2（只读）**：符合 `docs/01` 原则①。保留，但注册表的只读校验要**从"声明式"升级为"结构式"**（见 §4.6）。
3. **`max_steps` / `max_tool_calls` 双上限**：这是防绕圈的核心，必须保留，且必须**有测试证明上限生效**。

### 补充：核对代码时发现的两处**既有 bug**（工具层上线前必修）

| # | 位置 | 问题 |
|---|---|---|
| B1 | `backend/app/main.py:1251` | `dependencies.check_can_view_score(current_user, ...)` 传的是 `Employee` **对象**，但该函数签名要求 `user_id: str`。→ 主管查下属的分支是坏的 |
| B2 | `backend/app/main.py:1249` 附近的 `peer_performance_distribution` 分支 | 只查了目标员工是否存在，**没有校验当前用户能否查看该部门的聚合数据**。任何登录用户传一个 `target_employee_id` 就能拿到其所在部门的等级分布与（≥5 人时的）平均分 —— **越权读** |

**这两处都在工具层的必经之路上**（`/v1/qa/query` 要迁移到 `routes/qa.py`），所以**必须一并修掉**，否则工具网关会复制同一个越权洞。修法统一走 `access_control`：
- 员工 → 只能查自己；
- 主管 → 只能查直属下属（以及自己管理范围内的部门聚合）；
- HR → 全员与部门聚合。

> 这一条也印证了设计稿 §7.3「数据查询复用现有 `access_control` 的判定」的方向是对的 —— 只是**现有代码还没真正做到**，不能假设它已经安全。

## 一、范围与分期

### 1.1 一句话范围

**先做 QA 问答闭环**（L2 `/v1/qa/ask` + L3 `/v1/agent/qa` + 3 个只读工具 + 审计 + 测试），**不动已经跑通的 `/v1/agent/draft`**，计划助手的工具化放到阶段二。

### 1.2 分期与验收门槛

| 阶段 | 范围 | 验收门槛（全部满足才算完成） |
|---|---|---|
| **T0 地基**（1 天） | 配置项、令牌签发/校验、工具网关路由骨架、审计表 + 迁移 | 弱密钥导致启动失败；令牌过期/篡改/越权工具全部 401/403；有迁移往返测试 |
| **T1 工具层核心**（2 天） | `agent-service/app/tools.py`（`ToolSpec`/`ToolRegistry`/`http_handler`）、`complete_with_tools` 协议、`ToolUsingAgent` 循环 | 注册表拒写工具；白名单双重校验；上限/超时/截断全部有单测；`EchoModelClient` 工具循环确定性可测 |
| **T2 L2 只读网关**（2 天） | `backend/app/routes/agent_tools.py` + 3 个工具实现 | 工具参数**不接受** `employee_id`；令牌员工与 `access_control` 双重校验；k-匿名生效；PII 脱敏生效；**零写操作** |
| **T3 端到端 QA**（2 天） | `backend/app/routes/qa.py`（`/v1/qa/query` + `/v1/qa/ask`）、`agent-service` `/v1/agent/qa`、审计写入 | 员工问自己能答；问同事被拒；主管问下属能答；工具失败降级不报 500；`AiToolCall` 有记录 |
| **T4 真模型接入**（1–2 天，可并行） | `OpenAICompatModelClient` + `complete_with_tools` | 模型不可用 → 降级；工具调用轮次可观测；真模型下 20 条评测集有基线 |
| **T5 计划助手工具化**（3–5 天） | `get_plan_history` / `get_acceptance_standards` 工具 + 填实 `routes/employee_ai.py` | 生成建议引用真实历史计划；建议覆盖部门验收标准；采纳动作留痕 |

**T0–T3 是最小可交付闭环**，不依赖真模型。T4 与 T5 可并行。

### 1.3 明确不做

- ❌ 不给 `rating` / `comment` / `evidence` 加工具（`/v1/agent/draft` 数据已齐，加工具只增加延迟与不确定性）。
- ❌ 不实现任何写工具（改分、改状态、提交审批、写指标值）。
- ❌ 不让 agent-service 直连数据库或飞书。
- ❌ 不改 `review_service` 的 `AgentClient` 现有契约（避免影响已跑通的 draft 链路）。
- ❌ 不在本期做前端 UI（QA 面板）。先保证 API 可用、可测。

## 二、总体架构（符合本仓库五层模型）

```
L1 前端（本期不新增页面，仅复用现有 API 客户端）
        │  Authorization: Bearer <用户 token>
        ▼
L2 backend (唯一事实源)
   routes/qa.py
     POST /v1/qa/ask
       ├─ 1. get_current_user() → Employee        ← 真实身份
       ├─ 2. qa_permission.resolve_scope()        ← access_control 推导数据范围
       ├─ 3. issue_agent_tool_token(sub, task, allow, ttl=300)
       ├─ 4. POST agent-service /v1/agent/qa
       │      Header: Authorization: Bearer <用户 token>
       │      Body:   { question, context, tool_token }
       └─ 5. 响应透传（answer / citations / data_quality / degraded）
        │
        │  ▲
        │  │ agent-service 反向调回 L2（只读工具）
        │  └────────────────────────────────────────────┐
        ▼                                                │
L3 agent-service                                        │
   app/tools.py  ToolRegistry                          │
   app/agents.py QAAgent(ToolUsingAgent)                │
        │ POST /v1/agent-tools/{tool_name}              │
        │ Header: Authorization: Bearer <agent_tool_token>
        ▼                                                │
L2 backend/app/routes/agent_tools.py  ────────────────────┘
   ├─ 校验 agent_tool_token（签名 / exp / allow）
   ├─ 从令牌取 employee_id，**不接受请求体里的 employee_id**
   ├─ 用 access_control 复核该员工对目标数据的访问权
   ├─ 查库 → 脱敏 → k-匿名
   └─ 写 ai_tool_call 审计表
```

**关键点**：L3 → L2 是**反向调用**，用的是**独立于用户 token 的短时工具令牌**。这正是设计稿 §7.2 的意图，本方案把它落成具体实现。

## 三、核心接口契约

### 3.1 L2 → L3：QA 问答请求

`POST /v1/agent/qa`（agent-service）

```json
{
  "question": "我这个月哪些指标没达标？",
  "context": {
    "period": "202611",
    "scope": "self",
    "task_id": "T-2026-11-运营部"
  },
  "tool_token": "<L2 签发的短时工具令牌>",
  "tool_base_url": "http://127.0.0.1:8000",
  "allowed_tools": ["get_metric_values", "get_evidence", "get_department_stats"]
}
```

响应：

```json
{
  "answer": "本月有 2 项指标未达标：……",
  "citations": ["metric_value:gmv", "evidence:e-123"],
  "data_quality": {
    "completeness": 0.9,
    "as_of": "2026-11-30T23:00:00",
    "degraded": false,
    "citations": ["MetricValue.gmv", "Evidence.e-123"]
  },
  "degraded": false,
  "agent_status": {"qa": "ok"},
  "tool_calls": [
    {"tool": "get_metric_values", "ok": true, "latency_ms": 43, "step": 1}
  ]
}
```

> ⚠️ **响应里没有 `score` 字段**——沿用 `agent-service/app/main.py` 里 `DraftResponse` 的既有约定（`test_draft_api.py::test_no_score_in_response` 已固化这条）。总分由 L2 的 `scoring.py` 产生；QA 只能**引用** L2 给的数字，不能算。

### 3.2 L3 → L2：只读工具请求

`POST /v1/agent-tools/{tool_name}`

```json
{
  "period": "202611",
  "usage": "scoring"
}
```

**请求体里没有 `employee_id`**（B3）。员工身份来自 `Authorization: Bearer <agent_tool_token>`。

响应统一信封（与本仓库既有风格一致）：

```json
{"code": 0, "message": "", "data": { ... }}
```

错误：

| 状态码 | 场景 | 响应 |
|---|---|---|
| 401 | 令牌签名错 / 格式错 / secret 未配置 | `{"code": 401, "message": "工具令牌无效"}` |
| 403 | 令牌过期 / 工具不在 `allow` 白名单 / `access_control` 复核不通过 | `{"code": 403, "message": "无权调用该工具"}` |
| 400 | 参数不合法（周期格式错、`usage` 非法） | `{"code": 400, "message": "..."}` |
| 404 | 令牌绑定的任务/员工不存在 | `{"code": 404, "message": "..."}` |
| 500 | 未预期异常 | `{"code": 500, "message": "工具执行失败"}`（**不泄露堆栈**） |

> 401/403 的 `message` **必须统一措辞**，不区分"令牌过期"与"签名错"，避免给模型反馈可用于探测的信息（与 `agent-service/app/main.py::_verify_token` 的既有安全语义一致）。

### 3.3 工具清单（第一批：3 个）

设计稿列了 7 个，**第一批只做 3 个**，理由：每个工具都要配权限校验、脱敏、k-匿名、审计、单测，一次上 7 个必然失控。

| 工具 | 参数 | 返回 | 数据源 | 脱敏 |
|---|---|---|---|---|
| `get_metric_values` | `period`（必填，`YYYYMM`） | `{period, metrics:[{metric_code,name,value,target,unit,ratio,level,source,as_of}]}` | `MetricValue` + `ConfigSnapshot` + `Rubric` | 无 PII；`ratio`/`level` **必须由 L2 的 `scoring.py` 算**，不由 agent 算 |
| `get_evidence` | `period`（可选）、`usage`（可选：`scoring`/`reference_only`） | `{evidence:[{id,kind,summary,impact,usage,source,as_of}]}` | `Evidence`（复用 `evidence_service.list_scoring_evidence` + `split_by_usage`） | `summary`/`impact` 走 `redact_text`；`reference_only` 必须带 `disclaimer` |
| `get_department_stats` | `period`（必填） | `{period, department_id, total_employees, scored_employees, average_score, rating_distribution, note}` | `Employee` + `AssessmentRecord` + `Score` | **k-匿名**：人数 < 5 → `average_score=null` + `note`（复用 `qa_service.query_department_summary` 已有实现） |

**`get_metric_values` 的 ratio/level 口径必须严格复用 `review_service._build_metric_context` + `scoring.score_record`**，不允许另写一套换算。理由：`docs/01` 原则①说分数只由规则引擎产生；同一指标在 draft 链路与 QA 链路算出不同的 `level` 是不可接受的。

### 3.4 计划助手工具（阶段二）

| 工具 | 参数 | 返回 |
|---|---|---|
| `get_plan_history` | `months`（1–12，默认 6） | 近 N 个月的 `MonthPlan` + `MonthPlanItem` 摘要 + `Result` 摘要（**只返回本人**） |
| `get_acceptance_standards` | 无 | 当前员工部门的 `FormTemplate.fields_json` + `Metric.caliber` + `WeightSet` |

这两个工具**额外注意**：`MonthPlan.plan_month` 是 `YYYY-MM`，而 `MetricValue.period` 是 `YYYYMM`——**两个字段的周期格式不同**（见 `docs/11` 记录与 `services/period.py`）。工具实现里必须走 `period.to_dashed_period()` / `normalize_period()`，不要手写字符串拼接（`review_service.py:340` 的注释已经记录过这个坑）。

## 四、核心组件实现规格

### 4.1 L2 侧：配置

`backend/app/core/config.py` 新增：

```python
# 智能体工具层短时令牌密钥。与 auth_token_secret **必须隔离**：
# 泄露工具密钥 ≠ 泄露用户登录密钥；但反过来也不该让工具令牌成为万能钥匙。
agent_tool_secret: str = ""
agent_tool_token_ttl_seconds: int = 300
```

并在 `Settings` 的 `model_validator` 里加校验（照抄 `_validate_auth_secret` 的模式）：

```python
@model_validator(mode="after")
def _validate_agent_tool_secret(self):
    secret = self.agent_tool_secret.strip()
    if not secret or len(secret) < 32 or secret.lower() in _WEAK_AUTH_SECRETS:
        raise ValueError(
            "AGENT_TOOL_SECRET 配置不安全：必须为至少 32 位随机字符串。"
            "未配置时工具网关拒绝启动（宁可不提供工具能力，也不要裸奔）。"
        )
    return self
```

> **为什么工具层也要 fail fast 而不是"空则放行"**：`agent-service/app/main.py` 的 R12 加固已经把"secret 为空 → 免鉴权"这条债还掉了（见该文件 `_require_startup_secret`）。工具层是新代码，不能一出生就带这个洞。

### 4.2 L2 侧：令牌签发与校验

新建 `backend/app/services/agent_tool_token.py`。

**签发**（L2 内部调用，**永不通过 HTTP 暴露签发接口**）：

```python
@dataclass(frozen=True)
class AgentToolTokenPayload:
    sub: str          # employee_id —— 工具身份唯一来源
    task: str        # 绑定的考核任务/业务上下文
    allow: tuple[str, ...]   # 工具白名单
    scope: str       # self | department —— 粗粒度范围，配合 access_control 复核
    exp: int
    iat: int


def issue_agent_tool_token(
    *,
    employee_id: str,
    task_id: str,
    allow: Sequence[str],
    scope: str = "self",
    ttl: int | None = None,
) -> str:
    """签发短时工具令牌。

    ⚠️ 签名算法与 `routes/auth.py::_generate_token` 保持一致
       （base64url(payload) + "." + HMAC-SHA256 hex），
       但**密钥独立**（agent_tool_secret ≠ auth_token_secret）。
```

```python
    description: str
```

**相对设计稿的 3 处增强**：

1. **`frozen=True`**：工具定义不可变，防止运行期被篡改白名单。
2. **新增 `identity_params: frozenset[str] = frozenset()`**：声明该工具**禁止**接收的身份类参数（如 `employee_id`）。`ToolRegistry.register()` 校验：如果 `parameters.properties` 里出现 `identity_params` 中的键 → **直接抛错**。这把 B3 从"约定"变成"代码保证"，且**在 L3 侧也拦一道**（L2 侧已经拦了，双保险）。
3. **新增 `max_result_items: int = 200`**：列表类工具的条目上限，防止一个部门 5000 人把 8000 字符截断成不可解析的半截 JSON。

`ToolRegistry`：

```python
class ToolRegistry:
    def register(self, spec: ToolSpec) -> None:
        """注册只读工具。写工具、身份参数冲突、schema 不合法一律拒绝。"""
        if not spec.read_only:
            raise ValueError("绩效域不允许写工具")
        if spec.identity_params & set(spec.parameters.get("properties", {})):
            raise ValueError(f"工具 {spec.name} 不允许接受身份参数")
        if not spec.name or not spec.description:
            raise ValueError("工具必须有名称与描述")
        if spec.name in self._tools:
            raise ValueError(f"工具 {spec.name} 重复注册")
        self._tools[spec.name] = spec
```

`call()` 相对设计稿的增强：

```python
def call(
    self, name: str, args: dict[str, Any], allow: set[str]
) -> tuple[dict[str, Any] | None, str | None]:
    """执行工具。返回 (数据, 错误)。错误不是异常，交给模型处理。"""
```

- 白名单检查（`name not in allow`）——**双保险**：即使 `schema()` 过滤了，`call()` 仍要独立校验。
- **参数 schema 校验**：用 `jsonschema`？——**不引入新依赖**。改用轻量校验：检查 `required` 字段是否都在、`properties` 里是否有未知键、类型是否基本匹配。够用且零依赖。
- **超时**：设计稿说"单工具超时 8 秒"，但 `ToolSpec` 里没有真正实现超时的地方。实现方式：
  - `http_handler` 内部用 `httpx.Client(timeout=spec.timeout_s)` → **HTTP 层超时**（覆盖网络挂起）。
  - 工具内部若做重活（如大表扫描），L2 侧自己用 SQL LIMIT + 分页控制。
  - **Python 层不引入线程/信号超时**（信号在 uvicorn 多线程下不可靠，线程池中断不干净）。这是对设计稿的**修正**：文档里"单工具超时"要写清楚是"HTTP 客户端超时"，不是"任意 Python 代码强制中断"。
- **截断**：设计稿的 `{"truncated": True, "preview": text[:max_chars]}` 有问题——`preview` 是**半截 JSON**，模型解析会失败。**修正为**：

```python
if len(text) > spec.max_chars:
    data = {
        "truncated": True,
        "truncated_at": len(text),
        "note": "结果过长已截断，请缩小查询范围或分批获取",
        "preview": text[: spec.max_chars // 2],
    }
```

`preview` 定位为**给人看的调试信息**，明确标注是半截文本；模型看到 `truncated: true` 应知道要缩小范围。

最终循环结构：

```python
def run_with_tools(self, registry: ToolRegistry, **kwargs: Any) -> AgentResult:
    started = time.perf_counter()
    raw_payload = self.build_payload(**kwargs)
    red = redact(raw_payload)
    payload = red.output
    payload["agent"] = self.name

    messages: list[dict[str, Any]] = [
        {"role": "system", "content": self.system_prompt()},
        {"role": "user", "content": json.dumps(payload, ensure_ascii=False)},
    ]
    tools = registry.schema(self.allowed_tools)
    used = 0
    consecutive_errors = 0
    total_chars = 0
    last_error: str | None = None

    for step in range(self.max_steps + 1):
        if time.perf_counter() - started > self.total_timeout_s:
            last_error = "工具循环总超时"
            break
        resp, err = self.client.complete_with_tools(messages, tools)
        if err or resp is None:
            last_error = err or "模型无响应"
            break
        if resp.tool_calls:
            if used + len(resp.tool_calls) > self.max_tool_calls:
                last_error = "超出工具调用次数上限"
                break
            messages.append({
                "role": "assistant",
                "content": resp.content,
                "tool_calls": resp.tool_calls,
            })
            for call in resp.tool_calls:
                used += 1
                data, call_err = registry.call(
                    call.get("name", ""), call.get("arguments") or {}, self.allowed_tools
                )
                if call_err:
                    consecutive_errors += 1
                else:
                    consecutive_errors = 0
                content = json.dumps(
                    {"ok": call_err is None, "data": data, "error": call_err},
                    ensure_ascii=False,
                )
                total_chars += len(content)
                if total_chars > self.max_total_tool_chars:
                    content = json.dumps({
                        "ok": False,
                        "error": "工具结果累计超出上限，请基于已有信息作答",
                    }, ensure_ascii=False)
                messages.append({
                    "role": "tool",
                    "tool_call_id": call.get("id", ""),
                    "name": call.get("name", ""),
                    "content": content,
                })
                self._trace_tool_call(step=step, call=call, data=data, error=call_err)
            if consecutive_errors >= self.max_tool_errors:
                last_error = "连续工具调用失败"
                break
            continue
        # 最终答案
        try:
            validated = self.output_model.model_validate(resp.content or {})
        except ValidationError as exc:
            last_error = f"输出不符合 Schema：{exc.errors()[:3]}"
            break
        # → AgentResult(ok)
        return ...
```

**`/v1/qa/ask` 流程**：

```python
@router.post("/ask")
def ask(
    req: QAAskRequest,
    current_user: Employee = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> dict[str, Any]:
    # 1. 身份 —— 来自 token，不来自 body
    # 2. 范围推导 —— access_control
    scope = qa_permission.resolve_scope(current_user, req, db)
    # 3. 签发短时工具令牌
    token = issue_agent_tool_token(
        employee_id=current_user.id,
        task_id=req.task_id,
        allow=scope.allowed_tools,
        scope=scope.scope,
    )
    # 4. 调 L3
    try:
        resp = agent_client.qa({
            "question": req.question,
            "context": {...},
            "tool_token": token,
            "allowed_tools": scope.allowed_tools,
        })
    except Exception:
        # 5. 降级 —— 仍返回结构化数据（docs/02 D3）
        return _degraded_answer(scope, db, req)
    # 6. 组合响应：结构化数据 + AI 解读
    return {...}
```

**降级语义**（`docs/02` §九 D3 明确要求）：AI 不可用时**仍然返回结构化数据**，只是不生成自然语言解读：

```json
{
  "answer": "AI 问答暂不可用，以下是您的数据：...",
  "data": { ...结构化数据... },
  "data_quality": {"degraded": true, "degrade_reason": "智能体服务不可用"},
  "degraded": true
}
```

**新建 `backend/app/services/qa_permission.py`**（`docs/16` §3.4.4 已列入文件清单）：

```python
@dataclass(frozen=True)
class QaScope:
    scope: str                    # self | direct_reports | department
    allowed_tools: tuple[str, ...]
    employee_ids: tuple[str, ...] # 具体可查员工（scope=self 时只有自己）
    department_ids: tuple[str, ...]
```

```python
def resolve_scope(
    current_user: Employee, req: QAAskRequest, db: Session
) -> QaScope:
    """从已认证身份推导数据范围。

    ⚠️ 模型、请求体里的 employee_id 一律不参与范围判定。
       员工 → 只能查自己；主管 → 直属下属；部门负责人 → 管理范围；
       HR → 全员。判定依据只有 access_control。

    ⚠️ 不要用 `dependencies.check_can_view_score` ——
       它的第一个参数是 `user_id: str`，而 `main.py:1251` 传的是
       `Employee` 对象（签名不匹配的既有 bug，见 §零 C8）。
       这里直接用 `build_access_context` + `can_access_employee`。
    """
```

**关键红线**：`req` 里**不允许**有 `employee_id` 字段。要查具体某个下属，用 `target_alias`（姓名/工号模糊匹配），由 L2 在 `access_control` 允许的候选集里匹配——匹配不到就澄清，**绝不接受模型给的 ID**（`docs/02` §四、§六 C1）。

**迁移旧 `/v1/api/qa/query` 时必须修的两个洞**（见 §零「既有 bug」）：
1. `check_can_view_score(current_user, ...)` → 改为 `check_can_view_score(current_user.id, ...)`。
2. `peer_performance_distribution` 分支**补部门范围校验**（当前任何登录用户都能拿到任意部门的聚合数据）。

4. **API 契约校验**（`check_api_contract.py --strict`）：该脚本判定的是 **`missing` = 前端调了但后端没有**（`frontend - backend`），失败条件是 `missing > 0`；**`unused` = 后端有但前端没用**（`backend - frontend`）**不参与失败判定**。

## 十一、一句话总结

**工具层不是把后端接口暴露给模型，而是在 L2 加一层只读、窄权限、带脱敏与 k-匿名的工具网关，在 L3 加一个有步数/字符/超时三重上限的调用循环；第一批只给 QA 用 3 个工具，`/v1/agent/draft` 一行不动，整条链路先在 `EchoModelClient` 上可测，再接真模型。**
