### A6 交付内容

**不新增表** —— A6 的价值在于**打通 A4 → 绩效域的数据链路**。

此前**全代码搜 `plan_result` 根本不存在**：`result` / `result_evidence` 表

而 `Evidence` 的写入点原本只有两处：

| 写入点 | source | usage | 能进算分？ |
|---|---|---|---|

| `review_service` 飞书审批意见 | `feishu_approval` | `scoring` | ✅ 但那不是「成果」 |

**成果与绩效之间是断的** —— 员工交了成果、主管批了通过，AI 评语和规则引擎
**完全看不到**这些成果。

**新增服务层** `services/result_evidence_materialization.py`：

| 函数 | 职责 |
|---|---|
| `materialize_result()` | 物化 + **幂等**（同一 `source_ref` 直接复用，不重复生成） |
| `resolve_period()` | 周期归属：月成果取 `plan_month`；周成果取 `week_start` 所在月（**D6**） |
| `build_source_ref()` | 幂等键构造 |
| `list_plan_result_evidence()` | 按周期过滤列出成果类证据 |

**物化口径**（2026-11-16 确认）：

| 决策点 | 口径 | 理由 |
|---|---|---|
| 物化时机 | **审批通过时**（`approve_result` 那一刻） | 草稿 / 驳回的成果不该进绩效域；转换点唯一便于追溯 |
| 无附件 | **也要生成** | 成果描述本身就是证据，不强制要求上传文件 |
| `MetricValue` | **不碰** | 「计划执行率」是 A7 的正式指标，由规则引擎算；绕过它会破坏「算分唯一真值」 |
| 周期归属 | **D6：按周起始月** | 跨月周（11/30~12/6）归属 11 月，与考勤的周期口径一致 |
| 幂等 | `source_ref` + 服务层查重 | 重复审批 / 补跑物化不重复生成 |

**幂等键格式**：

```
{employee_id}|{period}|plan_result|{plan_type}|{plan_id}|{plan_item_id}|{version_no}
```

带 `version_no` 是因为**驳回后重新提交会产生新版本** —— 每个版本对应一次独立
审批，应各自生成一张证据；带 `plan_item_id` 是因为同计划下的多个条目是**不同成果**。

**接线**：

- `domain/enums.py` 新增 `EvidenceSource.PLAN_RESULT`
- `result_submission.approve_result()` 审批通过后调 `_try_materialize()`
  - **物化失败不阻断审批** —— 成果通过审批是既成事实，证据转换可事后补跑
    （`materialize_for_result`）

**物化出的证据卡片**：

| 字段 | 值 |
|---|---|
| `kind` / `source` | `plan_result` |
| `usage` | `scoring` ← **与考勤的 `reference_only` 相反**，成果是真业绩 |
| `status` | `approved`（已经过主管 / 部门负责人审批） |
| `visibility` | `share_with_manager` |
| `summary` | 标题 + 完成率 + 附件名（无附件时不含「附件」二字） |
| `impact` | 交付物 + 完成情况 + 个人绩效分 + 审批意见 |
| `as_of` | 审批通过时间 |

**测试**：`test_result_evidence_materialization_api.py` —— 25 个集成测试

### A7 交付内容

**不新增表** —— A7 补的是**指标链**：把「员工实际干得怎么样」变成算分引擎
能直接消费的 `MetricValue`。

A6 打通的是「成果 → 绩效证据」的**证据链**（给 AI 评语看的自然语言描述），
但规则引擎算分吃的是 `MetricValue` —— 这条链此前是断的。

**新增服务层** `services/plan_execution_metric.py`：

| 函数 | 职责 |
|---|---|
| `compute_execution_rate()` | 计算加权执行率 |
| `refresh_execution_rate_metric()` | 重算并写入 `MetricValue` |
| `ensure_metric_definition()` | 幂等创建指标定义 |
| `build_planning_stats()` | 统计装配 |
| `resolve_scope_employee_ids()` | 按 ACL 解析可见员工 |

**口径决策**（2026-11-16 确认）：

| 决策点 | 口径 | 理由 |
|---|---|---|
| 计算时机 | **审批通过时自动重算并写入** | 与 A6 物化同点位，链路一致；失败不阻断审批 |
| 计算公式 | **按条目绩效权重加权**：Σ(完成率×权重)/Σ权重 | 简单平均会让「核心任务只完成 30%」和「十条边角料全 100%」同分 |
| 周期粒度 | **按月（YYYY-MM）** | 与 A6 证据周期、D6 决策一致 |
| 统计范围 | **按数据范围（ACL）** | HR/管理员全公司，部门负责人管理范围，主管直属下属，员工本人 |

**四个「不写 0 分」的设计**（实现时踩坑踩出来的）：

1. **权重全为 0 → 退化为简单平均**，而不是除零给 0 分
   （0 分会被规则引擎当成「完全没干活」，是错误信号）。
2. **无已审批成果 → `value=None`，不写 `MetricValue`**
   （「还没提交」≠「执行率 0%」）。
3. **先定最新版本、再筛已审批** —— 反过来的话，最新版被驳回时会
   **回退到旧的已审批版本**，等于「这次被否了，但上次批过的算我头上」，
   员工可以靠多提交刷高分。
   （实现时踩到了，由 `test_rejected_newer_version_does_not_fall_back_to_old` 抓出）
4. **只统计已审批成果** —— 草稿 / 待审 / 被驳回都不计入，
   否则员工能用「还没通过的成果」刷高自己的分。

**接线**：

- `result_submission.approve_result()` 审批通过后调 `_try_refresh_execution_rate()`
  - **失败不阻断审批**（与 A6 物化同款处理）
  - 写入走 `evidence_service.add_metric_value` —— **算分集唯一入口**，不绕过
- `routes/planning.py` 的 `/stats` 接真实统计 + 补 `Depends(get_current_user)`
  （此前**无鉴权**）

**新增迁移** `0008_phase7_plan_execution_metric.py` —— 播种 `metric` 表的
「计划执行率」指标定义（`calculation` / `data_source` 非空 —— 决策③校验项）。
幂等、**不覆盖人工改过的定义**；downgrade 只删本迁移播种的那一行。

**`GET /planning/stats` 口径**（此前恒返回四个 0）：

| 字段 | 口径 |
|---|---|
| `pendingDayPlans` | 待审（待抽检）日计划数：`status=submitted` 且未记录抽检结论 |
| `overduePendingDayPlans` | 逾期未审：`approval_due_at` 已过期且未抽检 |
| `currentMonthResults` | 周期内成果总数（月按 `plan_month`，周按周起始月 —— **D6**） |
| `closureRate` | 计划执行闭环率 = 已审批成果数 / 应提交条目数 |

**测试**：`test_plan_execution_metric_api.py` —— 28 个集成测试
（公式加权 / 退化平均 / 只算已审批 / 最新版本 / 不写空值 / 写入口字段 /
upsert 不重复 / 指标定义幂等 / 审批联动 / 周期归属 D6 /
stats 真实数字 / 逾期统计 / 已抽检排除 / 鉴权 / 四种数据范围 / 端到端）。

> **顺带修正 A6 的一个断言**：A6 原先断言「审批后 `MetricValue` 为空」——
> A7 落地后不再成立（执行率指标**正是**审批时写的）。

### 真实数据库端到端验证（A2++）

`backend/scripts/verify_plan_approval_e2e.py` —— 在**真实库**（非 mock）上跑完整审批闭环，
并固化三个极易踩的坑：

1. **`get_db` 覆盖必须用 generator 形式**。若覆盖成 `get_sessionmaker`（它是个 class），
   FastAPI 会去解析它的 `__init__` 签名，把 `local_sessionmaker` / `local_kw` 当成必填 query
   参数 → **422 `loc: ["query","local_kw"]`**。这不是路由 bug，是依赖覆盖姿势问题。
2. **覆盖用的 generator 必须 `commit()`**。真实 `get_db` 在请求结束时提交；若覆盖版不提交，
   会「接口返回 200、库里没变化」—— 审批被静默回滚。
3. **`get_current_user` 不能塞已关闭会话的 `Employee` 实例**。访问 `name` / `department_id`
   会触发 `DetachedInstanceError`。应改为每次请求从当前会话取。

> ⚠️ 现有单测用 `lambda: db`（共享会话）覆盖，**未覆盖真实提交路径**。

### 3.3 🔴 关键设计问题：计划证据怎么进绩效证据表？

`Evidence` 表当前字段：

```python
employee_id, record_id (可空), kind, summary, impact, source,

quality_score, confidence, concern, anomaly_type, anomaly_count, approved_flag
```

**注意：`Evidence.record_id` 可空** —— 这意味着 Evidence 可以先脱离 AssessmentRecord 存在，等考核时再挂接。

三种方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **E1 成果直接写 Evidence** | 提交成果即创建 `Evidence(source='plan_result')`，`record_id=NULL`；考核时按 `source_ref` 关联 | 复用现表，查询统一 | Evidence 会快速膨胀（每个成果一条）；`source_ref` 需承载 plan/result id |
| **E2 计划域独立表 + 考核时转换** | 成果表独立，考核时由 `evidence_service` 转换写入 Evidence | 职责清晰，转换点唯一 | 多一层转换逻辑 |
| **E3 两者都写** | 成果表 + 同步写 Evidence | 查询方便 | 双写不一致风险 |

**我的建议：E2 + 延迟物化。** 理由：
1. `Evidence` 是**绩效域**的表，混进计划域数据会污染语义（现在 `usage` 只有两种，计划的"已提交/已审批"状态不该塞进 `status`）
2. 与方案 B 的经验一致 —— 考勤同步写 Evidence 是**只写 reference_only**，计划证据应该只在考核时按需物化
3. 转换点唯一，便于追溯"这条证据从哪个成果来的"
