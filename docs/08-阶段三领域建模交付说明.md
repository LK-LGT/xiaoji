## 二、关键技术决策

### 决策 ①：不重复建设已有的计划 CRUD

排查发现 `MonthPlan`、`MonthPlanItem`、`WeekPlan`、`WeekPlanItem`、`DayPlan`、`DayPlanItem`
**早已存在**（由 `0003_phase3_planning.py` 迁移创建），
且 `services/planning.py`（922 行）已提供完整 CRUD、状态机与乐观锁。

因此本阶段**没有**新建 `Plan` / `PlanItem` 通用表，
只补齐真正缺失的两张表：

- `plan_draft_version` —— 草稿版本快照
- `plan_approval` —— 提交 / 撤回 / 审批 / 驳回的审计流水

### 决策 ②：计划关联用多态复合键，而非三套可空外键

`PlanDraftVersion` 与 `PlanApproval` 需要同时关联月 / 周 / 日三种计划。
可选方案有三种：

| 方案 | 问题 |
|---|---|
| 三套可空外键（`month_plan_id` / `week_plan_id` / `day_plan_id`） | 三分之二恒为 NULL，索引膨胀，约束难以表达 |
| 单张通用 `plan` 表 | 需要数据迁移既有三张表，风险高 |
| **多态 `(plan_type, plan_id)` 复合键** ✅ | 无冗余外键，跨表查询时按 `plan_type` 分派 |

采用第三种。代价是**放弃了这层物理外键约束**，
因此在服务层补了显式的存在性校验与 `plan_type` 白名单校验。

### 决策 ③：争议状态机集中定义，非法迁移统一 409

```
SUBMITTED ──assign──> REVIEWING
SUBMITTED ──decide──> DECIDED
REVIEWING ──supplement──> NEEDS_SUPPLEMENT
REVIEWING ──decide──> DECIDED
NEEDS_SUPPLEMENT ──supplement──> REVIEWING
DECIDED ──archive──> ARCHIVED
```

非法迁移抛 `InvalidStateTransition`，由 `main.py` 的全局异常处理器
统一映射为 **HTTP 409**。状态机不散落在路由里，改一处即可全局生效。

### 决策 ④：权限复用既有 token 鉴权体系

复用 `dependencies.get_current_user`（token 校验）与
`access_control.build_access_context_for_user`（角色 / 数据范围），
**没有另起一套权限体系**。角色划分：

| 角色 | 可执行操作 |
|---|---|
| 员工 | 创建争议、查看**自己**的案件、补充材料 |
| 评审人 | 查看**被指派**的案件、提交评审意见、申请回避 |
| HR / 部门负责人 | 指派 / 移除评审人、裁决、归档、查看全部案件 |
| 未登录 | 一律 401 |

### 决策 ⑤：AI 只记录，不写业务状态（**关键边界**）

AI 复核表与会话表**只记录** AI 输出、遥测与人工采纳动作，
**绝不直接修改业务状态、评级或分数**。

- 分数、等级、状态一律由业务规则与人工确认产出；
- AI 的 `overallRisk` 只是**提示**，不参与任何自动流转；
- 建议采纳动作单独落 `ai_suggestion_action` 表，形成完整审计链。

这条边界是本阶段最重要的设计约束——它保证了「AI 建议」与「业务事实」
在数据层面可分离、可追溯、可回溯。

### 决策 ⑥：无 LLM 时的确定性规则引擎

尚未接入真实模型，因此实现 `ai_review_engine.py`：
用**确定性规则**（`R-PLAN-001~007`、`R-RES-001~004`）产出复核结果。

- 同样的输入永远得到同样的输出 → 可复现、可测试；
- 每条问题都带 `ruleId` / `basis` / `confidence`，符合「AI 输出必须给依据」的硬约束；
- 后续接入真实模型时，规则部分作为**兜底与交叉校验**保留。

### 踩坑记录

**坑 1：SQLite 内存库跨线程隔离**
`sqlite:///:memory:` 是**按连接**创建独立数据库的，而 FastAPI `TestClient`
在 worker 线程里跑请求，默认连接池会让请求拿到一个全新的空库，
报 `no such table`。解决：用 `StaticPool` + `check_same_thread=False`，
让所有线程共用同一连接。

**坑 2：`dependency_overrides` 是 app 级全局状态**
顺序创建多个 client 时，后创建的覆盖会顶掉前一个，导致所有请求
都变成「最后创建的那个用户」——表现为本该 200 的 HR 请求变成 403。
解决：改用 `as_user(user)` 上下文管理器，在 `with` 块内设置覆盖、
退出时移除，保证身份作用域严格隔离。

**坑 3：UUID 主键 vs 前端 `number` 类型**
前端 TypeScript 接口声明 `id: number`，但后端主键是 UUID 字符串。
路由参数若声明为 `int` 会直接 422。解决：路由签名统一用 `str`，
序列化时按前端契约输出。

### 关于绩效管理系统阶段三建设工作的汇报

**一、工作背景**

本阶段的核心任务，是把此前已经「接口打通」但「没有数据」的三个关键业务域
——员工工作计划、绩效争议、AI 辅助复核——从**演示可用**推进到**真实可用**。

在此之前，系统已完成 267 个前后端接口的契约对齐工作，接口层面全部打通、
无缺失。但调研发现，其中涉及计划、争议、人工智能辅助的这批接口，
返回的是固定空数据，没有对应的数据表、持久化逻辑和状态流转规则。
换句话说，界面上的按钮都能点，但点完之后没有真正落地的东西，
业务过程无法追溯，出了问题也无法复盘。

**二、本阶段解决的核心问题**

第一，把「看得见但记不住」变成「全程留痕」。

本阶段新增了 9 张数据表，覆盖计划版本快照、审批流水、争议案件、
评审人指派、评审意见、机器辅助复核记录、对话历史以及建议采纳动作。
这些表不是孤立的堆砌，而是构成了完整的业务证据链：
一条争议从提交、指派评审、提交意见、裁决到归档，
每一步是谁在什么时间做了什么，全部可追溯；
一条建议从机器生成到人工采纳、修改或忽略，同样完整留痕。

第二，解决了「状态可以随便跳」这个隐性问题。

过去状态流转散落在各个接口里，缺乏统一约束，容易出现业务逻辑上的矛盾状态。
本阶段把计划审批和争议处理各自的状态机集中定义，明确了每一种合法流转路径，
非法流转一律拒绝并返回明确的业务错误码，避免了脏数据进入系统。

第三，堵上了权限方面的实际漏洞。

本阶段统一复用了系统既有的令牌鉴权机制，并在此基础上补充了数据级权限判定。
现在普通员工无法查看他人的争议案件，无法指派评审人或下达裁决；
只有被指派的评审人才能发表评审意见，且一旦申请回避便不能再发表意见。
未登录访问任何业务接口一律拦截。这一机制是后续系统安全审计的可靠基础。

第四，为人工智能能力划定了清晰的安全边界。

这是本阶段一项重要的管理性设计。我们明确了人工智能在系统中的定位：
**它只能提供建议和记录，不能直接改变任何业务结论。**
分数、等级、最终状态一律仍由既定的业务规则和人工确认产生。
这样做的原因很直接——一旦允许算法自动改写考核结果，责任边界将无法界定，
一旦出现争议也将无法解释和追责。
同时，在尚未接入真实大模型的情况下，我们没有让系统空转，
而是实现了基于明确规则的自动复核，输出可验证、可重复、附带判断依据的检查结果，
既保证了当前功能可用，也为未来接入真实模型预留了兜底校验层。

**三、当前技术状态**

经全量验收，各项指标如下：

- 后端自动化测试 **439 项全部通过**，1 项因环境原因跳过，无失败项；
- 接口契约校验 **267 个接口全部对齐，缺失 0 项**，严格模式通过；
- 前端类型检查 **零错误**；
- 数据库迁移已在真实环境成功执行，**9 张新表、20 个索引全部就位，
  外键完整性校验零违规**，且已完成降级与升级的往返验证；
- 服务正常启动，接口文档正常输出，未授权访问被正确拦截。

**四、本阶段额外发现并处理的问题**

在推进过程中，团队主动发现并修复了若干容易遗漏的工程隐患，
这些在演示环境中不易暴露，但会在生产环境造成排查困难：

1. 部分数据表的索引字段与实际字段名不一致，导致数据库在启动阶段直接报错；
2. 内存数据库在多线程测试环境下存在隔离性问题，导致测试结果不稳定、
   存在偶发失败，已通过统一连接管理解决；
3. 自动化测试中的身份切换存在状态残留风险，可能导致权限相关的断言失真，
   已改为严格作用域隔离；
4. 前后端在标识符类型上的历史遗留不一致，已统一处理，避免了参数校验失败。

**五、后续工作建议**

按优先级建议推进以下事项：

**第一优先（建议立即安排）：代码入库与流水线建设。**
目前代码仓库中仍有部分新增文件未纳入版本管理，存在丢失风险，
建议尽快统一提交。同时建议建立自动化流水线，
把接口契约校验、后端测试、前端类型检查三项纳入每次提交的自动检查，
从机制上避免「本地通过、上线出错」的情况。这是当前最紧迫的基础性工作。

**第二优先：争议管理的前端界面建设。**
后端能力已经就绪，但前端尚未提供完整的管理界面。
建议下一步完成员工申诉入口、评审人处理界面和裁决界面的开发，
让业务人员能够真正用起来，而不仅是接口层面的完成。

**第三优先：接入真实大模型与证据包功能。**
当前的自动复核基于规则实现，稳定可用但能力有限。
待模型供应商与安全合规方案确认后，可接入真实模型，
规则层保留作为兜底与交叉校验。同时争议证据包的自动打包功能也列入后续计划。

**六、结论**

本阶段工作已从「接口打通」实质性地推进到了「业务可用、数据可信、过程可溯」。
三个核心业务域具备了完整的数据模型、持久化能力、状态流转规则和权限管控，
并通过了全量自动化验收。

系统的底层骨架已经搭建完毕，下一阶段的重点将转向业务功能的完善与前端交互建设，
让系统从「技术上可用」走向「业务上好用」。
