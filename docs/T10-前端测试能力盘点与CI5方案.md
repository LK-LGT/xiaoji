## 三、两条路线

### 路线 A · 组件测试层（`@vue/test-utils` + `jsdom`）

**做什么**：把「读源码断言」逐步换成「真实挂载 + 交互断言」。

```typescript
import { mount } from '@vue/test-utils'
import WeekPlanApproval from '../../src/views/leader/WeekPlanApproval.vue'

test('超长计划文本不溢出容器', () => {
  const wrapper = mount(WeekPlanApproval, { props: { plan: { text: 'x'.repeat(500) } } })
  const cell = wrapper.find('.approval-text-cell')
  assert.ok(cell.element.scrollWidth <= cell.element.clientWidth)
})
```

**优点**：
- 覆盖**逻辑**而非源码文本 ⇒ 直接消灭「假绿 / 假红」；
- 无需起后端、无需浏览器 ⇒ **CI 里跑得快**（秒级 vs 数十秒）；
- 可在 CI 里**并行**跑；
- 不需要维护 E2E 数据。

**缺点**：
- 测不到「跨页面跳转」「真实路由」「真实 HTTP」；
- 组件有外部依赖（Element Plus、Pinia、axios）时需要 mock。

**成本**：🟢 **中**（基础设施 1–2 天 + 每个组件约 30–60 分钟）

### 路线 B · 端到端（Playwright）

**做什么**：真浏览器跑通「登录 → 填计划 → 提交 → 审批 → 填成果 → 确认」。

**优点**：覆盖**唯一真实**的用户路径 —— 前后端契约、路由守卫、状态管理全部一起验。

**缺点**：
- 需要**真起后端 + 建测试库**（CI 里要跑 Alembic 迁移）；
- 需要飞书 OAuth 的**替身**（CI 无飞书凭证）⇒ 得靠 `TEST_USER_PASSWORDS` 那条通路；
- 每个用例几十秒 ⇒ 只能覆盖**极少数**关键路径；
- ⚠️ **架构风险**：后端已有 `verify_plan_approval_e2e.py` 做同一流程 ⇒
  **同一套流程维护两份**，极易两边漂移。

**成本**：🔴 **高**（基础设施 2–3 天 + 每条路径 1–2 天）

## 四、推荐方案：A 打底 → B 收口

⚠️ **不建议直接做 B**。理由：

1. **B 覆盖不了 134 个组件里的大部分**。6 条 E2E 路径 vs 44009 行代码 ⇒ 覆盖率极低，
   而 A 能覆盖「任意一个组件的逻辑」。
2. **B 的维护成本会随时间增长**，A 的边际成本低。
3. ⚠️ **两条路线的真实关系**：
   - A 负责**「组件行为对不对」** —— 快、密、便宜；
   - B 负责**「整条链路通不通」** —— 慢、稀、贵。

   ⇒ 正确关系是**互补**，不是二选一。

**建议路径**：

```
阶段 1 · 基础设施（1–2 天）
  ├─ 装 @vue/test-utils + jsdom
  ├─ 解决「.vue 单文件组件」在 node --test 下无法 import 的问题
  │   （需要 vue SFC 编译步骤 ⇒ 要么接 vitest，要么写最小编译钩子）
  └─ 建立「组件测试」目录约定 + 命名规范

阶段 2 · 存量替换（滚动，不设截止日期）
  └─ 把 165 处「读源码断言」中**逻辑相关**的部分逐个换成挂载断言
     ⚠️ 纯样式/纯约定类的（如「必须用 approval-text-cell 类名」）
        保留读源码断言 —— 那类断言本身是合理的

阶段 3 · E2E 收口（2–3 天，只做 1–2 条最关键路径）
  └─ Playwright + CI 里起后端
  └─ ⚠️ 数据准备**复用** verify_plan_approval_e2e.py 的逻辑，而不是重写
```

⚠️ **阶段 1 的技术难点要提前说清楚**：

当前前端测试跑在 **Node 内置的 `node --test`** 上（`--experimental-strip-types`）。
它**没有 SFC 编译能力** ⇒ `.vue` 文件**无法直接 import** ⇒ 挂载测试跑不起来。

⇒ 必须二选一：

| 方案 | 做法 | 代价 |
|---|---|---|
| **接入 vitest** | 引入 vitest + `@vitejs/plugin-vue` + jsdom 环境 | 需要迁移 43 个测试文件的 runner（`node:test` → `vitest`），⚠️ 但 vitest 兼容 `node:test` 风格 API，迁移面小 |
| **自建编译钩子** | 给 `node --test` 加 `--import` 钩子，用 `@vue/compiler-sfc` 编译 `.vue` | 改动小，但要自己处理 CSS、scoped、依赖收集 |

⇒ **推荐 vitest**（生态成熟、后续接 Playwright 也更顺）。

### 7.2 关键设计决策

**① 两条测试腿并存，不合并**

| 测试类型 | runner | 位置 | 测什么 |
|---|---|---|---|
| 纯逻辑 / 静态约定 | `node --test` | `tests/*.test.ts` | 纯函数、源码文本约定 |
| **组件行为** | `vitest` | `tests/component/**` | ⚠️ **真实挂载 + 交互** |

⚠️ **为什么老测试不迁移**：43 文件 / 337 例全依赖 `node:test` API。vitest 兼容该 API，
但搬迁需重跑验证全部 337 例，且老测试里大量是「读源码断言」—— 对 vitest **零收益**。

⚠️ **为什么组件测试只能跑在 vitest 上**：`node --test`（即使带 `--experimental-strip-types`）
**没有 SFC 编译能力** ⇒ `.vue` 无法 import ⇒ 挂载测试根本跑不起来。

**② 生产用「按需自动导入」，测试用「全量注册」**

生产靠 `unplugin-vue-components` 的 `ElementPlusResolver` 在**编译期**改写 `<el-xxx>`；
vitest **不走**那个插件 ⇒ `<el-table>` 会变成未知自定义元素 ⇒ 渲染空壳。
⇒ 测试环境**手动全量注册** Element Plus（`setup.ts`）。

### 7.3 踩到的坑

| 坑 | 现象 | 处置 |

| ⚠️ **vitest 3.x 自带 2 个 critical 漏洞** | `tinypool` 原型污染→RCE；`vitest` 路径穿越→任意文件读 | 升到 **vitest 5.1.1** ⇒ critical 清零 |

### 8.1 ⚠️ 核心发现：165 处断言**质量参差**，不能一刀切

阶段 2 的第一步是**普查**这 165 处读源码断言的强度。按断言手法分成三档：

| 档位 | 判据 | 数量 | 处置 |
|---|---|---|---|
| 🟢 **强** | 用了「切块 / AST / 函数体提取」等**语义级**手法 | 7 个文件 | ❌ **不动** —— 那类断言本来就合理 |
| 🟡 **中** | 纯样式 / 类名 / 文案约定 | 约 86 处 | ❌ **不动** —— jsdom 不做布局，读源码反而合适 |
| 🔴 **弱** | 断言里含**可执行逻辑**（`v-if` / `v-for` / `@click` / `computed` / `emit`） | **100 处** | ✅ **该换** |

⚠️ **一个反直觉的实测结论**：
最初以为「所有读源码断言都是假保障」，实际验证发现**不是**。
以 `tests/feishu-login.test.ts` 为例，它用「切块」精确校验了
`REASON_HINTS` 里每种诊断码的 `retryable` 取值，注释里甚至明确写了
「哪怕 exited 写成了 true，这条断言也会通过」——
**作者早已预判并防住了**。

⇒ **教训**：批量替换前必须先**逐个甄别**，
否则会把高质量断言降级成低质量挂载测试。

### 8.2.2 ⭐⭐⭐ AI 变更预览：apply 的 mode 是数据写入语义

`MonthPlanAiDiff.vue` 里最关键的一行：

```typescript
const append = props.operationMode === 'SUPPLEMENT'
emit('apply', { mode: append ? 'append' : 'replace', indexes: [...], items: [...], adoptedWithEdit: false })
```

⚠️ **若把 `append` 写成 `replace`** ⇒「补充」模式会变成**整体替换**
⇒ **用户原有任务被覆盖**。

⇒ 而源码里 `'append'` / `'replace'` 两个字符串都还在，
原来的正则断言**照样全绿**。

⇒ 挂载断言直接验证 **payload 的 `mode` 字段**：

| operationMode | 期望 mode |
|---|---|
| `SUPPLEMENT` | `append` |
| `OPTIMIZE` | `replace` |
| `REVISE_REJECTION` | `replace` |

同批覆盖的还有：**只带上被勾选的任务**（`indexes` + `items`）、
**换一批建议时勾选状态必须重置**（否则带着旧索引应用新数据）、
**「修改前」只在 OPTIMIZE / REVISE_REJECTION 显示**。

### 8.2.3 ⭐⭐ 组织架构：层级过滤

`OrgManagement.vue` 的 `visibleRows` 过滤：

```typescript
selected.value
  ? rows.value.filter((row) => row.id === selected.value?.id || isDescendant(row, selected.value!.id))
  : rows.value
```

⇒ 选中父节点后**只显示它 + 它的全部后代**，兄弟节点必须消失。
⇒ 现有断言只有 `assert.match(source, /<div class="section-header">[\s\S]*@click="openCreate"/)`。

⇒ 挂载断言覆盖四种选中位置（父节点 / 中间层 / 叶子 / 兄弟），
并验证**「兄弟节点不出现」**这条否定式断言。

⚠️ **诚实记录**：自检发现 `isDescendant` 的**哨兵值类型**问题
（`"0"` 写成 `0`）**在多数路径上结果相同** ⇒ 挂载断言**抓不到**它。
⇒ 这类要靠**类型/契约断言** —— 挂载断言擅长测**可见行为**，
不擅长测「值恰好相同时不会暴露的写法问题」。

### 8.2.1 ⭐⭐ 周计划任务卡片：性价比最高的一个

`WeekPlanTaskEditorCard.vue` —— **仅 75 行、零外部依赖**（只依赖一个纯函数
`countWeekWorkPoints`），却是 `week-plan-editor-state-ui.test.ts` 里
**19 处逻辑断言**的落点 ⇒ **挂载成本几乎为零，逻辑密度最高**。

原断言全是字符串匹配：

```typescript
assert.match(source, /v-model="model\.deliverable"/)
assert.match(source, /v-model="model\.quality"/)
```

⚠️ **假绿场景**：把 `v-model="model.deliverable"` 改成
`v-model="model.delivrable"`（拼错一个字母）⇒ **正则照样匹配得上** ⇒ 测试全绿，
而「交付物」输入框已经绑错字段 ⇒ **用户填的内容存不进去**。

⇒ 挂载断言直接验证**三个 textarea 的实际值**分别来自
`model.content` / `model.deliverable` / `model.quality`。

覆盖的六类行为：

| 行为 | 说明 |
|---|---|
| 要点计数 | `countWeekWorkPoints` 数的是**非空行**（空白行不计入） |
| 整体错误态 | 任一字段有错 → 卡片加 `has-error` |
| 逐字段错误提示 | 只有出错字段显示错误文案 + `is-error` 类 |
| 展开 / 收起 | `v-show` ⇒ 内容**仍在 DOM**，只是不可见 ⇒ 用 `isVisible()` 而非 `exists()` |
| 只读态 | `disabled` ⇒ 三个输入框都禁用 |
| 字段绑定 | 三个 textarea 的值分别来自三个 model 字段 |

### 8.2.1 ⭐⭐ 月计划列表：三条产品级规则（防重复建计划）

`EmployeeMonthPlanListRefactored.vue` 里有三条**数据一致性相关**的规则，
原先全部只被字符串断言覆盖：

| 规则 | 实现 | 原断言 | 缺口 |
|---|---|---|---|
| ① **7 个月份卡片都要渲染**（无计划也显示） | `Array.from({length: 7})`，**刻意没有** `v-if="monthCards.length"` | `doesNotMatch(/v-if="monthCards\.length"/)` | 改成 `v-if="monthCards.length > 0"` 就能绕过 |
| ② **主按钮文案随状态变** | `{{ selectedPlan ? '打开月计划' : '新建月计划' }}` | ❌ 无 | 「新建」二字会让人以为要多建一份 |
| ③ **已有计划 → 打开它，不重复创建** | `if (selectedPlan.value) return goEdit(...)` | ❌ 无 | **重复建计划** = 数据污染 |
| ④ **历史月份不能新建** | `canCreateSelectedMonth = currentMonth >= getCurrentMonth()` | ❌ 无 | 历史月份可补建 |

⇒ 挂载断言里，③ 直接验证 **`router.push` 的目标带上了已有计划的 id**，
④ 验证**空态区的提示文案与「新建」按钮是否存在**。

### 8.3 ⭐ 最有价值的发现：`displayTotal` 的折叠补偿

`LeaderEmployeeWork.vue` 的月计划折叠有个**易错点**：

```typescript
const displayItems = computed(() => collapseMonthPlanRows(pageData.value?.items ?? []))
const displayTotal = computed(() => {
  const collapsedOnPage = pageData.value.items.length - displayItems.value.length
  return Math.max(displayItems.value.length, pageData.value.total - collapsedOnPage)
})
```

⇒ 总数必须**减去本页折叠掉的行数**，否则分页会虚高、最后一页是空的。
⇒ 现有源码断言只有 `assert.match(source, /displayTotal/)` —— **完全测不到**。
⇒ 挂载断言：`total=8`、本页 3 条折叠成 1 行 ⇒ 必须显示「共 6 条记录」。

### 8.4 ⭐⭐ 断言有效性自检（本次的核心方法论沉淀）

⚠️ **挂载测试自身的风险是「测了，但测不出东西」**。
所以本阶段加了 `_assertion-efficacy.component.test.ts`：

做法 —— 在**测试内**复刻一份「**故意写错的折叠逻辑**」，
断言它与正确实现的输出**必须不同**：

| 错误实现 | 与正确实现的差异 |
|---|---|
| 折叠条件 `!==` 写成 `===` | 行数 3 vs 1 |
| 漏掉 `businessId` 去重 | 行数 3 vs 1 |
| 总数忘了减 `collapsedOnPage` | 8 vs 6 |
| 漏掉「不能早于本月」闸（历史月可建） | true vs false |
| 漏掉「已有计划就打开它」（会重复建） | create vs edit |
| **字段名拼错**（`content` → `contents`） | 读到值不同 |
| **空白行也计入要点数** | 2 vs 4 |

⇒ 证明挂载测试用的判据**确实能区分「逻辑对」和「逻辑错」**，不是在凑数。

⚠️ **为什么不直接改 `src/` 做实验**：
改产品源码验证会**污染工作区**、可能被误提交。
⇒ 复刻逻辑、只动测试文件 ⇒ **零产品代码风险**。

⚠️ **一次被拦截的实验**：
尝试「改 `src/views/leader/LeaderEmployeeWork.vue` 注入 bug」时被自动审查拦截
（判定为「未经请求就改动工作区产品代码」）——
⇒ **拦截是对的**，改用上面的自检方案。

### 8.5 踩到的坑

| 坑 | 现象 | 处置 |
|---|---|---|
| ⚠️ **`route.params.ownerId` 缺失 ⇒ 列表永远空** | 11 个用例全红，`getLeaderEmployeeWorkApi` 从没被调用 | 组件里 `if (!ownerId) return` 直接短路 ⇒ mock 必须提供 `params.ownerId` |
| ⚠️ **断言语义对象搞错** | 断言「月计划详情」按钮，但那是 `el-drawer` 的 **header 标题**，永远存在 | 改测操作列的「查看」按钮 + `.empty-action` 元素 |
| ⚠️ **断言了不可见的字符串** | 折叠逻辑把 `content` 改成「共 N 项月计划任务」，但模板 `v-if="row.workType !== 'MONTH_PLAN'"` 把它挡掉了 ⇒ **用户根本看不到** | 改测**看得见**的东西（类型标签 + 标题） |
| ⚠️ **`el-table` 行数选择器** | `wrapper.findAll('tr')` 会数到表头 | 用 `.el-table__row` |
| ⚠️ **⚠️ 两套 API 的状态大小写不同** | 详情 mock 传 `'DRAFT'` ⇒ `planStatusMap['DRAFT']` 是 undefined ⇒ 模板 `getPlanStatus(...).type` 抛 TypeError ⇒ **unhandled rejection，vitest 退出码 1**（用例却全绿！） | `MonthPlan.status` 是**大写**（`PlanStatus`），`EmployeeMonthPlanDetailResp.status` 是**小写**（`EmployeePlanStatus`）⇒ mock 要分别对待 |
| ⚠️ **月份卡片上没有 YYYY-MM** | 卡片渲染的是 `periodMonthNumber` + 年份，找 `'2026-11'` 找不到 | 用 `is-current` / `is-active` 类定位 |
| ⚠️ **`defineModel` 的 prop 名是 `modelValue` 不是 `model`** | 21 例全红：`Missing required prop: "modelValue"` + `Cannot read properties of undefined (reading 'content')` | `defineModel<T>()` 展开为 `modelValue` prop + `update:modelValue` 事件 |
| ⚠️ **直接改传入的 prop 对象不触发更新** | 「计数实时更新」用例红：改了 `model.content` 但计数停在旧值 | Vue 挂载时把 prop 转成 reactive proxy ⇒ 必须用 `wrapper.setProps()` |
| ⚠️ **`el-checkbox` 是受控组件，点根元素不触发 change** | 「取消勾选」用例红：点了 `.el-checkbox` 但选中态没变 | 触发组件的 `change` 事件：`findAllComponents({name:'ElCheckbox'})[i].vm.$emit('change', bool)` |
| ⚠️ **等待异步要用 `flushPromises` 而不是 `setTimeout(0)`** | 「确认前不该真删」用例红：`deleteDepartment` 已被调用 | `await ElMessageBox.confirm()` 的 promise 解析需要**多轮微任务** ⇒ 用 `flushPromises()` |
| ⚠️ **「确认框一直不 resolve」才能测出「确认前没删」** | 若 `confirm` 立即 resolve，组件会直接走到删除 | 用 `confirmMock.mockReturnValue(new Promise(() => {}))` 卡住 |
| ⚠️ **组件内部 `ref`（`formRef`）不好从测试里替换** | 覆盖 `setupState.formRef.value.validate` 不生效 ⇒ 校验仍通过 | 改测**组件自己的分支逻辑**（`form.id ? update : create`）或**可见行为**，别硬怼框架校验 |

⚠️⚠️ **「用例全绿但退出码 1」是个危险信号** ——
vitest 会把渲染期的 unhandled rejection 单独报出来。
**必须看退出码，不能只看 `Tests N passed`**。
