## 三、两条路线

### 路线 A · 组件测试层（`@vue/test-utils` + `jsdom`）

**做什么**：把「读源码断言」逐步换成「真实挂载 + 交互断言」。

```typescript
import { mount } from '@vue/test-utils'
import WeekPlanApproval from '../../src/views/leader/WeekPlanApproval.vue'

test('超长计划文本不溢出容器', () => {
  const wrapper = mount(WeekPlanApproval, { props: { plan: { text: 'x'.repeat(500) } } })
  const cell = wrapper.find('.approval-text-cell')
  assert.ok(cell.element.scrollWidth <= cell.element.clientWidth)
})
```

**优点**：
- 覆盖**逻辑**而非源码文本 ⇒ 直接消灭「假绿 / 假红」；
- 无需起后端、无需浏览器 ⇒ **CI 里跑得快**（秒级 vs 数十秒）；
- 可在 CI 里**并行**跑；
- 不需要维护 E2E 数据。

**缺点**：
- 测不到「跨页面跳转」「真实路由」「真实 HTTP」；
- 组件有外部依赖（Element Plus、Pinia、axios）时需要 mock。

**成本**：🟢 **中**（基础设施 1–2 天 + 每个组件约 30–60 分钟）

### 路线 B · 端到端（Playwright）

**做什么**：真浏览器跑通「登录 → 填计划 → 提交 → 审批 → 填成果 → 确认」。

**优点**：覆盖**唯一真实**的用户路径 —— 前后端契约、路由守卫、状态管理全部一起验。

**缺点**：
- 需要**真起后端 + 建测试库**（CI 里要跑 Alembic 迁移）；
- 需要飞书 OAuth 的**替身**（CI 无飞书凭证）⇒ 得靠 `TEST_USER_PASSWORDS` 那条通路；
- 每个用例几十秒 ⇒ 只能覆盖**极少数**关键路径；
- ⚠️ **架构风险**：后端已有 `verify_plan_approval_e2e.py` 做同一流程 ⇒
  **同一套流程维护两份**，极易两边漂移。

**成本**：🔴 **高**（基础设施 2–3 天 + 每条路径 1–2 天）

## 四、推荐方案：A 打底 → B 收口

⚠️ **不建议直接做 B**。理由：

1. **B 覆盖不了 134 个组件里的大部分**。6 条 E2E 路径 vs 44009 行代码 ⇒ 覆盖率极低，
   而 A 能覆盖「任意一个组件的逻辑」。
2. **B 的维护成本会随时间增长**，A 的边际成本低。
3. ⚠️ **两条路线的真实关系**：
   - A 负责**「组件行为对不对」** —— 快、密、便宜；
   - B 负责**「整条链路通不通」** —— 慢、稀、贵。

   ⇒ 正确关系是**互补**，不是二选一。

**建议路径**：

```
阶段 1 · 基础设施（1–2 天）
  ├─ 装 @vue/test-utils + jsdom
  ├─ 解决「.vue 单文件组件」在 node --test 下无法 import 的问题
  │   （需要 vue SFC 编译步骤 ⇒ 要么接 vitest，要么写最小编译钩子）
  └─ 建立「组件测试」目录约定 + 命名规范

阶段 2 · 存量替换（滚动，不设截止日期）
  └─ 把 165 处「读源码断言」中**逻辑相关**的部分逐个换成挂载断言
     ⚠️ 纯样式/纯约定类的（如「必须用 approval-text-cell 类名」）
        保留读源码断言 —— 那类断言本身是合理的

阶段 3 · E2E 收口（2–3 天，只做 1–2 条最关键路径）
  └─ Playwright + CI 里起后端
  └─ ⚠️ 数据准备**复用** verify_plan_approval_e2e.py 的逻辑，而不是重写
```

⚠️ **阶段 1 的技术难点要提前说清楚**：

当前前端测试跑在 **Node 内置的 `node --test`** 上（`--experimental-strip-types`）。
它**没有 SFC 编译能力** ⇒ `.vue` 文件**无法直接 import** ⇒ 挂载测试跑不起来。

⇒ 必须二选一：

| 方案 | 做法 | 代价 |
|---|---|---|
| **接入 vitest** | 引入 vitest + `@vitejs/plugin-vue` + jsdom 环境 | 需要迁移 43 个测试文件的 runner（`node:test` → `vitest`），⚠️ 但 vitest 兼容 `node:test` 风格 API，迁移面小 |
| **自建编译钩子** | 给 `node --test` 加 `--import` 钩子，用 `@vue/compiler-sfc` 编译 `.vue` | 改动小，但要自己处理 CSS、scoped、依赖收集 |

⇒ **推荐 vitest**（生态成熟、后续接 Playwright 也更顺）。

### 7.2 关键设计决策

**① 两条测试腿并存，不合并**

| 测试类型 | runner | 位置 | 测什么 |
|---|---|---|---|
| 纯逻辑 / 静态约定 | `node --test` | `tests/*.test.ts` | 纯函数、源码文本约定 |
| **组件行为** | `vitest` | `tests/component/**` | ⚠️ **真实挂载 + 交互** |

⚠️ **为什么老测试不迁移**：43 文件 / 337 例全依赖 `node:test` API。vitest 兼容该 API，
但搬迁需重跑验证全部 337 例，且老测试里大量是「读源码断言」—— 对 vitest **零收益**。

⚠️ **为什么组件测试只能跑在 vitest 上**：`node --test`（即使带 `--experimental-strip-types`）
**没有 SFC 编译能力** ⇒ `.vue` 无法 import ⇒ 挂载测试根本跑不起来。

**② 生产用「按需自动导入」，测试用「全量注册」**

生产靠 `unplugin-vue-components` 的 `ElementPlusResolver` 在**编译期**改写 `<el-xxx>`；
vitest **不走**那个插件 ⇒ `<el-table>` 会变成未知自定义元素 ⇒ 渲染空壳。
⇒ 测试环境**手动全量注册** Element Plus（`setup.ts`）。

### 7.3 踩到的坑

| 坑 | 现象 | 处置 |
|---|---|---|
| ⚠️ **vitest 3.x 自带 2 个 critical 漏洞** | `tinypool` 原型污染→RCE；`vitest` 路径穿越→任意文件读 | 升到 **vitest 5.1.1** ⇒ critical 清零 |
| ⚠️ **`vi.mock` 提升问题** | 工厂引用顶层变量 ⇒ `undefined` | 改用 `vi.hoisted()` |
| ⚠️ **axios mock 形状不足** | `src/api/http.ts` 在**导入期**执行 `http.interceptors.request.use(...)` ⇒ `Cannot read properties of undefined` | mock 的 `axios.create()` 返回值也要有完整 `interceptors` |
| ⚠️ **`useRoute` mock 缺 `query`** | 组件 `onMounted` 读 `route.query.id` ⇒ unhandled rejection | mock 里补 `query: {}` / `params: {}` |
| ⚠️ **vitest 5 废弃 `poolOptions`** | DEPRECATED 警告 | 改成顶层 `maxWorkers` / `minWorkers` |

### 7.4 ⭐ 有效性验证（注入 bug）

⚠️ **光「测试通过」不能证明测试有用** —— 必须证明它**抓得到 bug**。

做法：把 `WeekPlanApproval.vue` 里的 `row.status === 'PENDING'` 故意改成 `'APPROVED'`：

```
❯ tests/component/week-plan-approval.component.test.ts (5 tests | 2 failed)
   × PENDING 行有「通过」和「驳回」
   × APPROVED 行**没有**「通过」和「驳回」
```

⇒ **2 个用例立刻变红** ⇒ 测试确实在测行为，不是摆设。

⚠️ **对照**：同样的 bug，**现有的「读源码断言」测试一个都不会红**
（它只确认 `'PENDING'` 这个字符串还在文件里）。
