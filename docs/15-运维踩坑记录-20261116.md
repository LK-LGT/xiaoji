# 运维踩坑记录（2026-11-16）

本文档收录 2026-11-16 实际踩到、且**已验证过解法**的运维坑。

> **为什么单独成文**：这些坑与功能开发无关，但每次重装环境 / 恢复数据 /
> 推代码时都会再遇到一次。散落在待办清单里容易被当成「背景噪声」，
> 单独成文才能在真正撞上时被搜到。

## 一、恢复数据库前必须先停掉占用它的进程

**现象**：把备份的 `perf.db` 拷回去后，**数据没变**。

**原因**：SQLite 的 `-wal` 文件会**回放旧事务日志**。
即使把主库文件拷回去，只要 `perf.db-wal` 还在，
SQLite 打开时就会把旧内容重新盖回去。

**正确顺序**：

1. 停掉 uvicorn（占用方）
2. 删 `-wal` / `-shm`
3. checkpoint 源库
4. 拷主库文件
5. **再删一次** `-wal` / `-shm`

**验证**：恢复结果要用**只读模式**（`mode=ro`）打开，
否则 WAL 回放会污染读数。

## 二、Alembic 迁移本身不会清空业务数据

**已逐版本回放验证**：`0017→0018→0019→0020` 全程
`assessment_record` 保持 **67 行**不变。

## 三、GitHub DNS 可能被劫持 / 污染

**现象**：本地解析 `github.com` 报 `Bad DNS packet`，
但 `ping` 通、`8.8.8.8` 能正常解析。
此时 git 推送会**连续失败几十次**（不是 git 配置问题）。

**解法**：用 `http.curloptResolve` 把域名钉到可信 IP ——
**只影响本次命令，不改系统 hosts**：

```bash
git -c http.version=HTTP/1.1 -c http.sslBackend=schannel -c http.ipv4=true \
    -c http.lowSpeedLimit=0 -c http.lowSpeedTime=999999 \
    -c "http.curloptResolve=github.com:443:<IP>" push origin <branch>
```

**取 IP**：`Resolve-DnsName github.com -Server 8.8.8.8 -Type A`

> 用阿里 DNS（`223.5.5.5`）也能解析，但给出的 IP 在本机 443 不通 ——
> 优先用 `8.8.8.8` 的结果，并**先测 TCP 连通性**。

## 四、Alembic 与应用的 DB 路径不一致

应用默认读 `backend/data/perf.db`；但在 `backend/` 目录下跑 `alembic` 时，
相对路径会解析到 `backend/data/`，在仓库根跑则解析到 `<root>/data/`。

**统一用绝对路径**：

```bash
DATABASE_URL=sqlite:///<绝对路径>
```

否则迁移会打到错误的库上 —— **迁移日志显示成功，实际写进了另一个库**。

---

## 五、PowerShell 里 shell 环境变量会残留

上一轮设的 `$env:DATABASE_URL` 会一直影响后续命令。

**跑迁移前先清掉**：

```powershell
Remove-Item Env:\DATABASE_URL
```

## 六、测试污染真实库的隐蔽路径：Alembic 子进程

**现象**：真实库 `backend/data/perf.db` 里混进了 `CI_ADMIN`（测试账号）。

**原因**：`test_hex_id_routes.py` 的 `_upgrade_schema_to_head()` 原本写的是：

```python
env = {**os.environ}
env.setdefault("DATABASE_URL", url)   # ⚠️ 问题在这
```

但环境里**通常没有** `DATABASE_URL` → `setdefault` 不生效 →
子进程（**全新**的 Python 进程）会重新读 `backend/.env`，
拿到**真实库**的绝对路径（`.../backend/data/perf.db`）。

于是「给隔离库建表」实际建到了**真实库**上，
真实库被塞进 `CI_ADMIN` 测试账号 —— **不可逆**。

**为什么难发现**：

- 这类污染**只在全量跑时出现**，单跑一个文件复现不出来
  （模块级 fixture 与全局引擎 `core.db._engine` 的交互）；
- 逐个文件跑也复现不出来；
- 看起来像「同步脚本把数据删了」，很容易误判方向。

**正确写法**（**直接赋值**，不是 `setdefault`）：

```python
env = {**os.environ}
env["DATABASE_URL"] = isolated_url   # 直接赋值，覆盖继承来的值
env["AUTO_CREATE_TABLES"] = "false"
```

> `env["DATABASE_URL"]` 的优先级高于 `.env`（pydantic-settings：
> 环境变量 > env_file）。

**已加护栏**（防复发）：
`test_no_orphan_test_dirs.py::test_subprocess_alembic_must_receive_an_explicit_database_url`
—— 所有「子进程跑 alembic」的测试文件必须**直接赋值** `env["DATABASE_URL"]`，
不接受 `setdefault`。护栏本身也做了双向验证：
改回 `setdefault` 立即失败，改回直接赋值立即通过。

**自查数据库有没有被污染**：

```python
import sqlite3
con = sqlite3.connect("file:backend/data/perf.db?mode=ro", uri=True)
print(con.execute("SELECT COUNT(*) FROM employee WHERE id='CI_ADMIN'").fetchone()[0])
# 期望 0
```
